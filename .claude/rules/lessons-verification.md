# Verification lessons — each line cost a real debugging session

Every rule here was learned by shipping the mistake first. They are one-liners because this file is
injected into every turn; keep them that way. Add a line only when a defect actually escaped.

## Tests

- A test that passes with its guard removed pins NOTHING — never accept a new test without a recorded neuter run.
- READ THE RULE'S MODALITY, not just its text: a **SHOULD** is not enforced by a refusal, so an adversarial refusal test for it asserts a behaviour the rule never claims. R1.3 ("every team SHOULD have a COS") is enforced by AUTO-CREATION — the honest assertion is *omit it → one is created*. Ask "what does violating this look like?" before choosing the test shape.
- When the guard is an INITIAL VALUE, sample it DURING render — `result.current` is read AFTER effects flush, so an effect that sets the same value makes the assertion pass with the initial value INVERTED. Mine did: `useState(true)` neutered to `false` left the test green until it pushed from the render callback instead.
- Bound a scanned function at its OWN closing brace, never at the next export: brace-COUNTING desyncs on a `{` inside a multi-line parameter type (it called the repo's most obviously-locked mutator unlocked), and end-at-next-export swallows the module-level block between them (a COMMENT mentioning the call was blamed on the pure validator above it). Strip comments too — a module that documents its own locking in prose will match every needle you aim at its code.
- A machine-parsed table is not a place for prose: the enforcement map splits Guard on commas and resolves each piece as a path, so one explanatory citation reddened two ratchet tests at once. Put the explanation in the test file, keep the column parseable.
- A neuter run that does NOT fail is a finding about the TEST: mine asserted through a table-level `since` skip and never reached the branch it named, so the guard was decorative.
- Seed a violation in EVERY shape the real data uses — one shape proves only that shape, and a "zero findings on the live corpus" criterion cannot detect a blind extractor at all: swapping mine to a prefix-requiring regex left the live run clean at exit 0 AND the prefixed seeded violation passing, so only the BARE-id variant caught it. Measure the shapes in the corpus first (`blocked-by: [X]` vs `[TRDD-X]` vs lowercase vs a YAML number), then seed one of each.
- When several ENABLED inputs can produce the same output, a test must switch off every one but the branch it names — mine left `localMarketplaces` at its default, so that branch added the same plugin first, `addCandidate` is first-write-wins, and stripping `agentId` from the `agentLocalScopePlugins` branch under test left the suite GREEN. Isolate the producer, or the assertion is about code you did not mean to test.
- Encode a guard at the granularity the BUG had — janitor#123 was COLUMN-granular and my per-table `since` could not express it, making the branch unreachable by construction, not merely untested.
- When one ladder step is all that ships, a version-skew guard cannot be exercised end-to-end — export the pure check and inject a synthetic spec, or it stays unverified until the bug recurs.
- A test that passes for an unknown reason is a failure: isolate it (`-t "<full name>"`) before believing it.
- A PLAN'S NAMED INJECTION POINT CAN BE UNREACHABLE IN THE SCENARIO THAT REACHES THE GATE YOU CARE ABOUT — and the informative candidate may be the one that does NOT abort: my card said "fail G11's `updateTeam`", but G11/G12/G13b are gated on a title the manager→autonomous path never holds, so `updateTeam` is never called. Probing all four post-gate collaborators found two reachable ones, and the finding was the one that returned `success: TRUE` over a half-executed cascade — invisible to any assertion on the return value. Probe every candidate and read the STORE, not the verdict.
- `vi.clearAllMocks()` clears CALLS, not IMPLEMENTATIONS — a mock overridden in one test leaks into every test after it.
- Route every mock through `(...a) => mockX(...a)` and restore it in `beforeEach`; an inline `vi.fn(async () => …)` in the factory cannot be restored.
- Pinning only the SUCCESS path reads as coverage — assert what happens when the operation fails, or the suite is decorative.
- `-t "R18.1"` also matches `R18.10`; read the test NAMES and COUNT, never the exit code (vitest exits 0 when a filter matches nothing).
- Asserting only `success === false` passes on ANY earlier refusal (a missing password, a failed auth gate) — pin the REASON, e.g. the specific gate in the ops trace.
- A fixture that models the filesystem as ONE constant boolean cannot test a post-condition: an install needs `existsSync` false BEFORE and true AFTER. Model the writes, or the post-condition stays a WARN forever.
- When a guard is unreachable in a fixture, say so in the test's docstring and file it — never seed the developer's REAL `$HOME` to reach it.
- `expect(err).not.toMatch(/one specific message/)` is satisfied by EVERY OTHER error — a positive control must assert `success === true`.
- Choose a positive control to FALSIFY the failure you fear, not to prove a list is non-empty: mine asserted a nested path and stayed green while the pathspec `dir/**/*.ts` silently dropped every TOP-LEVEL file (71 matched, 0 top-level) — including the file the test existed to protect.
- A source-scanning guard needs its scan set controlled too — assert a real count AND one file of each shape it must cover, or the guard reports "clean" on a set it never built.
- A verification gate that reads a REAL path passes vacuously in every test: it inspects state the fixture never touched. Point it at the fixture's seam, then model the write.
- A test can be propped up by the very bug you are fixing: 4 here asserted a cascade that only ran because the buggy ORDER put it before the gate that was failing.
- Provoke an unreadable-input test with ENOTDIR/EISDIR, never chmod — a permissions fixture passes VACUOUSLY when the suite runs as root, and CI often does.
- When the OS will not vary the input you are testing, INJECT it: `expect(got).toEqual(got.sort())` on a real dir passes with the sort removed, so spy the readdir and name the element that must move.
- A plan can name the wrong half of the tool: "wire the SEARCH at FTS5, acceptance byte-identical" was self-contradictory because the search takes a REGEX — and it was the ACCEPTANCE CRITERION, not the code, that exposed it.
- A shared positive control does NOT protect the assertions that never execute it — my neuter made the index fall back, both sides became walks, and 5 of 6 `expect(indexed).toBe(walk)` passed comparing a walk to itself; put the non-vacuity guard INSIDE the helper both sides call.
- An A-vs-B differential needs a fixture that DISCRIMINATES the axis you fear: zone order only shows up on a `cancelled` card in archived/ (non-terminal, so it survives the done-filter) sharing a blocker with a proposals/ card — every other shape agrees under both orderings.
- A subprocess test cannot be contained by `vi.mock` — redirect `$HOME` in the spawn env (`os.homedir()` honours it on POSIX), and PROVE containment by counting the real dir before and after, not by reading the code that was supposed to do it.
- A negative test must assert WHY it failed, not merely THAT it failed: neutering my API mutation-gate left every gated call still exiting non-zero (it now reached the missing-API-key check downstream), so an `expect_refusal` asserting only exit≠0 would have passed against a deleted gate — match the specific message and the neuter run names exactly the 3 tests that pin it.
- A seeded config file must satisfy its LOADER's version check or the loader returns DEFAULTS and every test silently exercises the OFF branch: my governance.json omitted `version: 1`, so 8 tests got the route's `user_authority_model_disabled` 409 instead of the guard under test — a fixture that tests the wrong branch, loudly enough to notice only because I read the error string.
- Before adding to a corpus, grep for EVERY test that READS it, not just the one the plan names: my plan named the conformance test's family array and a SECOND file asserted the live spec's exact clause census (38), so +3 clauses reddened a test nothing had predicted. Re-derive such a census with your own `grep`, never by copying the number out of the failure output — the count and the code would then agree by construction.
- Two guards over one file can look redundant and cover different failures: renaming `3P-IDX-01` → `3P-QQQ-01` reddened the family-NAME check while the exact-COUNT check correctly stayed green (still a valid declaration, count unchanged). Before deleting either as duplicate, name the mutation each one alone would miss.
- MEASURE an acceptance box before building for it, and mistrust the instrument it names: of two "unmet" boxes, one was ALREADY satisfied and the other prescribed a `vi.mock` helper for a SUBPROCESS writer it cannot reach. When a SIBLING file does not exhibit the bug, diff its setup first — the neighbouring CLI test already redirected `$HOME`, which named the fix and made the +1-per-run vs +0 count decisive.

- To prove a LOCK is taken BEFORE a read, make that read fail DISTINCTIVELY — then WHICH error arrives is the ordering assertion: mine returned `busy` when correct and `cannot read TRDD zone` under the neuter, and no assertion on "it threw" could have told those apart. Pair it with a positive control that the read really does throw when reached, or the whole test passes whatever the order.
- A shared "did the index answer?" guard does NOT prove THIS verb consulted it: `runBoth`'s fallback check only proves the PROCESS did not degrade, so reverting `next` to its old walk would have produced the correct answer, no fallback warning, and a green byte-identical assertion — a walk compared to a walk. Assert a per-verb ARTEFACT instead (a verb that never touches the index never builds one).
- Asserting the truncation NOTE is not asserting the truncation: an identity `capped()` still printed "+2 more not shown" and passed, because nothing checked the dropped rows were ABSENT. Every cap needs both halves — what it kept and what it lost.
- The neuter that proves a differential non-vacuous is also the one that can find a REAL bug: restoring the walk feeder made the two paths DISAGREE on the answer, and the walk was wrong (`asList` was array-only, so a scalar `npt:` was invisible to the linter in 7 places). A disagreement is a finding about the implementations, not a broken test — diagnose before repairing the test.
- A fix can be RIGHT and inert, and you have to measure which: `asList`→`refList` changed zero live verdicts because **0 of 196** live cards use the scalar form — so a live-corpus diff could never have validated it, and only the fixture differential could. Measure the INPUT (does the corpus even contain the shape?) before reading a zero diff as either proof or refutation.
- A suite of `not.toContain` assertions cannot tell a working probe from a broken one — each passes whenever the probe returns null for ANY reason. Mine had two such tests for a filesystem probe and its body was **unreachable in the whole file**: the fixture ctx deliberately failed the entry guard (`expectFolderGone: false`) so the probes "stay inert", which is right for those tests and means zero tests ever executed the read. Every probe needs one `toContain` — which IS a positive control by construction, since a store id cannot appear unless the probe returned a detail, so it needs no neuter of its own.
- When a guard's own comment says it defends against a FUTURE shape, the today-shape cannot pin it: my user-scope test passed with `scope === 'local'` DELETED, because a today-shaped user row has no `projectPath` and the path comparison alone already excluded it. Seed the shape the comment names (a user row WITH the path) and the same neuter reddens exactly that test. Read the guard's stated reason, then seed against THAT.
- Neutering two guards together is sound only when you can name which test each one alone would redden: mine were independent by construction (the soft-delete case never reaches the second guard; the outside-root case already satisfies the first), so one run attributed both. Check that property before combining, or you have one failure and two candidate causes.
- A test that reuses the implementation to compute its own expectation cannot detect a change in that implementation — derive the expected value from the RULE (slashes→dashes, everything else kept), never by calling the function under test, and pick an input carrying the characters an earlier version got wrong.
- When a gate's correctness is half PRESENCE and half PLACEMENT, ONE neuter pins only half the file: DELETING G09b reddened my 3 removal tests and left the 2 soft-delete tests green, while MOVING it out of its branch reddened exactly those 2 and left the 3 green. Either neuter alone certifies a file half of which is vacuous — run the complementary pair, and expect each behavioural test to fall to exactly one.
- The containment that makes a destructive test SAFE can be what makes its branch UNREACHABLE: faking only ONE side of a path-prefix guard (`resolvedDir.startsWith(agentsRoot)`) leaves the other side pointing at the real home, so `startsWith` is false and the whole branch — here a folder removal, a transcript purge, and the gate under test — is silently skipped. 5 files drove the function and none had ever executed any of it. Fake BOTH sides, in a dedicated file, or the branch stays untested no matter how many callers you add.
- Arming a destructive branch is safe when a broken mock makes it FAIL INERT, and that property is worth stating rather than trusting: if either layer fails, the prefix compare is false, the branch is skipped, and the fixture folder SURVIVES — so the "folder is gone" assertion doubles as the containment proof (it can only pass if the fake root took effect). Never add the arming mock to an existing multi-case file — it arms every other case in that file at once.
- A stub must cover BOTH halves of a collaborator — the gate's call AND the post-condition probe's read of the same store: omit the probe half and G10 degrades to "verification unavailable", which prints as a WARN and reads as a pass. A post-condition that cannot run is indistinguishable from one that found nothing.
- A double that models an external command as a pure NO-OP cannot tell "it worked" from "it left no trace and the pipeline silently retried": mine skipped `claude plugin install`'s settings write, so G16 succeeded invisibly, G17's re-scan found 0 plugins, and its recovery reinstalled — TWO calls every run. Relaxing to `>= 1` would have passed while the test described the RECOVERY path and claimed the happy one. Model the ONE side effect the code reads back.
- When the branch under test loses a race to `list[0]`, the FIXTURE'S ORDER decides whether it is load-bearing: with the standing pick listed first, my keep-branch test passed with the keep-branch DELETED. Put the value the else-branch would choose FIRST, so only the branch can produce the expected outcome.
- A neuter that reddens NOTHING may mean you mutated a SHADOWED expression, not that the test is vacuous: I flipped `hasMultipleOptions = len > 1` → `> 0` and all 3 stayed green, because the render is `isSingleLocked ? … : hasMultipleOptions ? …` and the single-item case never reaches the second arm. Find which branch actually MATCHES for your fixture before naming a guard — the rule's text pointed at `> 1` and the working guard was the arm above it.
- A rule that shares an already-driven guard looks like a FREE pin, and free is what invites pinning only the easy CLAUSE: R20.5's second clause ("unless the caller picked a different compatible plugin") had its own site — G15's keep-branch — cited by nothing and driven by nothing, so citing the file on the strength of the first clause would have dropped the ratchet over a still-unenforced half.
- An ABSENCE assertion whose selector could never match is vacuous in BOTH directions, and only a neuter says so: `queryByRole('button', {name: /^bob$/i})` never matched because each entry renders an avatar initial, so the accessible name is `"B Bob"` — the "member is not offered" guard passed identically with the guard deleted. Prefer the loosest selector that still discriminates, and treat a neuter that reddens NOTHING as a finding about the TEST.
- When the property is a CHANGE BETWEEN two calls, a fixture already in the end state cannot test it — the clock (or the state) must MOVE. My "does not re-insert a record that EXPIRED between the revoke and the restore" seeded an already-expired row, so the loader pruned it before the code under test ever saw it: it tested the loader, and it would have stayed GREEN under the neuter that deletes the expiry skip (an empty record list restores 0 either way). `vi.setSystemTime` between the two calls is what makes the name true — and fake timers were safe only because the lock arms its timeout on the CONTENDED path alone.
- A neuter that reddens a test belonging to a DIFFERENT rule has found a COUPLING, not a bug: pinning the COS name to exactly 2 on-screen occurrences (banner + roster row) made R7.8's neuter break an R4.8 test, so two rows meant to be independent could never fail independently. Assert a FLOOR in the borrowing test and move the exact claim into the rule whose text actually makes it.
- A guard every test MOCKS has NO test, and the mocks read as coverage: all five references to `checkTeamAccess` were `vi.mock(… vi.fn(() => ({allowed: true})))` — mocking the guard to prove the guard, so every one survives its deletion — and a sixth "hit" was a COMMENT. Mocking a guard's DATA SOURCES is fine and necessary; mocking the guard is the pattern that makes a grep sweep lie.
- An existing test on the same symbol may pin a DIFFERENT CASE than the rule governs: R18.8 is about a feature that CANNOT map, and its only `WarningCollector` test drove a model that maps fine with a note. Both call the same collector, so the sweep hits — read the rule's text against what the test actually feeds it, or you cite a rule off a test that would pass with the rule violated.
- Choose a neuter that leaves the SUCCESS/FAILURE bit unchanged when you want to prove an assertion is specific enough: deleting the anonymous-deny branch left `allowed:false` (the request just fell through to the not-a-member deny) and failed ONLY on the reason regexp — so the neuter's own output demonstrated that a test asserting `allowed === false` would have stayed green through it.
- A rule enforced by an ABSENCE has no guard to delete — the neuter must ADD the forbidden behaviour — and every one of its assertions passes VACUOUSLY against a code path that never ran: R17.18a's "the registry gained no row" is equally true when discovery returned nothing, so the same call must first prove it ran AND discriminated. Pick the mutation so it reds only the half it targets: writing the stranger into the registry left the SURFACING test green, which is what separates "hide strangers" from "show them without adopting them".
- A sweep hit can be a same-name function in a DIFFERENT module: `listAgents` is both `lib/agent-registry`'s (well tested) and `services/agents-core-service`'s (untested), so the grep looked like coverage of a rule nothing touched. Check the import path, not the symbol — this is the mirror of the all-mocks false positive, and it fails in the opposite direction.
- IRREVERSIBILITY IS A PROPERTY OF THE MUTATION, NEVER OF THE VERB — read the write before designing around it: I built a whole "commit point" split on "a revoked AMP key cannot be un-revoked, re-issuing yields a different key", and `revokeAllKeysForAgent` is `key.status='active'→'revoked'` on the SAME record with `key_hash` untouched. All three "irreversible" gates were lossless JSON row edits, so the fork the design existed to resolve did not exist. `revoke`/`purge`/`destroy` name an INTENT; the code may be a status flip.
- A design that routes AROUND a rule usually re-proposes the thing that rule superseded, under a new name: my "irreversible tail, best-effort, failure is residue the post-condition reports" is verbatim what R51 abolished ("There is no reporting option. This supersedes the detect-and-report contract of TRDD-KERM18NX"). Before inventing an exception, grep the rule for the shape you are about to propose.
- A CODE COMMENT is not evidence about a RULE, and a sub-agent quoting one is not evidence at all: the advisor wrote "the auto-demote was convenience, not mandate (comment at 7055-7057)", I ruled on it, and `GOVERNANCE-RULES.md:482` (verdict **Explicit**) plus its normative spec twin both MANDATE that auto-demote — with a test pinning it. I was one commit from a governance violation, on a second-hand reading of a comment. Grep the rule corpus for the behaviour before ruling that the behaviour is optional.
- A ruling that requires editing the governance corpus is BY CONSTRUCTION not a ruling you may make under a general delegation: "you solve them" delegates decisions, not rewrites of `GOVERNANCE-RULES.md` + its spec clause + the test that pins them. Notice the edit the ruling implies BEFORE making the ruling — the file you would have to touch names the tier.
- A recorded "this CANNOT be tested" is a claim about the author's TOOLKIT, not about the code, and it is the second-hand report nobody re-checks because it closes the question: R20.28's decline ("a vitest assertion could only grep the script's TEXT, which pins the text and not the behaviour") was right about grepping and wrong that grepping was the only option — a subprocess with `$HOME` in the SPAWN ENV observes the behaviour, and 13 tests plus 4 neuters followed. Re-derive the option set before inheriting an untestable verdict.
- When the reason a guard is untestable is that it is BURIED, extract it — and prove the extraction byte-faithful by diffing against `git show HEAD:<file>` before trusting a single test that runs it: mine differed in exactly the 5 `SCRIPT_DIR` lines I intended, which is the only evidence that the 13 green tests describe the shipped behaviour and not a paraphrase of it. The extraction also turns a line-range citation (rotted ~87 lines, pointing at unrelated working code) into a whole-FILE one, which cannot rot.
- A COMMENT claiming a test exists is not a test, and it is worse than silence because it tells the next reader not to look: a headless-parity file said the restart manager-gate "is covered there by the governance suite", and the string `Cannot restart team agent` appears in ZERO tests in either mode — only the WAKE twin is driven. Grep the assertion the comment promises before trusting it, and when it is absent correct the comment IN PLACE rather than only filing the gap.
- A test that drives a FAITHFUL double of an interface cannot see that the REAL implementation of that interface is broken, and the two altitudes must BOTH exist: my fake adapter correctly asserted `targetDir`/`scope` at the boundary while the real adapter turned them into `--cwd <dir>`, an option `claude` does not have — so the gate under test was a no-op and 8 tests were green. When a boundary test is the only coverage, ask what the boundary is TRANSLATED INTO and pin that separately (here: the dir must be in the spawn OPTIONS and must NOT be in the arguments).

- A test can ASSERT THE NEGATION of a rule's named case and pass forever, under that rule's own name: R20.29 enumerates four sources and says the install step ALWAYS uses the client protocol for all four, and the governance test for it was titled *"routes a LOCAL-container source away from the CLI"* asserting `expect(claude call).toBeUndefined()` for source (c) — the one the rule names. Both map columns were green (the Guard citation had rotted onto retry-backoff code), because the routing decision it pointed at is real, deliberate, working code, so a test written against it looks exactly like coverage. Reading a rule's CITATION is not reading the RULE — open the rule text and check it against the branch, not against the line the map sends you to.
- COLLAPSING A BRANCH LEAVES THE REMOVED ARM UNPINNED BY CONSTRUCTION — every existing test feeds the input that took the SURVIVING arm, so it passes before and after and proves nothing about the change. My install-side neuter reddened 6; the identical uninstall-side neuter reddened **0** (exit 0, 4395 green over a fully reverted half), because every uninstall test passed a REMOTE marketplace and none ever passed a local one. After collapsing a branch, ask which INPUT used to select the deleted arm and grep whether any test supplies it.
- A FIX HAND-REPLICATED ACROSS SIBLING BRANCHES IS A COVERAGE QUESTION, NOT AN EDIT — and N-1 of N is indistinguishable from N: `4520ef9a` gave CreateAgent's R51.5 shape to G06's two branches and G07c and left G07b setting `agentId = null` unconditionally, because the only R51.5 test drives G06. Nothing reddened, and the missed site was the WORST one (its orphan has already joined a team). After fixing one instance of a repeated shape, grep for the shape — not for the symptom — and count the sites against the tests.
- PICK A NEUTER'S MUTATION FROM THE FIXTURE, NEVER FROM THE ENUM — one aimed at a value no test reaches reports the OPPOSITE of the truth: deleting `'backburner'` from the shared `DEFAULT_STATUSES` reddened only the DOCTOR, which reads as "the write gate re-authored the grammar", and no guard test uses `backburner`. Re-aimed at `'testing'` (the value the gate's own ratified-column positive control exercises), ONE mutation reddened BOTH consumers — which is what "one definition, not two that drift" had to mean.
- A CROSS-SCOPE FINDING IS A PROPERTY OF THE UNION, so EVERY SUBSET REPORTS CLEAN and the per-part run is not a weaker check but a blind one: `memgrep lint` read **0 ERRORs on each of the three memory scopes individually** (130 + 120 + 159 = 409 findings) while the union read **416 with 7 ERRORs** — all 7 being links whose two ends live in different scopes, so no single-scope run could see any of them. Before concluding "not in my scope, so not mine", check whether the rule being checked is even EXPRESSIBLE within one scope; the arithmetic (409 + 7 = 416) is what named the missing 7 as relational rather than missed.
- A "BIGGER THAN THE BIGGEST SINGLE FILE" FLOOR IS A CLAIM ABOUT A POPULATION, and grep and the extractor count different ones — so a floor taken from grep is a number about a set nothing reads. Mine sat at 55 while the biggest file had grown to 60, so a SINGLE-file read satisfied it and the guard quietly stopped meaning anything. Re-derive such a floor through the code that BUILDS the set (`walkRecords` saw 36/27 where a hand regex saw 49/29).
- A NEUTER MATCHED BY CODE SHAPE HITS EVERY PIPELINE THAT SHARES THE SHAPE — anchor it to a LINE NUMBER, and count the sites before running: my `s/if \(installResult\.success\)/…/` was meant for ChangeTitle's G16 and also silently broke `InstallElement::G08` and `CreateAgent::G11`, while `const updated = await updateAgent(agentId, {programArgs: newArgs})` also hit `ChangeCLIArgs::G04`. Only the post-substitution `grep -n` (7 hits where I intended 4) caught it; the run would have reddened tests in three unrelated pipelines and I would have attributed them to the gate under test.
- AN INERTNESS NEUTER *INVERTS* THE MOMENT THE THING IT PROVED INERT GOES LIVE, and running the unchanged mutation is the cheapest possible proof the wiring took: for seven slices "make the new undos throw" had to leave `change-title-window` GREEN (the driver never called them); after the swap to `runGateSequence` the identical mutation REDS it. No new test was needed to demonstrate the swap — the old neuter's flipped verdict IS the demonstration. Keep the neuter that proves a thing is disconnected; it becomes the one that proves it is connected.
- A NESTED TRANSACTION'S HONEST MESSAGE BECOMES A SUBSTRING OF THE OUTER ONE'S — so a bare substring assertion silently changes what it is about: CreateAgent's R51.5 test asserted `not.toMatch(/no changes were made/i)` on its own verdict, and once ChangeTitle became a transaction its clean R51.3 "…NO CHANGES WERE MADE…" was quoted verbatim as CreateAgent's `Cause:`. **Both claims were true and they were about DIFFERENT SYSTEMS** (the inner made none; the outer made some and could not undo them). Anchor an assertion about a VERDICT to the start of the message, never to a phrase that a nested cause may legitimately contain.
- WHEN A COMBINED NEUTER REDS SOMETHING, RUN THE COMPLEMENT BEFORE NAMING THE CAUSE: breaking G16+G16b+G17 together reddened 3 tests whose names all said G17, which is suggestive and not proof — restoring ONLY G17 and re-running left **310 files, ZERO red**, which is what actually established that G16 and G16b are unpinned and that all 3 failures were G17's. One run gives you one failure and N candidate causes; the second run costs the same and gives an attribution.
- "UNDO THROUGH THE MECHANISM THAT PERFORMED IT" MEANS THE PRIMITIVE, NOT A PIPELINE THAT WRAPS IT — routing an undo through a higher pipeline imports gates the forward path never ran, and ONE of them can make the undo impossible BY CONSTRUCTION: my G16 undo called `ChangePlugin`, whose G08 refuses to uninstall the plugin the CURRENT title requires, and on a reverse unwind that title is still the NEW one (the gate that restores it is EARLIER in the array, so it runs LATER). Every rollback past that gate reported R51.5 CRITICAL over a fully recoverable system. Fix by symmetry — call the mirror primitive — never by widening a bypass flag four other callers share.
- A COMPENSATION CAN BE MASKED BY A GATE IN A *DIFFERENT PIPELINE* ITS NEIGHBOUR CALLS, not only by a sibling gate: G15's undo reinstalls via `ChangePlugin(action:'install', rolePluginSwap:true)`, and THAT pipeline's own G11b rewrites the very `programArgs` G16b's undo restores — so neutering G16b's undo left the file 13/13 GREEN. Choose a fixture where the masking neighbour has nothing to do (here: seed NO role-plugin, so its ledger is empty and only the gate under test can restore the value).
- A SHARED WORKDIR ACROSS ONE FILE'S TESTS CARRIES STATE THE FIXTURE NEVER WROTE — `seedAgent` only `mkdir -p`s it, so a plugin an earlier happy-path test installed SURVIVES, the gate under test prints `Skipped (plugin unchanged)`, and the assertion passes over a gate that never ran. Both my tests were vacuous until each one WROTE its plugin set; `null` is a write, not an omission.
- TWO GATES THAT PRODUCE THE SAME OBSERVABLE ARE INDISTINGUISHABLE WITHOUT A NEUTER, and the one that reddens NOTHING is what tells you which gate you actually pinned: my test was written for G15's undo and pins G14d's (both uninstall role-plugins, both undos reinstall them). G14d runs FIRST and removes everything incompatible with the new title, so G15's detection finds nothing, its ledger stays empty, and its undo is UNREACHABLE on any compatibility-altering title change. Name the gate a test pins by MEASUREMENT, never by reading the array order.
- A STORE MOCKED AS A RETURN VALUE CANNOT PIN A RESTORE: `restore: async () => world.aidTokens` hands back a number and mutates nothing, so "the tokens came back" was true before the pipeline started and both one-line undos were unpinnable. Model the store as STATE (revoking DRAINS the counter, `restore()` puts the exact count back) and assert the SEEDED value with `toBe` — a restore that re-inserts a different number is a different bug wearing the same shape.
- WHEN A UNDO-PATH TEST FAILS ON THE VERDICT WHILE ITS OWN STATE ASSERTIONS PASS, THE BUG IS A NEIGHBOUR'S: mine asserted the flag (restored, correct) and `not.toMatch(/INVALID STATE/)` (red) — the second assertion is the only one that could see G16's broken undo, because a rollback's verdict is a property of the WHOLE unwind. A test that asserts only the state its own gate owns will call a half-failed rollback clean.
- WHEN A TEST CLAIMS "THE RIVAL IMPLEMENTATION WOULD FAIL THESE ASSERTIONS", THE NEUTER IS TO *IMPLEMENT THE RIVAL* — deleting the guard proves only that something is load-bearing, never that the test DISCRIMINATES the wrong fix from the right one. Mine asserted that an abort-at-G10 shape "passes every assertion above and FAILS these two"; writing that abort proved it exactly — it passed `success:false`, both error regexes, both residue assertions AND the ops assertion, and died only on `calls == ['removeManager','blockAllTeams']`. Without it the sentence would have been a comment no neuter reds, next to four assertions that a wrong fix satisfies.
- AN **ORDER** CLAIM IS INVISIBLE TO AN END-STATE ASSERTION, because the end state is the SAME either way — so its neuter is the SWAP, never a deletion: my two obvious neuters (undo writes the wrong value / undo made inert) both reddened, and neither could tell an out-of-order undo from a correct one. Moving the wake ahead of the flag restore left the end state at `false` and reddened exactly one line; the proof is that commenting out THAT line turns the swapped code GREEN. Two neuters that both redden are not two proofs when a third mutation the test names is untested.
- A PROBE THAT RECORDS THE **LAST** OCCURRENCE IS DEFEATED BY A LATER, CORRECT CALLER OF THE SAME COLLABORATOR: G10's undo re-wakes too, after G17 has already restored the flag, so last-write-wins read G10's `false` and the swapped G17 undo passed. Record the FIRST observation when the claim is about WHEN something happened — and check who else calls the collaborator before deciding which.
- A NAME-KEYED DETECTOR CANNOT SEE A COPY UNDER A DIFFERENT NAME, and the miss is invisible because the sweep reports CLEAN: `one-json-io-implementation.test.ts` forbids a fifth copy of the json-io family by matching the NAMES `loadJsonSafe|saveJsonSafe|readJson`, and the worst-placed copy in the tree was called **`readJsonSafe`** — one character — so the family looked consolidated while the only file that wrote the user's global settings.json with a direct `writeFile` survived, at five sites. When the harm is defined by a TARGET (this file must not be written unguarded), key the rule on the target, not on the helper's name; the offender then cannot rename its way out.
- A REGEX'S POSITIVE CONTROL EARNS ITS KEEP THE FIRST TIME YOU WRITE THE REGEX: both detectors in one new ratchet were broken and both were caught by their own controls, not by the sweep (which read "clean" either way). `writeFileSync?` parses as *"writeFileSyn" + an optional `c`* and therefore matches **NEITHER** spelling — write `writeFile(?:Sync)?`. And `[^)]*` cannot cross the `)` in `join(os.homedir(), '.claude', 'settings.json')` — the inline form the second legitimate owner itself uses — so the detector would have reported its own allowlisted file as absent; a bounded lazy `[^;]{0,120}?` stays inside one statement and crosses the nested call.
- PUT THE ASSERTION THE TEST IS *NAMED FOR* FIRST — a weaker assertion ahead of it absorbs every neuter and the strong one never executes: with the end-state check first, both my neuters died on it, so the ordering assertion the test exists for was reached by no mutation at all and was pinned by none of them. Assertion ORDER decides which assertions a neuter can reach.
- A RACE TEST THAT RELIES ON NATURAL SCHEDULING IS A LOTTERY — assert the EXCLUSION directly instead: mine fired four concurrent writers and asserted every write survived, and it passed under the neuter that removed the shared lock entirely, because whether the losing interleaving OCCURS is the scheduler's choice (and `updateJson`'s staleness gate absorbs many of the orderings that would lose one). The deterministic shape is *hold the lock, then observe that the contender cannot finish* — `expect(done).toBe(false)` while held, `release()`, `expect(done).toBe(true)` — where the second half is a mandatory positive control, since `false` is equally satisfied by a contender that threw, hung, or was never called.
- START THE CONTENDER OUTSIDE THE HOLDER'S CALLBACK when the lock is REENTRANT — AsyncLocalStorage propagates into anything called inside, so a contender started there inherits the held set, skips the lock, completes instantly, and the test passes no matter what the code does. It must run in a SIBLING async context to contend at all.
- A SHARED MODULE-GLOBAL MAKES A FIXTURE'S DISCRIMINATING POWER DEPEND ON TEST ORDER, which is indistinguishable from coverage: my backup-prune test ran with the write counter already past 40, so all thirteen names were 2-digit and sorted correctly with or without the zero-padding under test — the neuter reddened NOTHING. A test-only pin (`_setAtomicWriteCounterForTests(5)`, spanning 6..18) makes the fixture straddle the 9→10 boundary that is the only place padding changes anything. When a property has a BOUNDARY, the fixture must cross it on purpose, never by luck.
- COUNT A CODEBASE'S LOCK IMPLEMENTATIONS BY READING, NOT BY GREPPING THE ONES YOU KNOW: my card said "the guarantees are split across TWO modules" and a `grep -c 'withSettingsLock\|withJsonLock'` returned 0 for `claude-adapter.ts` — which I read as "unlocked" when it was locked by a THIRD mechanism, `withLock(settingsLockKey(path))`, a string key in a process-local Map. It guarded the SAME file the other two guard, so the two modules excluded each other NOWHERE — not even inside one process. A grep for the locks you already know about cannot find the one you do not.
- "ONE LOCK" MEANS ONE PHYSICAL OBJECT CONTENDED FOR, not one function each module calls: a string key in an in-process Map and a `mkdir` lockdir on disk are both "the lock", share nothing, and produce a system where every module is individually correct and the whole is unserialised.

- A CLEAN `git status` IS NOT EVIDENCE ABOUT A PROCESS THAT IS STILL RUNNING — it samples an INSTANT, and between a background agent's steps that instant is empty: mine returned nothing, I concluded "the agent produced zero work, its report was fiction", and it was mid-flight and had already moved a card (`design/tasks/` had dropped 113 → **112**, a number I printed in the same block and did not reconcile). I was one step from hand-closing a card it had already staged — the exact double-work I had warned about in that card's own STATE block. A garbled completion notice primed me to expect failure and I let the expectation pick the conclusion; the instrument was fine, the SAMPLING MOMENT was the flaw. Before declaring a running process idle, sample TWICE with the counter that must move (`find … | wc -l`), and treat a "completed" notification that contradicts the repo as untrusted rather than the repo.
- "SKIPPED 0" ON A CONTRACT THAT MAKES SKIPPING CORRECT IS A CLAIM TO PROBE, NOT A PASS: verify it by FALSIFYING one of the agent's own checklist assertions against live code, never by re-reading its report. Mine claimed a trust-shortcut was gone from a shell script — the only surviving hit was a COMMENT describing the removed bug, and its three cited SHAs all resolved, which is what made 18/18 credible. A tally is not evidence; a claim you could have proven false is.
- THOROUGH COVERAGE OF ONE HALF IS WHAT MAKES THE OTHER HALF'S ABSENCE READ AS COVERAGE — so the well-tested side is where to *start* looking for the gap, not where to stop: my file-bridge reader had 9 tests (staleness, pid guard, garbage, `JSON.parse` succeeding on `42`/`null`/`[]`) and the WRITER had none, and deleting `clearBootRestore()` from the service's `finally` left the FULL suite green — **359 files, 5051 tests, zero red**. Nothing looked untested, because the module everyone would open WAS tested. The asymmetry is the camouflage; measure the neuter on the half nobody wrote a file for.
- A SYMBOL'S TESTS PROVE ITS BEHAVIOUR AND NEVER ITS REACHABILITY, so "well tested" and "never runs" are indistinguishable without a PRODUCTION-CALLER COUNT — and the count needs a positive control, because a zero is also what a broken search returns. Twice in one hour, from opposite directions: `UserRecord.assistantAgentId` is READ by 4 production sites (the R38 messaging edge, the R39.6 cascade-delete) and written non-null by **zero** — every non-null value in the tree is a fixture, so the enforcement suite is green over a state production cannot enter; and `lib/oauth-rotator/cascade.ts` has **0** production callers against 26 test references (`cascadePlan` 0/3, `cascadeSummaryLine` 0/4, `CascadeLeg` 0/19; control `oauthOf` = 14 prod), because the live path re-derives the same taxonomy inline — and the two copies' constants had already drifted 3× apart (`KEEPALIVE_AHEAD_H` 6 vs 2.0). **⚠ STATE CORRECTED 2026-08-22T16:59 — RESOLVED, by DELETION, which is the right fix.** `cascade.ts` is gone (`b50cf390`, *"delete cascade.ts + cookie-vault.ts — a dead port of the janitor's live layer"*); all three symbols now read 0 prod / 0 tests, `KEEPALIVE_AHEAD_H` has exactly ONE definition (`lib/oauth-rotator/tick.ts:102`), and the drift went with the duplicate. **The measurement lesson stands unchanged** — count callers in `lib services app components` MINUS the defining file, with a control, because a zero is also what a broken search returns (the control itself has since moved 14 → 3, which is why it must be re-run and never quoted). **SECOND stale state-claim of my own found within one hour** (the other: the dev-mode enable flag above). This file accumulates STATE claims and they rot silently while being taught every turn — when you cite one, re-verify the artifact first and correct the state in place. Both modules even DOCUMENT their own safety: cascade's comment says its defaults "only matter when classify is used standalone (e.g. a unit test), so they are never a second source of truth" — with no callers, standalone-in-a-test is 100% of its usage, so the escape clause describes all of reality. Count callers in `lib services app components` MINUS the defining file, never grep the symbol globally: its definition and its tests both match and read as use.

- A FIX THAT ADDS A NEW MEANING TO AN EXISTING SENTINEL RE-CREATES ITS OWN BUG ONE LAYER UP, and the consumer reads as correct because it WAS correct when written: `usageRequest` returned status **0** only for network-error/abort/timeout, so `tick.ts`'s `const networkUp = liveStatus !== 0` was fair — then the 429-back-off card made 0 ALSO mean `cooldown` (we are throttling ourselves, deliberately) and `lock_contended` (another process is probing), and a self-imposed back-off became "the API is unreachable". The same failure the back-off existed to fix, arriving by the route the back-off opened, through FIVE gated behaviours — including a log line that says `API unreachable` and aims the next debugger at the one place nothing is wrong. When a change widens what a sentinel can MEAN, grep every CONSUMER of that sentinel in the same commit: the call sites do not change, so nothing reddens and nothing warns.
- A TEST SEAM NO CALLER CAN REACH IS NOT A SEAM, and its own docstring will insist that it is one: `NetworkDeps` declared `cooldownStore`/`probeLock` and explained that without them a 429 test writes the DEVELOPER'S real machine-wide state — while `netDeps` forwarded only `fetchImpl`, so no tick test could ever drive a cooldown. That is precisely why the overload above sat undetected. Follow a seam from the TEST'S entry point inward, never from the module's declaration outward.
- A NEUTER THAT REDDENS NOTHING IS A MEASUREMENT OF THE FIXTURE, and twice in one new file the fixture never reached the branch it named: one test ran at 50% usage, where the tick logs "within limits" and RETURNS before the candidate loop, so it counted refreshes on a path that never executed; another's fetch stub THREW BEFORE INCREMENTING ITS COUNTER, making an ATTEMPTED probe indistinguishable from a skipped one — so the mutation hard-wiring the guard TRUE passed unnoticed, which is the one mutation that test existed to catch. Both zeros looked like "this guard is unpinnable"; both were three-line fixture bugs. Count the ATTEMPT, and prove the fixture reaches the branch, before writing a guard off as untestable.
- WHEN A CARD'S PREMISE IS A GREP THAT "RETURNED NOTHING", RE-RUN THE GREP BEFORE BUILDING ON IT: mine opened *"there is no cache, TTL, cooldown, or Retry-After handling anywhere around `usageRequest`"*, and the module implementing all four — at the **exact constants the card proposed** — had landed under a different TRDD in the interim, wired and tested. Four of six acceptance boxes were already satisfied elsewhere, and building the card as written would have produced a second implementation of a working one. A card records a measurement taken once; the tree moves underneath it, and the more precisely a card states its evidence the more convincing the stale version reads.
- …AND A PARKED CARD'S **BLOCKER** IS THE SAME TRAP, AT A MEASURED **4-IN-5** RATE — parking is what stops anyone re-reading it, so the staler it gets the less likely anyone looks. Swept five parked cards in one sitting: a restart "the owner must authorise" HAD happened hours earlier (box satisfied, card advanced); a branch recorded as unpushed WAS pushed, so a peer had been waiting on an open gate (660 commits ahead → 13, 0 behind); a var that would "self-correct on the next restart" survived one that night, because a plain `pm2 restart <name>` replays the CACHED env and only `restart ecosystem.config.js --update-env` re-reads the file; and a CRITICAL fleet blocker (0 prefixed tags in two repos) had been fixed and CLOSED upstream 8 days before. Only one of the five was genuinely still blocked. **The fix is to write down the COMMAND, never the STATE:** `git diff <remote> HEAD -- <path>`, `cmp` against the installed copy, `ps eww -p <pid>`, `gh issue view N --json state` — each is seconds and re-runnable, whereas "the branch is unpushed" is a fact with a silent timestamp on it. A blocker with no test written beside it is a claim nobody can cheaply refute, so nobody does.

## Tools that gate

- A reader that returns `[]` on an I/O error turns its gate into one that passes because it read nothing — separate ENOENT (legal absence) from every other errno (a fault), or "clean" and "unread" are the same answer.
- A gate needs THREE exit codes: 0 clean · 1 findings · 2 could-not-run. With two, every failure to read reports success.
- The non-vacuity guard belongs in the TOOL, not only in the test that happens to exercise it — ours asserted `scanned > 100` in vitest for months while the shipped CLI certified an empty read.
- A secret/PII scan keyed on ONE shape is blind to every other shape BY CONSTRUCTION: mine matched `*.ts.net` FQDNs and so could never see the bare hostname, the raw `100.x` address, or the `user@` that were sitting in the same file — enumerate the classes, print a COUNT per class, and carry a positive control proving the scanner sees a string you know is present.
- A gate whose regex match CONSUMES its argument window skips every call site inside that window: mine matched `verb\s*\(` PLUS 240 chars, so `exec` advanced past a `saveJsonSafe(USER_GLOBAL_SETTINGS…)` sitting two lines below an `mkdir(…)` and reported it clean — match the verb ONLY, extract arguments separately.
- Splitting a call's first argument with a regex mis-cuts nested calls: `/,(?![^(]*\))/` cut `mkdir(join(CLAUDE_DIR, 'plugins'), …)` in the wrong place and attributed the finding to whichever token appeared later, so the SITE was right and the REASON was wrong — count bracket depth and skip string literals.
- A source scanner must EXCLUDE ITSELF — its own docs and pattern tables necessarily contain the patterns it hunts, so it reports its own prose as findings (the `pgrep -f` self-match trap, one layer up); mine flagged 2 violations in the detector file, which writes nothing.
- PIN what a detector CANNOT see: a write through a local variable (`renameSync(tmp, file)`) is invisible to textual matching, and silence about it reads as absence — list the blind spot as data and test the list, so it cannot grow unnoticed.
- Never print an `empty = none` label unconditionally after a grep — mine printed under a NON-empty result and I read "clean" off a screen that was listing the hits; label from the count, not from hope.
- A shared "set up the connection" helper can contain a WRITE, so an OBSERVER that calls it modifies what it measures by a route nobody would call healing: `applyPragmas` sets `journal_mode = WAL`, which is persistent, so a read-only verifier would have silently converted every rollback-journal index it inspected. Read what the helper does before reusing it on a path you only mean to look at.
- An observer that OPENS a path CREATES it unless told not to — `new Database(p)` materializes an empty db, so a sweep with one bad path leaves litter shaped exactly like the thing it audits. `fileMustExist: true` is the difference between an observer and a writer, and it is one word.
- A BOUNDED audit log written by a POLLING observer destroys the signal it exists to keep: at 50 slots and a 6-hourly sweep, one unrepaired fault fills every slot with copies of itself in two weeks and evicts all real history — the log then looks full of history and contains none. Record a TRANSITION (append only when this is not already the newest entry), never a poll.
- A CONDITION WRITTEN ONLY OVER THE *BAD* ITEMS IS VACUOUS ON AN EMPTY SET, and a governance rule is as vulnerable as a CLI: our "hard gate" said a terminal card needs *every `- [ ]` box checked*, so a card with NO checklist passed having proven nothing — inert on **87 of 108** open cards and **46** archived `completed` ones, three of them closed AFTER the rule landed. Any "no X may be Y" needs a companion "there is at least one X", and the retroactive half needs a stated grandfather boundary — flagging all 46 is the wall of warnings that gets a linter routed around.
- …AND THE SAME GATE HAS A **MIRROR** FAILURE THAT LOOKS LIKE DILIGENCE: a card whose body uses `- [ ]` for a SPEC LIST can never close, because the gate counts every box in the FILE and a specification is never "done". Met both in one night — one card with zero boxes (gate proves nothing) and one whose four `W-A..W-D` spec bullets duplicated its own Acceptance section (gate unsatisfiable with every acceptance box green). Same root: checkbox syntax doing two jobs. **One card, one gate — the boxes that gate live under `## Acceptance` and nowhere else.** Censused across this corpus the same night: of **124** open cards, **55 carry no boxes at all** and **8** carry boxes outside/above an Acceptance heading, so ~half the board's gates are still vacuous or ambiguous; **123 of 248** ARCHIVED cards closed with no boxes, which is the historical exposure and is frozen, not repairable. Do NOT script-repair that — per-card judgment, or the sweep destroys the audit trail it was meant to fix.
- A FUSED ACCEPTANCE BOX IS UNTICKABLE BY CONSTRUCTION WHEN HALF OF IT BELONGS TO SOMEONE ELSE — and it makes finished work read as unstarted: "post the answer on #134 AND confirm the consumer is unblocked" stayed open for 8 days over a relay that had shipped three comments, and "W-D posted ✓ and #46 CLOSED ✓" sat unchecked because a deferred probe shared its box. Three instances in one session. Split the act you control from the reply you do not, and tick the half you did — a box whose completion depends on another party's answer can never be honestly checked by you.
- A `vi.mock` FACTORY THAT SPREADS THE REAL MODULE AND REPLACES *NAMED* EXPORTS STOPS MOCKING SILENTLY WHEN THE CODE CHANGES VERB — and for a WRITE that is not a broken test, it is an ESCAPE: my route migrated `saveJsonSafe` → `updateJson`, the mock went on faithfully mocking a function nobody called, and the REAL writer ran against the DEVELOPER'S OWN `~/.claude/settings.json`, adding a marketplace named after the test fixture. The suite reported ordinary assertion failures and NOTHING said the global config had been edited. Guard it verb-agnostically — snapshot the real file around the suite and fail loudly if the bytes moved (naming CREATED/MODIFIED/DELETED, since those are different incidents) — because a mock list keyed on names cannot protect against the next rename either.
- A SCANNER KEYED ON VERB *NAMES* GOES BLIND THE MOMENT A REFACTOR RENAMES THE VERB, and blind reports as CLEAN: migrating three call sites from `saveJsonSafe` to `updateJson` dropped the write-boundary detector from 3 out-of-root findings to **ZERO** ("OUT-OF-ROOT WRITES (0)") — the writes had not stopped, the needle had stopped knowing what a write looks like. Only its own non-vacuity assertion (`byClass.constant > 0`) caught it, which is exactly the case that assertion exists for, arriving from a direction nobody predicted. Add a new write primitive to the verb list in the SAME COMMIT that introduces it.
- DELETING A NOW-STALE ALLOWLIST LINE WITHOUT RECORDING WHERE THE WRITE WENT MAKES A REAL WRITE INVISIBLE TO EVERY LIST AT ONCE: my `mkdir :: USER_GLOBAL_SETTINGS` entry went stale because the explicit call moved INSIDE the lock primitive — where it happens on a PARAMETER and no textual scan can ever see it. Stale-in-the-allowlist and gone-from-the-codebase look identical; the honest move is to re-home it in the known-indirect-writers list, never to drop it.
- SAFETY DOCUMENTATION IS INDISTINGUISHABLE FROM THE ATTACK IT DESCRIBES, TO A REGEX — so a prose-pattern detector reliably fires on the rule TEXT written to forbid that very thing, and "fixing" the hits damages real guidance: `agent-context-integrity` reported 17 authority-override / cross-skill-shadowing patterns across 7 files, and the top hit was Rule 0.b's *"you have BECOME the system"* — our own warning against the runner puppeting agents — with the rest being a diagnostic table row and a `never touch ~/agents/jvs-*` safety blacklist. All owner-authored, git-tracked, single-commit provenance. Two checks settle this class in one call: `git log` the cited path (external provenance or ours?) and READ the line (does it forbid the pattern or perform it?). Note the count inflates too — `.claude/rules/SCENARIOS_TESTS_RULES.md` is a tracked SYMLINK (git mode `120000`) to the `tests/` copy, so the same text is counted under both paths; `ls -la` before filing a duplication finding. **SETTLED 2026-08-16 at 18/8 — all FIVE named hits read and verified false, so stop re-litigating this advisory each fire:** `aimaestro-kanban-multiagent.md:155` (CRITICAL) is the clause *forbidding* concealment — *"it does **not** silently perform USER- or MANAGER-gated transitions"*, matched on the word `silently`, and its path is a **symlink** into `rules/aimaestro/` so it is one text counted twice; `aimaestro-trdd-approval.md:162` is the SECTION HEADING *"Tier 0 — Agent-independent — DEFAULT, no approval"* and `:237` a row of the AUTHORITY-LADDER table *"MEMBER · ARCHITECT · INTEGRATOR (no approval authority)"* — a taxonomy of who lacks authority, read as a claim to it; `scenario-runner.md:54` is the rule forbidding the runner from puppeting agents (*"you have BECOME the system"*) and `:101` a DIAGNOSTIC TABLE row. **Every one matched because it DESCRIBES the pattern it is accused of performing** — which is the whole lesson, and why the advisory is informational by design (*"no fixer is recommended here"*). **THE COUNT IS NOT FROZEN AND A DELTA IS NOT A NEW FINDING — do not re-litigate on one.** It read 18/8 then **21/8** hours later, and the only file the agent loads that changed in between was **THIS FILE**, which gained six lessons and now carries `silently` ×38 and `supersede` ×7 — the exact vocabulary of the `concealment-directive` and `authority-override` classes. So writing the lesson about the detector inflates the detector: **the observer modifies the observed, for the fourth time in one night.** Attribute a delta by asking *which loaded file changed since the last count* (one `git log --since --name-only` over `.claude/rules`, `.claude/agents`, `rules/aimaestro`) — and note this is ATTRIBUTION, not proof: the advisory names only five hits and hides the rest behind *"…and 16 more"*, so the three new ones were never displayed.
- **A CHECKLIST BUILT BY ENUMERATING *POWERS* WILL SYSTEMATICALLY MISS *PROHIBITIONS*, and the maintenance rule that keeps it honest is exactly what blinds it.** AMAMA's governance self-audit gates every governed act behind 12 questions, each CITING a rule, kept current by *"new power ⇒ its question in the SAME change"* — genuinely self-maintaining, and citation-clean at 20/20 with 0 rotted anchors. Yet a MANAGER authoring a Tier-0 self-mandated card and **implementing it itself** answers YES to all twelve, against `GOV-R13.2` (verdict **Explicit**, *"Does NOT write code"*) and the persona's own *"NO IMPLEMENTATION — THE ONE ABSOLUTE BOUNDARY … not 'just this once because it is small or urgent'"*. It slipped because **a standing prohibition that PREDATES the checklist fires no new-power event**, so nothing ever triggered — `R13` appeared in **0** of the 12 and in **0** of all 71 skill files, positive-controlled with the 18 rule ids that ARE cited AND with a CONCEPT needle (*"never write code"*, *"no implementation"*, *"develop software"*) so the zero was verified-absent rather than merely differently-worded. **Adding the two missing questions closes the instances and leaves the CLASS open**: the fix is the maintenance rule gaining "new or newly-discovered PROHIBITION ⇒ its question in the same change", plus one sweep of the prohibitions that predate the checklist. Generalize: any gate assembled from "what may I do?" needs a second pass asking "what may I never do?" — the two lists are not complements, and only the first one grows by itself.
- READ THE FLAG'S OWN HELP before believing it filtered anything: `--min-severity error` sets the **exit code** only — the run still PRINTED all 426 lines (19 ERROR / 229 WARN / 176 INFO), so the first screen of a severity-"filtered" run was pure INFO and reading it as the error set would have inflated 19 into 426. A flag named after a severity is not necessarily an output filter; grep `^ERROR` yourself.

- **A NON-VACUITY GUARD WRITTEN OVER *FINDINGS* FIRES ON SUCCESS — the exact mirror of the vacuous-gate defect, and it silently makes an acceptance criterion UNSATISFIABLE.** A sweep guarded itself with `if [ ! -s "$RESULTS" ]; then echo "SWEPT NOTHING … check the path"; exit 2; fi`, reasoning correctly that a typo'd path must not read as "no dead claims". But that fires when zero refs were **FOUND**, so a fully cleaned corpus is indistinguishable from a broken one: clearing the last stale ref moved the exit **1 → 2, never to 0**, and its governing card's box (*"exits 0 after the mechanism lands"*) could not be satisfied by any amount of correct work. The guard must key on **INPUT CONSUMED** (cards scanned), never on output produced — scanning N>0 and finding nothing IS the clean case. Same family as *"a condition written only over the BAD items is vacuous on an empty set"*, pointed the other way: **that one passes when it should fail; this one fails when it should pass**, and the second is harder to spot because it looks like rigour. Fixing it then hit a second bug shellcheck had to name (**SC2030/SC2031**): the counter was incremented inside a loop whose body is a **pipeline**, hence a SUBSHELL, so every increment was discarded at `done` and the count read 0 regardless — reproducing the very false "SWEPT NOTHING" the counter was added to prevent. Count with `find … | wc -l` BEFORE the loop (never `ls "$DIR"/*.md`: an unmatched glob passes through literally and `ls` lists the CWD, returning a plausible non-zero count for the wrong directory). Control a gate in **all three** directions — clean input → 0, broken input → 2, seeded bad input → 1 — because two of the three passing is what this defect looks like.

- **THE FIRST FALSE POSITIVE OF A NEW DETECTOR IS THE PROSE YOU WRITE DOCUMENTING IT — twice in one session, in two different files.** After fixing a blocking-prose sweep I wrote the fix up on its own governing card, quoting the example phrases verbatim (*"blocked on <owner/repo#N>"*, *"instead of waiting on <owner/repo#N>"*) — and the next run reported **that card** as holding two live waits. Fixed it, moved to a second card, annotated a cleared gate with *"verified: #35 …"*, and the bare number in **my own explanation** re-tripped it. This is USE-vs-MENTION with a specific trigger: the moment you explain a detector, you necessarily write the shape it hunts, in the corpus it scans. The rule that already existed (*"a keyword-keyed detector cannot distinguish USE from MENTION"*) describes the phenomenon; this is the operational corollary — **when documenting a detector inside its own scan set, DESCRIBE the shape, never paste it** (name the issue by title, say "the coordination issue", strike it, or blockquote it), and re-run the detector after writing the note, because the note is the most likely new hit.

- **EXISTENCE IS NOT EVIDENCE — THE SUBJECT MUST MATCH.** Resolving a bare `#35`/`#37` to a repo, the obvious candidate had **both** numbers live, which reads as confirmation and is not: their titles were *"Detect and unblock a stalled agent"* and *"[FLEET R41] Adopt APPROVAL/MANDATE"*, while the citing text said *"#37 **decoupling** (gated on MANAGER #35)"*. Hypothesis refuted on content. The right answer came from a **full URL** already sitting in the same card 44 lines away, and its title (*"Coordinate: MANAGER ↔ ai-maestro"*) matched the claim. In any numbering-per-repo namespace (GitHub issues, PRs, ticket ids) a number resolves nearly everywhere, so **"it exists there" is worth nothing; only "its subject is what the citation claims" is evidence.** Corollary from the same pass: when your hand grep and the tool disagree, run the TOOL'S OWN pipeline to locate the hit — my `[^0-9a-zA-Z/]#35` returned **0** on a file where `grep 'MANAGER #35'` returned **1** (ordinary space, no explanation found), and replicating the sweep's extraction found the site immediately.

- **`git add` FAILS THE *WHOLE* PATHSPEC ON ONE MISSING PATH, AND `2>/dev/null` TURNS THAT INTO A RENAME-ONLY COMMIT.** After a `git mv` I ran `git add -- <new-path> <old-path> 2>/dev/null`; the old path no longer existed, so the add staged **nothing**, and because `git mv` had already staged the rename, the commit succeeded looking normal — `1 file changed, 0 insertions(+), 0 deletions(-)` — under a message describing five content edits. HEAD then held a card in `design/archived/` still reading `column: todo`, a ZONE-MISMATCH in the committed tree, while the `trdd:doctor` run that reported `ZONE-MISMATCH 0` was reading the **working** tree, which was correct the whole time. Three guards, each cheap: never suppress stderr on a command you depend on and **gate on `$?`**; after any `git mv`, check `git diff --cached --numstat` shows non-zero insertions before committing; and when the claim is about a COMMIT, verify with `git show HEAD:<path>`, never the tree. *A verified working tree is not a verified commit* — already in this file, and it recurred through a door that rule did not name.

- **A DETECTOR KEYED ON A STRUCTURED FIELD IS BLIND TO EVERY RECORD THAT NEVER POPULATES THAT FIELD — and the records that skip it are systematically the oldest and largest ones, so the blind spot is worst exactly where the stakes are highest.** `trdd:extrefs` reads the `external-refs:` FRONTMATTER field and reported a confident **"45 open cards, 70 refs, 14 repos, 0 unresolved"**. Measured across the open zones: **168 cards, 111 with the field, 57 without — and 27 of those 57 cite an issue in body prose.** One of the 27 was `TRDD-903B7A20`, the board's largest campaign card, whose sole blocker `ai-maestro#132` sat in prose, **CLOSED for 8 days**, still gating a descoped gate that its own re-entry condition had already reversed. The tool ran clean over it every time and could not have done otherwise. **This is the mirror of the verb-rename blind spot** (a needle keyed on a NAME goes blind at a rename): here the needle is keyed on a SCHEMA, and goes blind at every record that predates or ignores it — which no rename ever announces either. Two things make it invisible: the number it reports is *true* of the population it scanned, and a field-keyed scan looks more rigorous than a text scan, so nobody asks what the field's coverage is. **The fix is not to scan prose** — a bare `#35` matches ordinary text and filing off it manufactures false positives (already hit on this board) — **it is to COUNT the unscanned population and PRINT it**, so a clean run says "clean of what I can see" rather than "clean". Before trusting any field-keyed report, measure `records WITHOUT the field` as a first-class number; it is the floor on what the tool cannot answer.
- **A DESCOPE THAT NAMES ITS OWN RE-ENTRY CONDITION IS A SELF-CANCELLING PARK THAT STILL NEEDS A WATCHER — and it reads as more responsible than a plain park, which is why nobody watches it.** G4 was descoped with a correct, evidenced measurement (*"zero callers, the wiring is UNBUILT, so this gate cannot honestly gate"*) and it explicitly wrote its own reversal: *"re-enters as its own card when a visualizer actually wires the CLI."* The visualizer wired it, shipped it in two releases with its own test suite, recorded itself as *"the FIRST caller"* — and the gate stayed descoped, because a condition stated in prose fires for nobody. Fifth instance of the stale-blocker class already recorded here at 4-in-5; the new wrinkle is that **naming the reversal condition creates a false sense that the reversal is handled.** Same fix as the parent lesson, sharpened: write the re-entry condition as a RUNNABLE COMMAND in the box (`gh issue view 132 --json state`, `grep -rl PANEL_CLI <plugin>`), never as a sentence — a sentence has a silent timestamp, a command re-answers itself.

## Lenient readers and the writes built on them

- A LENIENT READER'S READ SIDE IS VACUOUS AND ITS WRITE SIDE IS DESTRUCTIVE — count the WRITES, not just the reads: my card was filed for verifications reading *unreadable* as *absent*, and **21 of 21** `saveJsonSafe` calls turned out to be read-modify-write fed by that same reader, 4 of them on the user's own `~/.claude/settings.json`, each REPLACING the file with a minimal object built from `{}`. The worst site logged `writing safeguard` while truncating it — an ops line that reads like a REPAIR.
- GUARD THE WRITE PRIMITIVE, NOT THE CALL SITES, WHEN COMPENSATIONS CALL IT DIRECTLY: a per-call-site read guard cannot see an undo that writes a SNAPSHOT (`c.prior`, `structuredClone`d from the same blind read — so on a corrupt file the ROLLBACK restores `{}` and destroys what it exists to protect). The primitive is the only choke point both the forward and undo paths traverse, and it is the only fix that covers a FUTURE call site.
- THE PROJECT'S OWN RATIFIED ANSWER BEATS YOUR REASONING *AND* THE ADVISOR'S — grep for a sibling that already solved it BEFORE designing: `lib/claude-settings-enforcer.ts` had ruled exactly this ("Corrupt JSON — NEVER overwrite … would destroy whatever the user actually has") with a test pinning it; the ruling had simply never been extended to the family. It also caught what neither of us had: `JSON.parse` SUCCEEDS for `[]`/`null`/`42`/`"str"`, so a `data: Record<string, unknown>` return type is a LIE and the caller writes the result of mutating an array.
- AN HONEST BRANCH THAT ALREADY EXISTS AND IS UNREACHABLE IS THE TELL: three gates in one file carried the right message ("Could not check…", "Could not read settings for verification") in a `catch` that could never fire, because the lenient reader does not throw. The right answer had been written down three times and disarmed three times by the same reader — so look for the dead `catch` before writing a new branch.
- THE SAME FUNCTION IS OFTEN BOTH AN OPERATION AND A COMPENSATION, AND A VERDICT CORRECT FOR ONE IS CATASTROPHIC FOR THE OTHER — ask WHO CALLS IT before wiring a check to fail: I made `ChangePlugin`'s G11 fail on a genuine mismatch, and `ChangeMarketplace`'s R51 rollback *reinstalls plugins through it*, so a restored system was reported as `THE SYSTEM IS IN AN INVALID STATE … manual repair is required`. One hour after arguing PG01 must not do exactly this. The axis was per-CALLER, not per-action, and no amount of reading the gate would have shown it — the rollback TEST did.
- WHEN A CHANGE REDS N TESTS, SPLIT THEM BEFORE FIXING ANY: 13 of my 15 were fixtures encoding the bug (mocks that never persist the write, asserting an install "succeeded" with the plugin absent) and **2 were the design telling me no**. Fixing the 13 first would have buried the 2 under a pile of green.
- AN INVARIANT MAY ABORT ON A POSITIVE VIOLATION AND NEVER ON AN UNKNOWN — and check whether the gate is a "mere WARN" before believing it: mine flipped `result.success`, a later gate turned that into a REGISTRY flag, and the wake route refuses to start an agent carrying it. So a corrupt settings file made a CORRECT install report failure and brick the agent. "It only warns" was three hops from a bricked agent.

## Verifying a fix

- **TWO MEASUREMENTS TAKEN IN THE SAME WRONG ENVIRONMENT AGREE WITH EACH OTHER AND PROVE NOTHING — and the agreement is what makes you stop.** Three tests failed; I separated mine from pre-existing by reverting my change and re-running at HEAD (correct), then reproduced from a SHELL against a `mktemp` fixture instead of trusting the assertion (correct), and filed a card asserting a broken CLI stderr contract. Both arms ran on **Node v26.5.0** against a `package.json` whose `engines` caps at **`<26`**, in a repo whose CLAUDE.md opens by calling Node 22 *"a hard ABI constraint, not a preference"* and prints the exact prefix. Re-run through `bash scripts/with-node.sh`: the contract holds, and the file goes **3 failed → 1 failed** (the cluster 3/117 → 1/119). **Two of the three "pre-existing failures" were manufactured by my own shell**, and the card I filed on them named a defect that does not exist. The tell was in output I had already printed and skimmed — `node -v`. **The structural gap: yarn enforces `engines` before a SCRIPT, so `yarn test` is protected, while `npx vitest run <file>` — what anyone reaches for to run ONE file — bypasses it entirely and fails in a way that reads as a product bug.** Run the pinned toolchain explicitly whenever the result will be written down; rigour inside a wrong harness is indistinguishable from rigour. (TRDD-W636KQBN, which is the retitled corpse of that card.)
- RUN YOUR OWN GATE ON YOUR OWN ARTIFACT: flipping a card to a terminal column is TWO edits — the column AND the `git mv` — and I did the first, committed, and shipped a ZONE-MISMATCH that the very linter this card delivered then flagged. A terminal column left in the OPEN zone makes the open count a lie, and it is exactly the half a human forgets.
- A ticked acceptance box recording a decision since REVERSED is worse than an open one — the next reader takes it as current: mine said the pillar CLIs are "repo-local, and here is why" hours after the USER ordered them installed. Strike it through with the reversal's CAUSE, and name the half that SURVIVES (the Node-22 objection was real; it is now handled, not avoided).
- The positive control that proves a subprocess READ your injected input is also what finds the bug: mine proved the fake `$HOME` was live and thereby exposed that `process.cwd()` is a kernel realpath while a recorded path is a typed string — so a lexical `path.resolve` compare made an agent in its OWN workdir report "not an agent". No in-process test could reach it (the constant is fixed at module load), and no zero-writes assertion is non-vacuous without it.
- Diagnose by dumping the actual ops/trace, not by reasoning about what the code should have done — the trace named the real cause in one run, twice, after reasoning had blamed the wrong thing.
- A verified WORKING TREE is not a verified COMMIT: every gate I ran (`validate`, `pillars:lint`, the doctor) reads the tree, all three passed, and HEAD meanwhile held a `column: dev` card inside `archived/` — the exact mismatch the doctor exists to catch. When the verdict matters, run the gate against what you actually committed (`git stash -u`, a temp clone, or `git show HEAD:<path>`).
- A sha written INTO the commit that carries it is correct only until the next `--amend`: I recorded the pre-amend sha in `implementation-commits:`, amended for an unrelated reason, and the list then named a commit that does not exist — and nothing checks it. Record a commit's own sha in a FOLLOW-UP commit, never inside itself.
- An acceptance box naming ANOTHER card as its destination is voided when that card goes terminal first: mine said "state the number in CTEQX0ZA's budget table" and CTEQX0ZA had reached `complete` hours earlier, where rule 12 freezes the body — name a destination you still own.

- An acceptance box can name the wrong OWNER, not merely an unmet state: mine sent a `~/.aimaestro/` inventory row to the janitor's footprint rule, which contains ZERO mentions of that path (it documents what the JANITOR creates) — and the precedent it told me to copy, `kanban-index`, was itself undocumented in the real owner. Check the box's named document AND its cited precedent before writing to either. Three of that card's four boxes had a wrong premise.
- A cross-boundary violation has TWO ends, and the fix belongs at the end with fewer edits — COUNT them before choosing: my plan promoted a page to clear 2 findings, but resolving its 11 outbound links first showed 9 pointed the forbidden way, so the promotion would have ADDED 9 to clear 2, and stopping the cascade meant migrating all 111 pages. Two consecutive plan revisions picked the wrong end because neither counted.
- `git checkout -- <file>` CANNOT TELL YOUR FIX FROM YOUR SABOTAGE: reverting a neuter discarded the still-UNCOMMITTED fix underneath it, silently, and the next run's green was green about the ORIGINAL code. **Commit the work BEFORE neutering it** (I had done exactly that for the previous card and skipped it for this one), or revert the neuter with a targeted edit. The complement of the held-lock lesson above: there the safety net is unavailable, here it is available and eats the thing you were protecting.
- NAME EVERY FAILING FILE INDIVIDUALLY BEFORE CALLING ANY OF THEM A KNOWN FLAKE — a label attaches to the SET and hides whatever else is in it: three files failed under full-suite load and all three were being carried as "pillar-graph-cli timeouts". Two were genuine 5s timeouts; the third was a real concurrency bug, and its assertion (`expected 420 to be 292`) was not the count it resembled but **octal file modes, 0o644 vs 0o444** — the defect caught in the act. "Passes in isolation" is the SIGNATURE of a concurrency defect, not evidence that there is none.
- THE CHEAP DISCRIMINATOR IS THE FAILURE **MODE**, NOT THE FILE SET — read it BEFORE re-running anything: a timeout says "did not finish", an assertion says "finished and was WRONG", and only the second can be a regression. Two full runs minutes apart gave 3 red files each with only ONE in common (4 distinct files, 1 overlap) — an unstable set is contention's signature, since a real regression fails the SAME test every time. All 5 failures across both runs read `Test timed out in 5000ms`, ZERO assertions, and every affected file spawned a subprocess or drove a full pipeline harness. Two `sed` calls settled it, beating the per-file isolation re-runs I had already spent on the previous set. The trap in the other direction: `grep -c FAIL` on such a log counts the word FAILED inside the negative-path tests' own expected OUTPUT — mine matched a dozen lines of deliberately-injected failures before reaching the summary. Parse vitest's `Failed Tests` block, never a substring.
- WHEN TWO RULES CONTRADICT, CHECK WHICH ONE IS STILL **SHIPPED** BEFORE RULING ON THE DISAGREEMENT — a superseded predecessor that nobody deleted reads exactly like a peer authority, and both load into every session at once: a peer Claude filed a careful 4-question governance issue over "the archival protocol contradicts the terminal-freeze", and the archival protocol it cited lives in an ORPHAN (`trdd-approval-tiers.md`, mode 644, mtime 07-22, **no** janitor header) whose successor is this repo's DEP overlay, while the freeze lives in the canonical file (mode 600, mtime 07-31, header present) that already answered all four questions verbatim. The provenance was three cheap facts — header, mode, mtime — cross-checked against the shipping component's own manifest of what it ships. Rule the PROVENANCE first; the "conflict" often evaporates. **⚠ REFUTED (2026-08-20) — the "orphan" classification above was itself wrong, from the same failure this whole file exists to catalogue: a signature was treated as diagnostic without ever measuring its base rate.** Census of `~/.claude/rules/`: 41 files, only 7 carry the janitor header, and mode splits 9×600 / 27×644 / 5×664 — so **32 of 41 (78%)** share the "644-or-664 + no header" signature this lesson called a mark of orphanhood. Live counter-examples sharing that exact signature: `manager-approval-defaults.md` (644, headerless, mtime **2026-08-20**, content read first-hand the same day), `decide-on-facts.md`, `never_use_sed.md`, `how-to-fix-issues-of-other-projects.md` — and the mtime leaks the other way too, since `janitor-heartbeat-protocol.md` is 600 WITH no header. Re-measured, `trdd-approval-tiers.md` itself now carries mtime **Aug 8** (not 07-22, i.e. edited AFTER this lesson was written) — it is not dead, it is a live, user-scope rule that still teaches the `approval-tier: N` field its own project retired on 2026-07-10 (`rules/aimaestro/aimaestro-trdd-approval.md:286`, "`min-approval-requirement:` supersedes `approval-tier: N`"). That makes the original finding WORSE, not resolved: the file needs a CORRECTION, not a dismissal as orphaned. **The transferable rule: a signature only discriminates if you have measured how common it is in the population, and then actively hunted for a counter-example that shares it and is provably live** — a specific, well-formed, confident-sounding claim (three cheap facts, cross-checked!) is exactly what makes a wrong classification credible to the next reader, including the one who wrote it. **The method that actually settles "which version is current" for a governed field: the newest artifact still WRITING that field beats any rule text as evidence** — `grep -l "^<field>:" design/**/*.md` sorted by `created:` (in this repo: 79 cards still carry `approval-tier`, newest 2026-07-29; 334 carry `min-approval-requirement`, newest today) — because rule prose can rot in place while the corpus it governs keeps moving. **AND THE AMENDMENT ABOVE COMMITTED ITS OWN DEFECT ON ITS FIRST DRAFT: it carried the corrected CONCLUSION and the base-rate number but NO command to re-derive them** — a lesson saying "count the population" that the next reader cannot recount is another measurement recorded as a property, caught by the same peer who refuted the original. So a durable note carrying a measured fact MUST carry its DATE **and** the command that reproduces it; here that is `find ~/.claude/rules -maxdepth 1 -name '*.md' -type f | wc -l`, `grep -l 'ai-maestro-janitor rule' ~/.claude/rules/*.md | wc -l`, and `find ~/.claude/rules -maxdepth 1 -name '*.md' -type f -exec stat -c '%a' {} \; | sort | uniq -c` (2026-08-20: 41 · 7 · 9×600/27×644/5×664). A measurement with neither a date nor a repro reads as a property, and that is the whole failure — the stale mtime in the original claim WAS its own disproof, sitting in the same sentence, unread for weeks, because a recorded fact does not invite re-checking the way an open question does.
- VERIFY AN ISSUE NUMBER AGAINST ITS REPO BEFORE CITING IT: my own handoff listed `#49` as open work (it is CLOSED) and `#106` as this repo's (it is the JANITOR's) — two repos' numbering conflated in a list I then read back as fact. `gh issue view N --repo <owner>/<repo>` is one call and it is the difference between a work item and a phantom.
- Ask who the AUDIENCE of a reference is before valuing it: I refused to remove a link because it was "a good link", when a shared-store page naming a machine-private page cannot resolve for any other reader BY CONSTRUCTION — it was already dangling for everyone but me, so it had nothing to protect and cost self-containedness.
- A VERIFICATION WHOSE RESULT YOU CANNOT GATE ON IS NOT A VERIFICATION — never put the check and the irreversible act in the SAME command block: I ran `test -f <flag> && echo PRESENT || echo absent` in the same block as the `git commit` that asserted the flag was absent, so the commit sealed the claim before I could read the output — which said **PRESENT**. I did check. I just could not act on it, which is indistinguishable from not checking, except that it *feels* rigorous. Worse than skipping the check: the transcript shows diligence next to a false claim. Put the probe in its own turn and branch on it, or write the claim only after the probe's output is in front of you.
- INFERRING A SUBSYSTEM'S **RUN** STATE FROM THE CARD THAT BUILT IT IS A CATEGORY ERROR: a card records what its author BUILT and freezes at the moment they wrote it, while ACTIVATION is a separate act by someone else that no card observes — mine said "WORKING but INERT … nothing runs against the real credentials", and the USER had armed the flag six days earlier, so the "gated infra" I was describing was a live credential writer beating every 60 s. Check the runtime gate itself (the flag AND the thing it produces — here the tick's own stamp, proving it beats rather than merely being enabled).
- TWO SIBLING CARDS THAT DISAGREE ARE A FREE DEFECT DETECTOR, and the contradiction is cheaper to spot than either error alone: one card's acceptance box said a dependency had "landed and wired" while that dependency's own card said `column: todo` over NINE `implementation-commits`. Neither is suspicious read by itself — `todo` looks like backlog, "landed" looks like progress — and together they cannot both be true. Cross-read the cards that cite each other before believing either.

## Concurrent writers over shared derived state

- A carve-out list naming only the fault you have MET destroys healthy state on the next one: `downgrade` was carved out of the self-heal and `busy` was not, so a second process's lock timeout took the generic "delete and rebuild" branch. And "is this healable?" was being decided in TWO places, neither of which knew about the new code — make it ONE set.
- A `catch` that re-throws as `new Error(\`…: ${err.message}\`)` ERASES `err.code`, so an outer handler switching on that code cannot see it — and two conditions with OPPOSITE repairs silently collapse into one. Translate at the throw site, and guard the CONDITION rather than the reporter.
- `unlink` SUCCEEDS against a file another process still holds open (POSIX), so "delete it and rebuild" as a repair destroys a concurrent writer's work IN SILENCE — it goes on writing into an unlinked inode and reports success — while the heal ledger fills with "damage" that was only contention.
- A deliberate decision can rest on a false premise about a setting the SAME module enables: "holding the write lock across the read would block every other reader" is true for rollback-journal and FALSE in WAL, which `applyPragmas` turns on two files away. Check the mode before accepting the rationale that cites it.
- `busy_timeout` does NOT retry a snapshot conflict — a deferred `BEGIN` that reads before it writes can fail `SQLITE_BUSY_SNAPSHOT` unretried — so such a transaction is safe only by the ACCIDENT of its statement order, and the first `SELECT` anyone adds inside it breaks that silently. `BEGIN IMMEDIATE` puts the wait where the timeout applies.
- A REPAIR THAT MUST UNPROTECT A RESOURCE TO REPAIR IT OPENS THE VERY WINDOW IT EXISTS TO CLOSE — the moment it can run concurrently with ITSELF: the invariants watchdog restores read-only (0444) rule files, and `writeProtected` must `chmod 0o644` first (a `mode` option applies only at CREATE). `setInterval` with no re-entrancy guard let a second sweep read a PARTIALLY-written rule, conclude "bytes differ", and chmod it writable — a protected file was transiently writable BECAUSE the guardian was guarding it. Ask of any self-healing loop: can two runs overlap, and does the repair pass through a weaker state than the one it enforces?
- A `.finally` THAT NULLS A **SHARED** HANDLE IS CLEARED BY WHICHEVER RUN FINISHES FIRST, NOT BY ITS OWNER: `void inFlightSweep.finally(() => { inFlightSweep = null })` meant sweep A finishing wiped sweep **B**'s handle, so `stop()` returned `Promise.resolve()` while B was still writing — reintroducing, in the overlap case, the exact bug the `inFlightSweep` handle had been added to fix. Clear by identity (`if (shared === mine)`), and treat "we already fixed that" as scoped to the concurrency the fix assumed.
- A handle leaked on an error path is bounded by what the CALLER does next: when the caller DEGRADES and keeps running (falls back to the slow path), the leak lasts the whole process rather than until exit.
- **A PERSISTENT RESOURCE WHOSE SHAPE IS DERIVED FROM THE CALLER'S AMBIENT CONTEXT OSCILLATES BY CONSTRUCTION — and it is WORSE than two payloads disagreeing, because making the payloads agree cannot fix it.** The branch-protection baseline on 9 public repos took `pull_request` from `require_pull_request_for()` → `in_ai_maestro_agent_env()`, which reads `AIMAESTRO_AGENT`/`AID_AUTH` **from the calling process**, and `required_status_checks` from `detect_required_status_checks()`, which reads `.github/workflows` **from the caller's CWD**. So the hub applier (inside a harness agent) wrote `pull_request` and the janitor applier (standalone) removed it — **neither buggy on its own terms**, one predicate honestly answering two callers, and the same applier will flip against ITSELF depending on where it is invoked. Measured: 6 repos carried the hub's 01:50 shape, 3 the janitor's; **the split was by WRITER, not by repo.** Two things make it invisible: **each writer's post-condition is true of what it SENT**, and a conformance checker that re-derives the expected payload IN ITS OWN CONTEXT agrees with whichever writer shares that context and flags the other — so the verdict depends on where the CHECK runs too. No single-process test can see it; the divergence exists only ACROSS processes. Ask of any persistent resource: is its shape a property of the RESOURCE, or of the moment someone wrote it? (`TRDD-SX5FPMG0`; the discriminating evidence was a repo that HAD a checkout and a workflow file and still got no checks rule — the two repos with no checkout at all were consistent with the story but could not discriminate it.)

## Measuring at scale

- Measure peak RSS, not just wall time: the wall here was MEMORY and it landed at ~60-70k documents — BELOW the 100k target — so the failure is a heap crash, not a slow run.
- Hoisting a parse OUT of a transaction (to avoid holding the write lock) still has to STREAM — retaining the rows makes peak memory the CORPUS SIZE, and that exact hoist-and-retain shape appeared twice: the linter (4.45 GB crash) then the index builder (2.36 GB at 10⁵).
- A structure that is written, validated and tested but never QUERIED is invisible to the whole suite — my tests proved `records_fts` was POPULATED, never that anything reads it, so it dominated the cold build for a year unnoticed; grep for a consumer (`MATCH`/`bm25`), not for coverage.
- An RSS PLATEAU is a diagnosis, not a plateau: it stops rising exactly when accumulation ends, so flat-during-the-write-phase told me the wall was the pending array and not the writes.
- A fixture built from the SAME assumption as the code validates the assumption, not the behaviour: 10 green tests fed my checker a `.git/HEAD` mtime table, and the real `.git/HEAD` had not moved in a MONTH (a commit rewrites the reflog, not the symbolic ref) — so it reported "fresh" about a 5-hour-stale build. When the question is a fact about the world, one test must read the world.
- A committed fix is not a DEPLOYED fix: `pm2 restart` replays the existing build, so my ledger fix sat in git for 20 min while the server kept writing the buggy value — the corruption I had just repaired came straight back, and I only saw it because I checked the DATA rather than the commit.
- Which files are bundled decides which fixes a restart picks up: `server.mjs` + `lib/*.mjs` are loaded at runtime (live immediately), while `lib/*.ts` goes through `.next` (stale until rebuilt) — so "I restarted it" is true and irrelevant unless you know which half you changed.
- Date the artifact against the commit before trusting a deploy: `.next` mtime 13:59 vs fix 18:47, and `grep -c nextSeq .next/server` = 0, settled it in one command.
- Read the WHY-comments before designing a repair — they name the invariant you are allowed to lean on: verify()'s comment explaining that it ANCHORS on entries[0] "so a rotated file verifies" is the entire reason a lossless split existed, and I had been about to re-sign 703 entries.
- Before accepting a menu of bad options, ask which field the check actually reads: `seq` sits FIRST in canonicalize(), so renumbering re-signs — and that one fact turned "pick your loss" into "split the file, lose nothing".
- "One discontinuity" and "702 duplicate values in one file" are different diagnoses of the same scan — I reported the gap and only found the DUPLICATES by asking separately; a contiguity check cannot see an overlap.
- A dependency's module-level cache defeats streaming outright — gray-matter keys a cache on each file's full text, so a reader retaining NOTHING still accumulated the whole corpus; grep the parser for `cache` before believing a streaming rewrite.
- Peak RSS is not the live set: RSS counts uncollected garbage, so measure RETENTION with `--expose-gc` + `heapUsed`, or a heap-cap sweep — mine dropped 57% while the retained set barely moved.
- A memory correlation has more than one plausible cause: identical frontmatter + 4.4x memory looked exactly like V8 sliced strings, and deep-flattening every string moved it −3%, refuting it — run the candidate fix as a PROBE before editing any source.
- Extrapolation can be wrong in KIND, not degree — a projected "~6.5 GB, 80-90 s" was in fact an OOM CRASH at 4.45 GB; generate the real 10^5 fixture, because "slow" and "dead" are different verdicts.
- When a refactor must preserve output ORDER, say which alternative you rejected for it: evaluating rules inside the stream would have moved every cross-card finding into a trailing block, and that is invisible on a corpus whose cross-card rules all pass.
- Super-linear wall time near the limit is a SYMPTOM of the memory wall (GC pressure), not a second problem to optimize.
- "Do we need an index?" is usually "is the index rebuilt in RAM every run, or persisted?" — grep for the Maps first; this linter already built one, and that in-memory index WAS the 6.5 GB.
- Cost the JOIN, not just the scan: validating references is O(N × refs × lookup), and a lookup that re-readdirs the corpus makes a linear-looking tool quadratic.
- A generated fixture of identical stubs measures filesystem throughput and nothing else — give it the real body size, the real field set, and real cross-references, or the number is theatre.
- An "undocumented" marker from a plugin whose stub AUTO-ROLLS to the newest cached version is VERSION SKEW, not a missing spec: my session's rules were injected at SessionStart from 0.60.1 while the firing dispatcher had rolled to 0.64.1, whose OWN shipped rule documents the marker (3 mentions) and even tests it. I treated a documented marker as unknown for 3 turns and was one command from filing a false issue against a user-owned repo. Diff the newest cached version's shipped rule against the installed copy BEFORE concluding anything is missing — mine was byte-identical to an older version, i.e. stale, not broken.
- Before generalizing over N consumers, verify they share the shape you assume — I checked all three pillars on disk and found three different document models, one of which (PRRD) has no zones and no id in any filename.
- When the repo lacks an instance of the thing you are encoding (no PRRD.md here), find a REAL one elsewhere rather than encoding the grammar from memory.

## All-in-one functions (R50/R51)

- A COMPENSATION FUSED TO ONE ABORT SITE IS INVISIBLE TO EVERY OTHER ONE, and it reads as coverage because it is real, careful code: DeleteTeam's 45-line reverse restore lived inside `if (revertFailures.length)` and so ran ONLY for a per-agent failure, while G04's `return result` reported "registry delete failed" over a team whose every member had already been un-enrolled, demoted, plugin-stripped and hibernated. Code can only roll back the failure it is written for — the runner's value is not the undo but DECIDING WHEN IT RUNS.
- A gate whose `run` is a LOOP is not atomic: register its compensation BEFORE running it, or its own partial work is the one thing nothing reverts.
- WHEN TWO COMPENSATIONS OVERLAP ON ONE FIELD, a test that drives only the path where the outer one runs cannot see the inner one: G04's undo restores the PRE-G03 team snapshot, whose `agentIds` already holds every agent, so it silently also restores membership and the LIFO neuter left that test green. Not a bug — but name the overlap, or the next edit deletes the half no test can miss.
- An `undo` must tolerate `run` having done none, some, or all of its work — reverse only what `run` recorded in ctx.
- Check every precondition (adapters, permissions, reachability) BEFORE the first mutation; ordering prevents states that rollback can only repair.
- The last write in a pipeline still needs a compensation — a registry write after the filesystem work leaves the two disagreeing forever.
- Swallowing a per-item failure into `console.warn` and continuing converts one bad item into an invalid system.
- Order a compensation by the CONSTRAINT graph, not by blind reversal: if the do-path removed X first to satisfy a gate, the undo must restore X first to satisfy that gate's mirror.
- A snapshot nothing reads is not a safeguard — if a gate announces an archive, point at the artifact or stop announcing it.
- "Nothing was deleted" is false the moment ANY earlier sub-step landed; a preserved parent row with its children stripped is a husk, not consistency.
- A COMPENSATION THAT RETURNS EARLY DOES NOT THROW, so a runner's `<gate>: reverted` line proves only that the undo did not FAIL — an empty one earns it too. My neuter (`if (true) return`) left all 10 tests green, and the second assertion was vacuous in a different way: `not.toContain(result.agentId)` compared against NULL, because a clean rollback is exactly the case that nulls agentId, and nothing contains null. Assert on the STORE the compensation moves (here the `updateTeam` call sequence: the id in on the join, out on the undo), never on the runner's log line or on a field the failure path has just cleared.
- AN `undo` AFTER THE LAST GATE THAT CAN ABORT IS UNREACHABLE, and unreachable compensation is worse than none because it READS as a guarantee: a compensation runs only when a LATER gate fails, and CreateAgent's G08-G12 are all WARN-and-continue with nothing fallible after them — so ~150 lines of careful undos for the tmux session, the keypair and the SHARED AMP index row could never execute, while the next reader would believe that index row was covered. Put them outside the sequence and write the trigger that would make them reachable ("if any of these is ever made fatal it MUST move in"). Find that boundary by asking which gate can still abort, not by wrapping everything that mutates.
- REVERSE-ORDER UNWINDING ASSUMES THE COMPENSATIONS COMMUTE IN LIFO — when two mutations have a forward order AND a reverse order that is NOT its mirror, they are ONE gate, not two: ChangeTitle Gate 9 requires membership for a team title and REFUSES a standalone title while still a member, so join→title reverses as leave→demote — the same order again, not its mirror. As two gates, LIFO demotes first, Gate 9 refuses, and EVERY rollback reports R51.5 "INVALID STATE" about a fully recoverable system. Read the nested pipeline's constraints BEFORE choosing the gate boundaries; the neuter that proves it is "swap the two halves inside the undo".
- A COMPENSATION CAN BE MASKED BY ANOTHER GATE'S, so its test passes with it DELETED and only the neuter says so: my "G04b restores the orchestratorId" passed with G04b's undo gone, because the title restore in the NEXT undo runs ChangeTitle, whose Gate 13b re-sets that same field. A redundant compensation is not wrong — but it is unpinnable on the happy path, so the test must drive the branch where the masking gate does NOT run (here: make the forward title write FAIL, so `titleChanged` stays false and nothing else can restore the slot).
- THE LAST GATE THAT CAN ABORT HAS A LATENT UNDO BY CONSTRUCTION, so no neuter can red it and calling it covered is a lie: write-ahead registration makes a failing gate's own compensation reachable only if `run` completes its mutation and THEN throws, and G05's single `saveJsonSafe` has nothing after it — so its flag is either set with the write durable or never set with nothing to restore. Neutering it reddened 0 of 4 tests. It stays (the runner requires it, and the partial-work contract makes it correct); what a test CAN pin is that its FAILURE unwinds the gates before it. Name the latency instead of counting it.
- THE BOUNDARY IS PER BRANCH, NOT PER FUNCTION — wrapping a whole pipeline to look thorough manufactures fake guarantees: ChangeMarketplace's `remove` had a four-store window while `add`/`update` had one mutating gate each with nothing abortable after, and `update` has no honest undo at all (you cannot un-pull a marketplace). Wrapping all three would have invented two unreachable undos to buy one real one — and the runner's refuse-to-start check exists precisely to reject the third.
- AFTER FUSING TWO GATES TWICE, THE REFLEX IS TO FUSE, so apply the LIFO test in BOTH directions and expect the opposite answer sometimes: in one pipeline G03+G04 fused (one `marketplace add` restores both registration and cache, so a split unwind would restore the cache *before* the re-add that re-creates it) while G02b+G03 correctly stayed SPLIT (a reinstall needs the marketplace registered, and reverse order runs the re-add first — dependency and unwind agree). Same test, opposite verdicts, one function.
- MEASURE EVERY CANDIDATE'S WINDOW BEFORE PICKING BY SIZE — the op count is not the risk: 5 of 5 remaining sub-100-op pipelines turned out to be ONE mutating gate with nothing abortable after (`ChangeMCP`, `ChangeLSP`, `ChangeHook`, `ChangeMetadata`, `ChangeCLIArgs`), so retrofitting any of them moves the conformance ratchet and buys zero safety. Five `awk`-scoped greps settled it; picking by gate count would have spent a session on the wrong one.
- A MUTATION IS NOT A WINDOW JUST BECAUSE IT IS A MUTATION — "does abortable work follow the write?" is necessary and NOT sufficient, because it finds windows a rule then FORBIDS you to close: 3 of `InstallElement`'s pre-EXE mutations passed that test and failed the second one — `.claude/` is a guaranteed agent invariant (deleting it fights the watchdog that re-creates it), the marketplace registration is SHARED (deregistering breaks every other agent), and the converted plugin dir is protected by R20.31 verdict **Explicit** (*"NEVER DELETES … the user's responsibility"*). Retrofitting by op count would have written a compensation that deletes a user-owned source folder and called it R51 compliance. Ask BOTH: is there abortable work after it, AND is reversing it legal and harmless?
- COPYING A SIBLING MODULE'S RATIONALE CAN SHIP A FALSE PREMISE UNDER A CORRECT DECISION, which is the hardest kind to catch because the code is right and only the WHY is wrong: I justified restoring an expired portfolio token with *"`loadPortfolio` prunes nothing"* — it prunes, and the module's own header says so. The DECISION survived (the two stores prune by different means: one REMOVES rows and persists it, the other only DERIVES a status in memory), but nothing in the tests could have caught the sentence, and the next reader inherits it as fact. When you write "unlike X, this one …", open X AND this one and state the actual difference; a comment is the one artifact no neuter reds.
- A REPAIR THAT FAILS LEAVES THE PRE-CALL STATE, WHICH IS EXACTLY WHAT R51 ASKS FOR — so a post-gate that only ever turns OFF an already-wrong flag is not a window and must not be gated: I recorded `InstallElement`'s two USER-scope writes as "two scopes disagreeing about what is installed" when PG03/PG07 only DISABLE a duplicate that pre-dated the call. Gating them would revert a good install to avoid a duplicate that already existed. Read what the write DOES to the store before classifying it as a mutation that needs an undo.
- A MESSAGE THAT HARDCODES A FACT THE CODE NEVER ESTABLISHED IS AN APOLOGY FOR A MISSING COMPENSATION — and a test asserting it is propped up by the gap: G07b's invalid-state message named `joined team <id>` whether or not the join had succeeded, and the rollback never left the team, so the string stood in for the undo nobody wrote. Once G07 recorded the join and its undo reversed it, the honest message names a team ONLY when one is still occupied, and the assertion had to go. Interpolating a value you did not read back is the tell.
- MAKING A HALF-WRAPPED CASCADE *ABORT* IS THE OBVIOUS FIX AND CAN BE A SECURITY REGRESSION, because the abort strands whatever an EARLIER gate already wrote: ChangeTitle's G10 swallowed a `blockAllTeams` failure and returned success, and "un-wrap it so it aborts" — which my own card had recorded as the fix's shape — skips the later revocation gates, leaving a demoted MANAGER holding AID tokens that EMBED `manager`, with the retry short-circuiting at Gate 6 (`titleUnchanged` ⇒ `success:true`) before revocation is ever reached. Ask what the abort SKIPS and whether a RETRY can still reach it; when it cannot, withhold the VERDICT at the terminal and let the alignment gates run. Abort becomes correct only once the earlier write is itself compensable.
- THE CTX A GATE RUNNER PASSES IS AN UNDO LEDGER, NOT A REIFICATION OF THE FUNCTION'S LOCALS — and mis-sizing it does not merely bloat the edit, it DEFERS the work: my card said "reify ~10 threaded locals", a later measurement inflated that to *117 declarations, ~12-15 carriers*, and on that estimate a whole session declined to start. The landed sibling's ctx has **4 fields, every one something `run` records so `undo` can reverse it**, with the adapters, plans and dirs closed over LEXICALLY — so its content is decided by the undos and there is nothing to reify before them. Read a sibling's ctx before sizing the edit.
- A WINDOW STARTS AT THE FIRST MUTATION WHOSE REVERSAL IS LEGAL AND HARMLESS, and that is not only a safety question — it decides whether the restructure is EXPRESSIBLE AT ALL: opening at ChangeTitle's literal first mutation (a `program` self-heal whose undo would restore the corrupt empty value) would have enclosed two gates that early-return SUCCESS, which `runGateSequence` cannot represent — it gives a gate return-or-throw and no third outcome. The conversion dies mid-edit on a shape the plan never mentioned.
- CONVERTING `return` TO `throw` INSIDE AN EXISTING `try` HANDS YOUR ABORTS TO ITS `catch`: G14's two drift checks sat inside the try that guards its disk read, harmless as returns, and as throws would have been swallowed and re-reported under the generic "verification failed" — losing the specific message. Narrow the try to the I/O it was written for, and keep a sentinel error class so a deliberate abort stays distinguishable from a bug (else every unexpected exception is silently reclassified as a clean refusal).
- A DEFENCE-IN-DEPTH ABORT IS UNPINNABLE BY DESIGN, so its neuter reddening NOTHING is the MEASUREMENT, not a broken test — but take the measurement rather than trusting the comment: G15's R9.13 denial says "Gate 3 should already have rejected this path", and neutering it to a no-op left the full suite at 310/4437/2. What the missing test means is that the conversion is safe only by an equivalence nothing checks — `return result` after setting `result.error` and `throw new GateAbort(msg)` agree ONLY because the loop's catch does `result.error = err.message; return result` on the SAME `result` object. Say which invariant each unpinned conversion rests on; the day the driver builds a fresh result, every unreachable abort changes silently.
- THE GUARD THAT EXISTS *BECAUSE* A FALSE SUCCESS SHIPPED IS THE ONE MOST LIKELY TO HAVE NO TEST — the incident is treated as the evidence, so nobody writes one: ChangeTitle's G22 was promoted from a silent WARN after three separate scenarios found callers claiming success while `governanceTitle` stayed null on disk, and disabling BOTH of its drift aborts leaves the full suite green (310/4437/2, zero red). A retrofit is the moment you learn this, because the neuter is already in your hand — and the gap PRE-DATES the change, so it is a finding to file, not an EHT to hang on the card that found it.
- MOVING AN ASSIGNMENT INTO A CLOSURE DELETES TYPE NARROWING AT EVERY *OTHER* CLOSURE, and the error surfaces far from the edit: hoisting G15's `targetPluginName` above the array and assigning it inside the gate's `run` made TS drop the guard's non-null proof inside a later `() => adapter.install(...)` thunk — 130 lines away, in code the slice never touched. ## Reading a running system

- "No log line" is a claim about YOUR FILTER until proven otherwise — I concluded "the watchdog stopped beating" twice from my own instrument: first an `awk '$2 >= "09:09"'` whose `$2` was the literal `|` (pm2 prefixes each line), then a grep of `pm2-out.log` when the logger is `console.warn` → **stderr** → `pm2-error.log`. The beats were there the whole time.
- Before concluding a periodic task is dead, find the ONE branch that decides whether it logs at all: this watchdog logs only `if (stalled.length || tokenBlocked.length || dead.length)`, so silence and health are the same output.
- `pm2 restart <name>` replays the env pm2 CACHED at first start — it never re-reads `ecosystem.config.js`, so a var ADDED later never reaches the process no matter how often you restart. Use `pm2 restart ecosystem.config.js --update-env`, then verify against the PROCESS (`ps eww -p <pid>`), never against the file you just edited.
- `pm2 save` is a THIRD copy: the live process, the config file, and `~/.pm2/dump.pm2` (what `resurrect` replays after a reboot) drift independently. Ours held a var the config no longer defined and lacked the one it did.
- A gated feature that logs its own gate state (`[detect-only: FLAG not set]`) had been saying so on every beat for six days — detection nobody reads is not detection. Grep the log for the gate string before believing a flag is live.
- A live end-to-end probe of a route-level gate proves NOTHING when an earlier layer refuses first: my curl from the real Tailscale IP got the middleware's 401, never reaching the console check. Isolate the ONE link you actually doubt — a throwaway server printing `req.socket.remoteAddress` settled it in seconds.
- On a dual-stack (`::`) bind, loopback presents ONLY `::ffff:127.0.0.1` — so the "IPv4-compat" branch of a loopback check is the SOLE path the owner takes, not an edge case, and dropping it locks them out at their own keyboard.
- ASK the supervisor where it logs — never assume the default: pm2 was configured to `<project>/logs/pm2-*.log` while I read `~/.pm2/logs/ai-maestro-*.log` (18 days stale), so a healthy boot read as "produced no output at all". `pm2 jlist` → `pm_out_log_path`/`pm_err_log_path` settles it in one call.
- Do NOT append a marker into a log to bracket a restart: the supervisor REOPENS the file so the marker is orphaned, and the write freshens that file's mtime — which is exactly how I certified a dead log as live and read its silence as evidence.
- A restart is not a redeploy of the half you changed: under `tsx server.mjs` in FULL mode, `server.mjs` is transpiled at runtime but API routes still come from the prebuilt `.next`, so a process started AFTER the fix commit was still executing pre-fix route code — check `MAESTRO_MODE`/`NODE_ENV` on the PROCESS before reasoning about which half moved.
- Prove a deploy from the ARTIFACT THAT EXECUTES, not the commit: `grep`ping the compiled chunk for the new expression (`nextSeq(){…e.seq+1…}`) and for ZERO instances of the old shape is the check; `git log` showing the fix is what made this bug survive 20 minutes of believing it fixed.
- BEFORE WAITING ON EVIDENCE FROM A SYSTEM, PROVE THE CODE YOU ARE WAITING ON IS THE CODE THAT IS RUNNING — otherwise every observation is about the OLD code and you will attribute it to some other actor, which leaves the wait with no end condition. I spent three measurement rounds waiting on "a Claude Code boot" to explain hourly registry writes; the writer was MY OWN undeployed lane (`.next` built 07:08:18 and pm2 started 07:08:27, both BEFORE the first fix commit at 07:26:25 — and `services/*.ts` is BUNDLED, so a restart alone never loads it). I had even correctly ruled out "this is a boot" in writing, then never asked *who else it could be*: **ruling out one cause is not identifying one.** The three tells were all non-temporal and each decisive alone — the new FIELD absent from the state file, the state file's rows still carrying the OLD shape, and the cadence still matching the OLD interval.
- SNAPSHOTTING `ps` TO A FILE DOES **NOT** REMOVE THE SELF-MATCH — it only removes the *grep's*. The snapshot is taken BY a shell whose own argv already contains the search string (the whole pipeline is in the `zsh -c` command line), so that shell appears in its own snapshot and the count comes back +1. Mine read `2` for a single live process and I nearly reported two refreshes. The snapshot fixes the narrow case and the general defence is still the bracket trick (`[c]laude plugin marketplace update`) or matching a column the argv cannot contain — and ALWAYS eyeball the matched LINES, not just the count, since a self-match is instantly recognisable as your own command and a count is not.
- ONE MODULE CAN HAVE TWO LIVE COPIES WITH DIFFERENT DEPLOY MECHANICS, and verifying the wrong one reads as proof: `services/auto-update-service.ts` is BUNDLED into `.next` for the API routes, and ALSO imported by `server.mjs` as `await import('./services/auto-update-service.ts')` — the TypeScript SOURCE, transpiled at runtime — for the scheduler. So the scheduler half goes live on `pm2 restart` ALONE and the route half needs a build, and my `.next` grep proved only the half that was not running the lane. **Ask WHO LOADS the code you changed before choosing what to grep.** Two zeros were the tell and I nearly read past them: a function NAME (minified away) and a pre-existing control string that lives only on the scheduler path, hence is never in `.next` at all. For a runtime-imported module the honest proof is RUNTIME BEHAVIOUR — here, `ps` showing one argless `claude plugin marketplace update` at exactly boot+settle, which proved the catch-up fired AND that the new single-call shape replaced the per-name loop.
- A BARE `setInterval` FIRES FIRST AT boot+INTERVAL, so a process restarted more often than its interval NEVER runs that chore — and RAISING a cadence multiplies the starvation window (1 h → 3 h tripled mine, three hours after I had "fixed" the lane). Compute the first fire from a PERSISTED last-run stamp, not from process uptime; persistence is also what makes it safe under a restart LOOP, since the first catch-up stamps the field and every reboot inside the interval then computes "not overdue". Two fail-safe directions worth pinning explicitly: an unparseable stamp must count as never-run (failing the other way starves the chore forever on one bad write), and a FUTURE stamp must count as fresh (a backwards clock must not cause a storm).
- AN ASYNC EFFECT'S ABSENCE IS NOT EVIDENCE UNTIL YOU HAVE WAITED LONGER THAN THE EFFECT TAKES: my 5-minute waiter reported "the catch-up wrote nothing", and the catch-up had fired on time — its refresh was still in flight (900 s timeout, and the previous sweep took minutes), and the state file is written only on completion. "No output yet" and "it never ran" are the same observation; separate them by looking for the WORK IN PROGRESS (a `ps` snapshot, an open handle, a partial artifact), not by waiting a bit more.
- A NUMERIC CONSTANT IS THE WRONG NEEDLE FOR "IS MY FIX IN THE BUNDLE?" — a bundler keeps `3 * 60 * 60 * 1000` as the EXPRESSION, so the new `10800000` AND the old `3600000` both matched **0** files and that zero was uninformative in both directions (it reads as "the old value is gone", which is what you want to hear). Build a NUL from a NUMERIC literal (`String.fromCharCode(0)`, `Buffer.from([0])`) and VERIFY BY BYTE COUNT — it is invisible in every terminal and editor that would otherwise show it to you. Guard: `tests/governance/no-nul-bytes-in-tracked-text.test.ts` (whose own first draft planted three, and was caught by itself).
- A COMMAND ON PATH WITH NO ARG PARSING HANGS FOREVER ON THE FIRST THING ANYONE DOES TO IT: a statusline wrapper deliberately has no options (every argument is the inner command) and reads stdin unconditionally, which is correct under Claude Code and a trap on PATH — `--help` blocked for **8 minutes** with no output. Its 352-line test file covered byte-identical relay, exit codes, cancellation and temp-file leaks but never "invoked without piped stdin", because every test necessarily supplies input; the bug lived in the one shape the harness could not produce. Guard with `[ -t 0 ]` (false under any pipe, so the production path is untouched), and prove the guard on a REAL pty — `spawnSync` always hands the child a pipe, so without one the branch is pinned by nothing.
- A citation pointing at a CONST TABLE is worth LESS than no citation: R19.10 cited one line of `TITLE_PLUGIN_MAP`, and a test written against a table stays green after every guard that READS the table is deleted — so the row advertises a pin it never had. Cite the site that ACTS on the data, never the data.
- A rot-proof gate qualifier does NOT make its line range trustworthy: the check verifies the LABEL exists in that pipeline and never that the range still contains it, so R20.5's ranges sat ~74 lines adrift under a passing check. Re-measure the range whenever you touch a qualified row.
- A rule marked ENFORCED can have a guard implementing a SUPERSEDED version of its text, and both instruments are blind to it: the ratchet sees a citation naming real working code, and a test written against that code PASSES and thereby certifies the divergence. Read the rule TEXT against the guard before pinning — R39.5/R39.7 were two easy ratchet points that would have laundered a 2026-07-22 refinement out of existence.
- A CONTRADICTED row with no guard is not automatically a stale citation — read the RULE TEXT before "fixing" it: R9.13 says REJECT while the code QUARANTINES, so the row was correct and the citation was the lie waiting to be written.
- COUNT THE CLAUSES, then count the cited SITES: a rule with two clauses is usually enforced at two places and cited at one — 3 for 3 in two sessions (R32.2's mint half, R37.4's DELETE twin, R37.2's suspension). The uncited site is invisible to every instrument, because the citation it lacks names real working code; a neuter that reddens a test the cited RANGE does not cover is the proof.
- A guard reachable only when a flag is UNSET stays untested when every existing test sets that flag — grep the fixture for the skip flag before believing a gate is covered.
- `awk '/^func/,/^}/'` stops at the FIRST `}` at column 0 and can report a 425-line function as 11 — brace-count the span before concluding a symbol lacks a guard.
- A gate enforced in the ROUTE is absent from every non-route caller: headless routers call services directly, so a quarantine flag set by a pipeline is bypassable until the refusal lives in the SERVICE.
- Prove a guard dead by EXPERIMENT (break it, watch a named test fail), never by reading — a static read produced a confident false positive the tests already refuted.
- Verify a cited line range before writing against it: this repo's citations have been wrong roughly a third of the time.
- `grep -l '^field:'` matches the BODY too — a field inside a fenced example is not frontmatter; check where the `---` block ENDS before calling two values a conflict.
- When a green instrument contradicts your confident reading, re-check the READING: the linter ignored a body-only field and was right, twice in one session (cf. the TITLE_PLUGIN_MAP inversion).
- Scope a new lint to the SCAN SET of the consumer it mirrors — flagging cards no consumer evaluates produced 218 findings that named no broken reader, and a wall of warnings is how a linter gets routed around.
- Two `catch` arms in one function are two bugs with two fixes — I reported "the parser returns null on corrupt frontmatter" when that arm deliberately keeps the file and a DIFFERENT arm drops read errors; name the arm before writing the fix.
- Before flagging a documented invariant as violated, check what the rule's own examples mechanically ARE: the reference DAG's legal edges are all frontmatter fields, so 18 prose mentions of a TRDD id in specs were never edges and a body-scanning lint would have flagged the arbiter itself.
- A CAVEAT IS NOT A CHECK, and writing one is often what STOPS you checking: I published "the dispatcher never writes the sidecar" to a public tracker under a self-caveat saying it was inferred from a sub-agent's one-word "absent" — the write is at `memory-maintenance.py:416`, atomic, before the marker, with a test pinning it, and the check was the two commands I ran an hour later. Hedging FEELS like rigor and functions as permission to publish. Before any outward-facing write, a factual claim is CHECKED or REMOVED; hedge only what genuinely cannot be checked (a dead agent's cwd), never what one grep would settle.
- NEVER WRITE AN INSTRUMENT THAT PRE-SUPPOSES ITS ANSWER — mine was `find … ; echo "(none listed = absent)"`, and the "absent" label printed directly beneath a line that had just LISTED the file, which is how I came to believe it was missing. Compute the label from the RESULT (count the output and branch on it), never assert it alongside. Same root as the caveat above: when you anticipate an outcome, you build the output around it instead of testing for it.
- Checking does not merely correct a detail, it can CHANGE THE FINDING: the verified version was "the sidecar was written and NOT READ, so the chore is stamped as run without running and skips a full cadence" — a different, worse bug than the missing write I nearly filed, and the janitor's own code comment had predicted it verbatim. The unchecked issue would have sent them looking at code that was already correct.
- A CENSUS inside a normative doc can be falsified by the very commit that writes it — my clause said "the specs carry 18 provenance mentions" while adding more of them. State the boundary test qualitatively and cite the card that holds the DATED count; a spec asserts a contract, not a headcount.
- Never use REAL ids as format examples in a document others parse for references: four real TRDD ids illustrating "prefix optional, case-insensitive" would have minted phantom provenance edges inside the arbiter file itself. Generic forms (`[ABCD1234]`, `[TRDD-abcd1234]`, `[25]`) state the identical contract and cannot be mistaken for citations.

- A SPEC can be WEAKER than the comment implementing it, and the gap is where a wrong "safe to change" comes from: `governance-spec` pinned only "`verify` exits non-zero", while the script's own header pinned `2 = INVALID, 1 = ERROR` — so reading the spec alone said renumbering was permitted and the unauditable external consumers said it was not. Read the spec AND the code's own documented contract AND who consumes it before calling a contract changeable.
- When two conventions collide on one surface, MEASURE which is canonical instead of picking: `grep` itself exits 0/1/2 (match / no-match / error), so the grep-shaped CLIs were already right and the wrapper was the inverted one — and the file stating the exception must name the canon BESIDE it, or a reader of that file alone learns the inverted rule in isolation and copies its `||` idiom onto the tool where `||` silently means the opposite.
- A HAND-MAINTAINED NAME LIST IS NOT AN INVENTORY, and a count taken off one is not a measurement: TRDD-DQ6XN2VP's "26 pipelines, 21 remaining" (its STATE said 19) counted 7 one-line DELEGATORS as pipelines and omitted a real one that was already done — measured from the AST, the answer was **19 and 14**, a third smaller. A list is a snapshot of what someone believed once; DISCOVER the set from the code, and the number cannot go stale between sessions.
- WHEN A SHARED HELPER EMITS THE SAME SIGNAL AS THE SUBJECT, IT INFLATES EVERY COUNT — discriminate by which one OWNS the state, never by name: `gate0Auth` pushes a real `G00:` line into its CALLER's `ops` array, so by gate-ops alone it read as a pipeline, and it would have sat in the violation list permanently as a thing nobody can fix (there is no pipeline there to wrap). A pipeline DECLARES `const ops = []`; a helper takes it as a parameter. That test dropped it and nothing else — a name blacklist would have needed updating forever.

- A RETRY LOOP'S EXIT CONDITION DECIDES WHAT A NEW PER-CALL FIELD CAN MEAN AT THAT SITE — read the exit before theorising about the site: I filed that a `mismatch` inside a candidate-key retry chain *"plausibly means: this key shape did not take, try the next"*, and the loop advances ONLY on `success === false`, so a verdict riding on `success: true` returns at the first candidate and the next one is never reached. Five lines of control flow refuted it. And the REAL reason not to copy the pattern was a third thing neither option named — a sibling handler's stale-cleanup retry, gated on `!ok`, that already REPAIRS the exact condition the mismatch reports, so a 409 there would report a fault the route knows how to fix.
- WHEN YOU CATCH YOURSELF WRITING "PLAUSIBLY MEANS" ABOUT CODE YOU HAVE NOT OPENED, that is the whole finding — twice in one card I theorised about a call site (*"success is only ever assigned true"*, *"a mismatch means try the next shape"*) and both died to a single read. A hypothesis recorded in an acceptance box reads as analysis and is deferred like analysis; the read that settles it costs less than the sentence hedging it.

- "SHOULD THIS GATE ABORT?" PRESUPPOSES A WINDOW — locate the transaction's CLOSE before answering, because the answer is often that there is nothing to abort into: I carried abort-vs-report as the card's largest open question, and the pipeline's only `runGateSequence` **closes 86 lines and several gates BEFORE** the gate in question, with three of five actions never entering it at all. So the real question was *"should the window be widened across five actions?"* — a different and far larger one. One grep for `if (!txn.ok)` reframed a deferred design debate into a measured fact.

- A HELD `.git/index.lock` TAKES YOUR SAFETY NET, NOT JUST YOUR COMMIT — and the safety net is what makes a NEUTER safe: `git stash` and `git checkout -- <file>` both fail on the lock, so any TEMPORARY source mutation becomes unprotected, and a turn that dies mid-way (rate limit, compaction, a heartbeat boundary) leaves it sitting in a file that is already modified, with no clean way to tell neuter from work. Under a held lock: read-only measurement only, and defer every neuter until the lock clears. Notice this BEFORE reaching for the mutation — "I'll just edit it back" is true only for the turns that finish.

- RE-READ YOUR OWN EDIT AFTER A COMPACTION BEFORE REPEATING "VERIFIED" ABOUT IT — the claim is inherited from a measurement you can no longer see, and mine survived four turns of me asserting it: re-reading the two route files I had not opened since the compaction found the design **wired at FOUR sites and pinned at ONE**, so reversing the check order at three of them reds nothing. The edit was correct; the COVERAGE claim was not, and only opening the files could tell those apart.
- THE ORDER OF TWO GUARDS IS INVISIBLE TO THE TYPE CHECKER, so a "tsc 0 lines" verification says nothing about it: my `!success → 400` had to precede `verified === 'mismatch' → 409` at four sites, and reversed it would blame the read-back for a gate denial while compiling perfectly. When a fix adds a second early-return beside an existing one, the PRECEDENCE is the new claim — grep both line numbers at every site.

- A PROCESS LIST IS NOT EVIDENCE ABOUT *THIS* REPO UNTIL YOU CHECK EACH PROCESS'S **cwd** — `ps` shows the whole machine, and a plausible-looking culprit can be working somewhere else entirely: I blamed four live `git difftool` sessions for a `.git/index.lock` and told the user so four times over 1h44m; `lsof -a -p <pid> -d cwd` showed **three of the four were in OTHER repositories** and could never have touched it. The lock was 0 bytes with mtime equal to my OWN interrupted `git commit`, and `lsof` on it showed no holder at every probe — the right answer was available in the first five minutes. **The tell was in output I had already printed** (one session had `src/exactTokens.ts` open, a path that does not exist in this repo) and I read past it, because I was scanning for confirmation of the story rather than for the one field that discriminates. When a shared-name resource looks contended, identify the CONTENDER before believing the contention.

- A FIXTURE THAT MODELS *EXISTENCE* BUT NOT *CONTENT* IS STILL A NO-OP WRITE, and the second half is the one read-back verifications need: the fs overlay I inherited tracked which paths exist — its own comment saying it was added because "a mocked write is a no-op, so no post-install assertion could ever discriminate" — and never what they CONTAIN, so 13 tests still asserted an install "succeeded" with the plugin absent from the settings file it had just written. Fixing it took THREE layers, each found by the next red rather than by reading: record the body on write and consult it on read; MOVE the body on `rename` (an atomic `saveJsonSafe` writes `<path>.tmp.N` first, so content must travel or the target lands existing-but-empty); and model the SUBPROCESS's own effect — a user-scope install is performed BY the CLI, so nothing ever calls `writeFile` on that path and no amount of fs modelling reaches it.
- WHEN AN ACCURATE MOCK BREAKS A PASSING TEST, THE TEST WAS PINNING THE MOCK'S GAP — not the code: making the CLI mock actually remove the settings entry (which the real one does) broke a test asserting that a `writeFile` HAPPENED, because that write was the service's *fallback*, reachable only while the CLI mock did nothing. Split it: assert the OUTCOME for the happy path, and give the fallback its own test driving the case it exists for (the CLI THROWS). The neuter then reds the fallback test and only it — proving a safeguard block that nothing had pinned before.
- A TEST THAT FAILS MAY BE ASSERTING A REQUIREMENT YOU INVENTED — read the code's own claim before believing your test: mine asserted a cleanup sweep removes a DIFFERENTLY-SPELLED key, and the source says it *"only removes a key the CLI was already asked to remove — a second writer that can only ever converge on the CLI's own outcome"*. The red was correct and my expectation was the bug.
- PAIRING AN ERROR WITH "THE LAST FAIL LINE SEEN" IS UNSOUND UNDER PARALLEL OUTPUT — vitest interleaves files, so an `awk` that carries the most recent `FAIL` forward attributes errors to the wrong one: mine invented a "14th fixture" in a file that turned out to contain no reference to the function under test at all. Confirm an attribution by running the suspect file ALONE before recording it as a finding.

- THE FIRST FILE THAT *ANSWERS* YOUR QUESTION IS NOT THE FILE THAT *OWNS* IT, and a number taken from it is a guess wearing a measurement's clothes — ask WHICH SOURCE IS AUTHORITATIVE before quoting any count. Three files, three upward corrections, one session, same question ("how many plugins would deleting this loop strand?"): `settings.json::enabledPlugins` said **19**; `~/.claude/plugins/known_marketplaces.json` (270 entries vs settings' 252) proved the marketplaces were not *absent* but flagged `autoUpdate:false`/unset, so I had also had the MECHANISM wrong; `~/.claude/plugins/installed_plugins.json` (91 entries) showed `enabledPlugins` was the wrong DENOMINATOR entirely — the loop updates INSTALLED plugins, the live fire did 78 updates (tracking 91, not 35), and the real answer is **52**, on two marketplaces my earlier passes never even named. Nothing contradicted anything (enabled ⊆ installed); each source was internally consistent and each was a *subset view*, which is precisely why every intermediate number looked verified. **The tell is structural, not textual:** I never asked "is this the authority?", only "does this answer me?" — and a subset always answers, quietly and low. Corollary that bit in the same hour: I wrote *"X is the ONLY key holding marketplaces"*, true of the file I had open and false of the system, one `ls` away from the second registry. When a count will be acted on, enumerate the candidate sources FIRST (`ls` the config dir, not just the file you know), state which one owns the fact, and re-derive from that one.
- "ZERO FAILURES" IS ALWAYS SCOPED TO WHAT THE LOG RECORDS, so quote the scope or the phrase overstates itself — mine read *"zero failures across all 200 trail rows"*, which was true and meant *zero failures of the thing we log*: the rows are per-PLUGIN updates plus ONE aggregate marketplace row derived from a single process exit code, and **10 marketplaces had silently not refreshed in 11-155 days** while the lane printed `Refreshed every registered marketplace`. A per-item failure inside a one-invocation batch cannot move that batch's exit status, so an aggregate success claim over N items is evidence about 1 item, not N. Before reporting a clean run, name the population the counter actually covers — and treat any message asserting *every* from one exit code as the defect (TRDD-FXPV7L4D).

- CHANGING A TUNED CONSTANT OBLIGES YOU TO FIND EVERYONE WHO KNOWS THE OLD VALUE — the edit is one line and the blast radius is every party that derives from it: I moved an absorbed chore's cadence 3h→4h on a USER directive, and a DIFFERENT REPO's watchdog judges that same chore stale past **180 m**, so a HEALTHY run trips a `claimed-chore-stale` alert. I had spent the same session removing three messages that asserted the opposite of the truth (`tick-stalled`, `all-maxed`, "Refreshed *every* registered marketplace") and was about to ship a fourth of my own making — caught ONLY because the detector fired at me mid-session, not by any review. Two tests pinned the constant locally and both reddened, which is exactly why they exist; **no test on either side could see the cross-repo consumer.** So: grep the value AND its semantic twins across every consumer you ship to, and prefer DERIVING a peer's bound from something you publish over letting one cadence live in two codebases.
- **…AND THEN VERIFY THE MECHANISM BEFORE YOU REPORT THE NUMBER TO ITS OWNER — a remembered constant that reproduces the RIGHT number can still be the WRONG story, and the wrong story sends the fix to the wrong line.** I wrote the lesson above claiming the peer *hardcoded* 180 m. It does not. The bound is `max(3 × cadence, cadence + 600)`, where `cadence` is read from **that repo's own chore roster**, which lists this chore at 3600 s — so 3 × 3600 = 10800 s = 180 m, numerically exact and mechanistically fiction. There is no duplicated constant anywhere; the peer derives, which is precisely what my own lesson prescribed. Getting this right changed BOTH halves of the report. **Severity:** the ask is not "bump 180 to 240" — our 4 h cadence now EXCEEDS the 3 h threshold outright, so a healthy server reads as wedged for the last hour of EVERY cycle, permanently, where at 3 h it sat exactly on the boundary and fired only on jitter (my edit converted a latent defect into a deterministic one). **Owner:** the real defect is that a chore CLAIMED by another executor has its threshold derived from the NON-EXECUTOR's cadence — a bug that recurs for every chore any server claims at its own rate. And the function carried a soundness proof: *"the roster is test-asserted against `daemon.py` name-for-name and default-for-default, so this can never describe a cadence the daemon does not use"* — **true, and about the wrong party**, since this detector runs only on chores the daemon is NOT executing. A guarantee about the wrong party reads exactly like a guarantee.

## Refactoring under static tooling

- A static scraper keys on code SHAPE, so a refactor that preserves runtime behaviour can still break every citation — update the scraper in the FIRST refactor, not the 26th.

## Shell

- **`log` IS A zsh BUILTIN, SO macOS's `log show` NEVER RUNS UNDER zsh — AND ITS FAILURE LOOKS LIKE A CLEAN NEGATIVE.** `log show --last 5m --predicate '…'` returns `(eval):log:2: too many arguments` and **0 lines**, which reads exactly like "the unified log contains no such event". Use **`/usr/bin/log`**, and positive-control it (`--predicate 'eventMessage CONTAINS "a"'` returned 60131 lines) before believing any empty result. **This is not a quirk of one machine — zsh ships a legacy `log` builtin, so it is true of every zsh on every box**, and since zsh is the default macOS shell it applies to essentially every session here. I first wrote this up as "a shell function on this machine"; `type log` says `log is a shell builtin`, which is both the correct mechanism and a far wider blast radius — **`command -v log` prints a bare `log` and does NOT reveal it**, so `type`/`whence` is the probe that works. Every session that greps the unified log for a kill, a crash, or a service event and reads emptiness as evidence draws a wrong conclusion silently. Recorded here as well as in the runaway-investigation lesson above, because *here* is where someone hunting a shell trap will look.

- **A CHECK BUILT FROM THE EDIT YOU JUST MADE CAN ONLY SEE THAT EDIT — so it answers "did my change land?" while you read it as "is the file clean?"** Scrubbing a credential from a rules doc, I removed the Rule 12 example, ran `grep -c "and click Confirm"` → **0**, and reported the file clean; the card said **2 occurrences** and I wrote into its STATE block that the card was off by one. The card was right. The survivor was the WORSE of the two — the step-format table's `Action` row mandating *"Never write \"enter password\" — write `enter password <literal>`"*, i.e. the instruction that PRODUCES the exposure, in the table an author consults for every step. A needle derived from the passage you edited is structurally incapable of finding a second instance elsewhere; the instrument has to be built from the THING SOUGHT, over the whole population. For a secret that means extracting the token from the pre-fix blob **by SHAPE** and counting occurrences across every tracked file — never reading or printing it — which is both sounder and safer than the grep it replaces. Note the failure also inverted a correction: I "fixed" a true record to match a false measurement, so the wrong number would have outlived the wrong check.
- **STOPPING AT THE FIRST `✗` IN A LONG STATE BLOCK, THEN SCOPING THE RE-CHECK TO THE WRONG POPULATION, PRODUCES A CONFIDENT FALSE "STILL BLOCKED".** A card recorded *"✗ NO Emasoft template repo exists"*; I ran `gh repo list Emasoft --json isTemplate` → **0** and published *"the blocker is REAL and still standing 25 days later"* in a box AND a commit message. Nine paragraphs further down, the SAME card records the USER resolving it that same day with a **third-party** template (`fannijako/repo_template` — PUBLIC, `isTemplate: true`, wired at 4 sites by a named commit). So the resolution named a different OWNER, and a search of `Emasoft` could only ever return 0 — a number that reads exactly like a standing blocker and cannot distinguish *absent* from *not in the set I searched*. Two independent guards, both cheap: **read the whole STATE block before acting on any one entry in it** (they are append-only, so the newest fact is at the BOTTOM and the ✗ you find first is usually the oldest), and **derive the search population from the resolution, never from the problem statement**. This is the mirror of the stale-blocker pattern: there, a recorded blocker had cleared and nobody re-read it; here, it had cleared, the card SAID so, and I re-measured the wrong thing anyway.
- **A NEGATIVE CLAIM NEEDS AN UNBOUNDED INSTRUMENT — never `head`/`-m`/`limit` a search whose result will support "X does not exist."** `find app/api -ipath '*governance*' -name route.ts | head -6` printed six paths, `manager/` was the eighth, and I published *"there is no `app/api/governance/manager/route.ts`"* to another repo as fact. The truncation IS the finding and it is invisible: a capped list and an exhaustive one are byte-identical up to the cap. The tell is structural, not textual — I chose the cap, so the absence I "found" was one I imposed. Before writing *doesn't exist / absent / gone*, re-run the command with no cap and a `wc -l`. (Same family as `ls dir/*.md | wc -l` and `$?`-after-a-pipeline: an instrument whose failure mode is a plausible number.)
- `cmd | tee FILE | head` truncates FILE via SIGPIPE — capture to the file first, then inspect it.
- A SCRIPTED SECTION-REPLACE SILENTLY DELETES EVERY SECTION INSIDE ITS RANGE — and the follow-up edits aimed at the deleted text then no-op WITHOUT ERROR: slicing a card from `## Problem` to `## Approval log` ate its whole `## Acceptance` block, and three later `.replace()` calls on its checkboxes reported nothing wrong. Counting the boxes returned **0**, which is the only reason I caught it. After any range replacement, COUNT what should still be there.
- **A NEUTER MEASURED WHILE ANOTHER PROCESS EDITS THE SAME FILE MEASURES NOTHING — AND IT FAILS BY REDDENING *EXTRA* TESTS, WHICH READS AS A RICHER RESULT, NOT A BROKEN ONE.** A delegated agent's neuter reddened 2 where it predicted 1; the second was my concurrent revert landing underneath its run, and the honest move it made was to DISCARD the measurement rather than report it — caught by `git hash-object` vs `git rev-parse HEAD:<path>`, never by reading the neuter's output, which was internally consistent and wrong. This is the concurrent twin of the `sed -i ''` case (a neuter that applies nothing): there the file did not change when it should have, here it changed when it should not, and BOTH present as a plausible test result. So when anything else may touch the tree — a background agent, a watcher, a formatter — bracket every neuter with a blob-hash check, and treat "reddened more than predicted" as suspect rather than as a bonus finding.
- **THE COREUTILS ON THIS MACHINE'S PATH ARE GNU, NOT BSD — DESPITE `platform: darwin`** — so every macOS idiom in your fingers is the WRONG one here, and the failures are silent in different ways per tool: `sed -i ''` takes `''` as an empty FILENAME (edits nothing, exit 0 ⇒ three neuters "measured" that never applied), while `date -j -f FMT` dies on `invalid option -- 'j'` (⇒ a `|| echo "$NOW"` fallback fabricated a whole staleness table reading **19/19 at exactly 0 days**, when the truth was 10 cards ≥7 days and two at 38-39). Hit TWICE in one session on two different tools before I generalised it, so generalise it now: **do not reach for a BSD flag at all** — `perl -pi -e` for in-place edits, `python3` for date arithmetic, both identical everywhere. And when a fallback exists, a uniform column of identical values is the tell that the fallback fired, never a result.
- BACKTICKS IN A DOUBLE-QUOTED `git commit -m` ARE COMMAND SUBSTITUTION, AND THE SHELL DELETES THE WORDS: my message read *"a row that is `updated`, or `skipped` carrying a pid, or `failed` whose detail…"* and SHIPPED as *"a row that is , or  carrying a pid, or  whose detail…"* — the three load-bearing values gone, replaced by the empty output of three not-found commands, while `zsh: command not found: updated` scrolled past as if it were noise from something else. A commit message is write-once documentation, so the corruption is permanent unless caught in the same turn. Never put prose containing a backtick (or `$`, or `!`) in a double-quoted `-m`; write it to a file and use `-F`. Same family as the `sed`-that-matched-nothing: the shell reports ITS own success, not whether your intent survived.
- `$?` AFTER A PIPELINE IS THE *LAST* COMMAND'S STATUS, so `grep X file | head` reports `head`'s success and reads as "matched": mine printed `exit-of-grep=0 (1 = no findings)` under NO output at all — the label and the number contradicted each other and I nearly believed the label. Use `grep -c` and read the COUNT, never a pipeline's exit code.
- A NODE INSIDE A `catch` BLOCK IS NOT PROTECTED BY ITS OWN `try` — an instrument that walks the parent chain for enclosing `TryStatement`s OVER-REPORTS: mine called 4 writes "swallowed" and the true answer was 3, because one sat in the fallback `catch` where a throw propagates. Compare `node === tryStatement.tryBlock`, not mere ancestry.
- `cp -R` over an EXISTING file keeps the DESTINATION's old mode, so withdrawing an exec bit silently never lands on any machine that installed the previous version; `-p` forces it down (and is also the only form that survives a restrictive umask — plain `-R` under `umask 077` yields 700/600). Measure the overwrite case, not just the fresh one.
- `stat -f` is two different tools: BSD reads it as a FORMAT string, GNU as "filesystem info", so `stat -f '%Lp' file` on GNU prints filesystem stats for a file literally named `%Lp` and errors on the real one — use `stat -c '%a'`, or sidestep it with `node -e 'fs.statSync(f).mode & 0o777'`.
- `sed -i ''` is BSD-only: under GNU sed the `''` is an extra EMPTY FILENAME, so every call printed `can't read :` AND STILL applied the mutation — the stderr equally supported "my neuter never landed" and "it landed fine". Count the changed lines (`diff | grep -c '^<'`) and read the red test NAMES; an error message is no more proof the work failed than silence is proof it succeeded.
- A variable holding a COMMAND does not word-split in zsh either: `$mode src dst` with `mode="cp -R"` looks for a binary named `cp -R`, copies nothing, and every downstream check reads as a clean negative — the same non-splitting trap as `for x in $VAR`, and again only the positive control caught it.
- `git mv` stages the rename from the blob already in the INDEX, so content edits made BEFORE the move stay UNSTAGED at the new path — and `git status --short` renders that as `RM`, one letter from a plain `R` and reading as "renamed" at a glance. Stage the moved file BY NAME after every `git mv`.
- Never `pgrep`/`ps | grep` for a cmdline: the scanning shell matches itself. Snapshot `ps` to a file, then search the file.
- `grep -r --include=<glob>` SILENTLY DOES NOT FILTER on some toolchains — a positive control with `--include=*.cjs` returned `LICENSE` and `.cspell.json`, so a whole-ecosystem audit produced **38 false violations** across 4 repos that I was one step from filing upstream.

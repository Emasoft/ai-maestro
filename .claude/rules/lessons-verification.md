# Verification lessons — each line cost a real debugging session

Every rule here was learned by shipping the mistake first. They are one-liners because this file is
injected into every turn; keep them that way. Add a line only when a defect actually escaped.

> **Budget (TRDD-IIXYIU7G).** This file rides every turn, so it is capped at 96 KB and an entry may be at
> most 500 characters. Longer lessons live, verbatim and under the same headings, in
> `.claude/rules-reference/lessons-verification-full.md` — read it on demand by path. Nothing is ever
> deleted — an entry leaves CORE only by being MOVED there, verbatim and under the same heading. TWO
> conditions trigger a move: an entry that outgrows 500 characters, and the FILE reaching its cap
> (98304 bytes — 96 KiB, not 96000). For the second, relocate by LOWEST RECURRENCE FREQUENCY: an
> entry whose text is mostly one incident's own identifiers (a named gate, a named pipeline, a
> completed survey's result) has earned the reference; a trap that bites weekly stays in CORE,
> however old. `tests/governance/lessons-file-budget.test.ts` asserts both limits.

## Tests
- A NEUTER THAT REDDENS *EVERYTHING* NAMES A STRUCTURAL GUARANTEE, NOT THE THING YOU MEANT TO TEST — the wall is the finding: deleting `undo:` reddened 7 of 8 because the runner refuses to start, BEFORE ANY GATE RUNS, a sequence whose mutating gate lacks one (`failedGateId: 'PRECHECK'`, gate 0), and the 8th survived by never driving the pipeline. The discriminating form is INERT-BUT-PRESENT (`async () => {}`): exactly 1 reddened, proving the compensation is INVOKED, not merely registered.
- A test that passes with its guard removed pins NOTHING — never accept a new test without a recorded neuter run.
- READ THE RULE'S MODALITY, not just its text: a **SHOULD** is not enforced by a refusal, so an adversarial refusal test for it asserts a behaviour the rule never claims. R1.3 ("every team SHOULD have a COS") is enforced by AUTO-CREATION — the honest assertion is *omit it → one is created*. Ask "what does violating this look like?" before choosing the test shape.
- When the guard is an INITIAL VALUE, sample it DURING render — `result.current` is read AFTER effects flush, so an effect that sets the same value makes the assertion pass with the initial value INVERTED. Mine did: `useState(true)` neutered to `false` left the test green until it pushed from the render callback instead.
- Bound a scanned function at its OWN closing brace, never at the next export: brace-COUNTING desyncs on a `{` inside a multi-line parameter type (it called the repo's most obviously-locked mutator unlocked), and end-at-next-export swallows the module-level block between them (a COMMENT mentioning the call was blamed on the pure validator above it). Strip comments too — a module that documents its own locking in prose will match every needle you aim at its code.
- A machine-parsed table is not a place for prose: the enforcement map splits Guard on commas and resolves each piece as a path, so one explanatory citation reddened two ratchet tests at once. Put the explanation in the test file, keep the column parseable.
- A neuter run that does NOT fail is a finding about the TEST: mine asserted through a table-level `since` skip and never reached the branch it named, so the guard was decorative.
- Encode a guard at the granularity the BUG had — janitor#123 was COLUMN-granular and my per-table `since` could not express it, making the branch unreachable by construction, not merely untested.
- Seed a violation in EVERY shape the real data uses — one shape proves only that shape, and a "zero findings on the live corpus" criterion cannot detect a blind extractor at all: swapping mine to a prefix-requiring regex left the live run clean at exit 0 AND the prefixed seeded violation passing, so only the BARE-id variant caught it. Measure the shapes in the corpus first (`blocked-by: [X]` vs `[TRDD-X]` vs lowercase vs a YAML number), then seed one of each.
- When several ENABLED inputs can produce the same output, a test must switch off every one but the branch it names — mine left `localMarketplaces` at its default, so that branch added the same plugin first, `addCandidate` is first-write-wins, and stripping `agentId` from the `agentLocalScopePlugins` branch under test left the suite GREEN. Isolate the producer, or the assertion is about code you did not mean to test.
- When one ladder step is all that ships, a version-skew guard cannot be exercised end-to-end — export the pure check and inject a synthetic spec, or it stays unverified until the bug recurs.
- A test that passes for an unknown reason is a failure: isolate it (`-t "<full name>"`) before believing it.
- AND ITS MIRROR, MORE DANGEROUS: a test that FAILS for an unnamed reason is equally untrustworthy, because a red READS AS THE GUARD WORKING. Mine reddened on `replaceAtLines` refusing an empty `expect` — a precondition failing before the logic under test ran — so I read it as the approach being rejected. One non-empty trailing line in that fixture and it ships green; on the real document it corrupted it. Name the reason for a red.
- `vi.clearAllMocks()` clears CALLS, not IMPLEMENTATIONS — a mock overridden in one test leaks into every test after it.
- Route every mock through `(...a) => mockX(...a)` and restore it in `beforeEach`; an inline `vi.fn(async () => …)` in the factory cannot be restored.
- Pinning only the SUCCESS path reads as coverage — assert what happens when the operation fails, or the suite is decorative.
- `-t "R18.1"` also matches `R18.10`; read the test NAMES and COUNT, never the exit code (vitest exits 0 when a filter matches nothing).
- Asserting only `success === false` passes on ANY earlier refusal (a missing password, a failed auth gate) — pin the REASON, e.g. the specific gate in the ops trace.
- A fixture that models the filesystem as ONE constant boolean cannot test a post-condition: an install needs `existsSync` false BEFORE and true AFTER. Model the writes, or the post-condition stays a WARN forever.
- When a guard is unreachable in a fixture, say so in the test's docstring and file it — never seed the developer's REAL `$HOME` to reach it.
- `expect(err).not.toMatch(/one specific message/)` is satisfied by EVERY OTHER error — a positive control must assert `success === true`.
- Choose a positive control to FALSIFY the failure you fear, not to prove a list is non-empty: mine asserted a nested path and stayed green while the pathspec `dir/**/*.ts` silently dropped every TOP-LEVEL file (71 matched, 0 top-level) — including the file the test existed to protect.
- A source-scanning guard needs its scan set controlled too — assert a real count AND one file of each shape it must cover, or the guard reports "clean" on a set it never built.
- A verification gate that reads a REAL path passes vacuously in every test: it inspects state the fixture never touched. Point it at the fixture's seam, then model the write.
- A test can be propped up by the very bug you are fixing: 4 here asserted a cascade that only ran because the buggy ORDER put it before the gate that was failing.
- Provoke an unreadable-input test with ENOTDIR/EISDIR, never chmod — a permissions fixture passes VACUOUSLY when the suite runs as root, and CI often does.
- When the OS will not vary the input you are testing, INJECT it: `expect(got).toEqual(got.sort())` on a real dir passes with the sort removed, so spy the readdir and name the element that must move.
- A plan can name the wrong half of the tool: "wire the SEARCH at FTS5, acceptance byte-identical" was self-contradictory because the search takes a REGEX — and it was the ACCEPTANCE CRITERION, not the code, that exposed it.
- A shared positive control does NOT protect the assertions that never execute it — my neuter made the index fall back, both sides became walks, and 5 of 6 `expect(indexed).toBe(walk)` passed comparing a walk to itself; put the non-vacuity guard INSIDE the helper both sides call.
- An A-vs-B differential needs a fixture that DISCRIMINATES the axis you fear: zone order only shows up on a `cancelled` card in archived/ (non-terminal, so it survives the done-filter) sharing a blocker with a proposals/ card — every other shape agrees under both orderings.
- A subprocess test cannot be contained by `vi.mock` — redirect `$HOME` in the spawn env (`os.homedir()` honours it on POSIX), and PROVE containment by counting the real dir before and after, not by reading the code that was supposed to do it.
- A negative test must assert WHY it failed, not merely THAT it failed: neutering my API mutation-gate left every gated call still exiting non-zero (it now reached the missing-API-key check downstream), so an `expect_refusal` asserting only exit≠0 would have passed against a deleted gate — match the specific message and the neuter run names exactly the 3 tests that pin it.
- A seeded config file must satisfy its LOADER's version check or the loader returns DEFAULTS and every test silently exercises the OFF branch: my governance.json omitted `version: 1`, so 8 tests got the route's `user_authority_model_disabled` 409 instead of the guard under test — a fixture that tests the wrong branch, loudly enough to notice only because I read the error string.
- Before adding to a corpus, grep for EVERY test that READS it, not just the one the plan names: my plan named the conformance test's family array and a SECOND file asserted the live spec's exact clause census (38), so +3 clauses reddened a test nothing had predicted. Re-derive such a census with your own `grep`, never by copying the number out of the failure output — the count and the code would then agree by construction.
- Two guards over one file can look redundant and cover different failures: renaming `3P-IDX-01` → `3P-QQQ-01` reddened the family-NAME check while the exact-COUNT check correctly stayed green (still a valid declaration, count unchanged). Before deleting either as duplicate, name the mutation each one alone would miss.
- MEASURE an acceptance box before building for it, and mistrust the instrument it names: of two "unmet" boxes, one was ALREADY satisfied and the other prescribed a `vi.mock` helper for a SUBPROCESS writer it cannot reach. When a SIBLING file does not exhibit the bug, diff its setup first — the neighbouring CLI test already redirected `$HOME`, which named the fix and made the +1-per-run vs +0 count decisive.

- To prove a LOCK is taken BEFORE a read, make that read fail DISTINCTIVELY — then WHICH error arrives is the ordering assertion: mine returned `busy` when correct and `cannot read TRDD zone` under the neuter, and no assertion on "it threw" could have told those apart. Pair it with a positive control that the read really does throw when reached, or the whole test passes whatever the order.
- A shared "did the index answer?" guard does NOT prove THIS verb consulted it: `runBoth`'s fallback check only proves the PROCESS did not degrade, so reverting `next` to its old walk would have produced the correct answer, no fallback warning, and a green byte-identical assertion — a walk compared to a walk. Assert a per-verb ARTEFACT instead (a verb that never touches the index never builds one).
- Asserting the truncation NOTE is not asserting the truncation: an identity `capped()` still printed "+2 more not shown" and passed, because nothing checked the dropped rows were ABSENT. Every cap needs both halves — what it kept and what it lost.
- The neuter that proves a differential non-vacuous is also the one that can find a REAL bug: restoring the walk feeder made the two paths DISAGREE on the answer, and the walk was wrong (`asList` was array-only, so a scalar `npt:` was invisible to the linter in 7 places). A disagreement is a finding about the implementations, not a broken test — diagnose before repairing the test.
- A fix can be RIGHT and inert, and you have to measure which: `asList`→`refList` changed zero live verdicts because **0 of 196** live cards use the scalar form — so a live-corpus diff could never have validated it, and only the fixture differential could. Measure the INPUT (does the corpus even contain the shape?) before reading a zero diff as either proof or refutation.
- When a guard's own comment says it defends against a FUTURE shape, the today-shape cannot pin it: my user-scope test passed with `scope === 'local'` DELETED, because a today-shaped user row has no `projectPath` and the path comparison alone already excluded it. Seed the shape the comment names (a user row WITH the path) and the same neuter reddens exactly that test. Read the guard's stated reason, then seed against THAT.
- Neutering two guards together is sound only when you can name which test each one alone would redden: mine were independent by construction (the soft-delete case never reaches the second guard; the outside-root case already satisfies the first), so one run attributed both. Check that property before combining, or you have one failure and two candidate causes.
- A test that reuses the implementation to compute its own expectation cannot detect a change in that implementation — derive the expected value from the RULE (slashes→dashes, everything else kept), never by calling the function under test, and pick an input carrying the characters an earlier version got wrong.
- When a gate's correctness is half PRESENCE and half PLACEMENT, ONE neuter pins only half the file: DELETING G09b reddened my 3 removal tests and left the 2 soft-delete tests green, while MOVING it out of its branch reddened exactly those 2 and left the 3 green. Either neuter alone certifies a file half of which is vacuous — run the complementary pair, and expect each behavioural test to fall to exactly one.
- Arming a destructive branch is safe when a broken mock makes it FAIL INERT, and that property is worth stating rather than trusting: if either layer fails, the prefix compare is false, the branch is skipped, and the fixture folder SURVIVES — so the "folder is gone" assertion doubles as the containment proof (it can only pass if the fake root took effect). Never add the arming mock to an existing multi-case file — it arms every other case in that file at once.
- A stub must cover BOTH halves of a collaborator — the gate's call AND the post-condition probe's read of the same store: omit the probe half and G10 degrades to "verification unavailable", which prints as a WARN and reads as a pass. A post-condition that cannot run is indistinguishable from one that found nothing.
- A double that models an external command as a pure NO-OP cannot tell "it worked" from "it left no trace and the pipeline silently retried": mine skipped `claude plugin install`'s settings write, so G16 succeeded invisibly, G17's re-scan found 0 plugins, and its recovery reinstalled — TWO calls every run. Relaxing to `>= 1` would have passed while the test described the RECOVERY path and claimed the happy one. Model the ONE side effect the code reads back.
- When the branch under test loses a race to `list[0]`, the FIXTURE'S ORDER decides whether it is load-bearing: with the standing pick listed first, my keep-branch test passed with the keep-branch DELETED. Put the value the else-branch would choose FIRST, so only the branch can produce the expected outcome.
- A neuter that reddens NOTHING may mean you mutated a SHADOWED expression, not that the test is vacuous: I flipped `hasMultipleOptions = len > 1` → `> 0` and all 3 stayed green, because the render is `isSingleLocked ? … : hasMultipleOptions ? …` and the single-item case never reaches the second arm. Find which branch actually MATCHES for your fixture before naming a guard — the rule's text pointed at `> 1` and the working guard was the arm above it.
- An ABSENCE assertion whose selector could never match is vacuous in BOTH directions, and only a neuter says so: `queryByRole('button', {name: /^bob$/i})` never matched because each entry renders an avatar initial, so the accessible name is `"B Bob"` — the "member is not offered" guard passed identically with the guard deleted. Prefer the loosest selector that still discriminates, and treat a neuter that reddens NOTHING as a finding about the TEST.
- A guard every test MOCKS has NO test, and the mocks read as coverage: all five references to `checkTeamAccess` were `vi.mock(… vi.fn(() => ({allowed: true})))` — mocking the guard to prove the guard, so every one survives its deletion — and a sixth "hit" was a COMMENT. Mocking a guard's DATA SOURCES is fine and necessary; mocking the guard is the pattern that makes a grep sweep lie.
- An existing test on the same symbol may pin a DIFFERENT CASE than the rule governs: R18.8 is about a feature that CANNOT map, and its only `WarningCollector` test drove a model that maps fine with a note. Both call the same collector, so the sweep hits — read the rule's text against what the test actually feeds it, or you cite a rule off a test that would pass with the rule violated.
- Choose a neuter that leaves the SUCCESS/FAILURE bit unchanged when you want to prove an assertion is specific enough: deleting the anonymous-deny branch left `allowed:false` (the request just fell through to the not-a-member deny) and failed ONLY on the reason regexp — so the neuter's own output demonstrated that a test asserting `allowed === false` would have stayed green through it.
- A sweep hit can be a same-name function in a DIFFERENT module: `listAgents` is both `lib/agent-registry`'s (well tested) and `services/agents-core-service`'s (untested), so the grep looked like coverage of a rule nothing touched. Check the import path, not the symbol — this is the mirror of the all-mocks false positive, and it fails in the opposite direction.
- A design that routes AROUND a rule usually re-proposes the thing that rule superseded, under a new name: my "irreversible tail, best-effort, failure is residue the post-condition reports" is verbatim what R51 abolished ("There is no reporting option. This supersedes the detect-and-report contract of TRDD-KERM18NX"). Before inventing an exception, grep the rule for the shape you are about to propose.
- A ruling that requires editing the governance corpus is BY CONSTRUCTION not a ruling you may make under a general delegation: "you solve them" delegates decisions, not rewrites of `GOVERNANCE-RULES.md` + its spec clause + the test that pins them. Notice the edit the ruling implies BEFORE making the ruling — the file you would have to touch names the tier.
- A COMMENT claiming a test exists is not a test, and it is worse than silence because it tells the next reader not to look: a headless-parity file said the restart manager-gate "is covered there by the governance suite", and the string `Cannot restart team agent` appears in ZERO tests in either mode — only the WAKE twin is driven. Grep the assertion the comment promises before trusting it, and when it is absent correct the comment IN PLACE rather than only filing the gap.
- A "BIGGER THAN THE BIGGEST SINGLE FILE" FLOOR IS A CLAIM ABOUT A POPULATION, and grep and the extractor count different ones — so a floor taken from grep is a number about a set nothing reads. Mine sat at 55 while the biggest file had grown to 60, so a SINGLE-file read satisfied it and the guard quietly stopped meaning anything. Re-derive such a floor through the code that BUILDS the set (`walkRecords` saw 36/27 where a hand regex saw 49/29).
- A SHARED WORKDIR ACROSS ONE FILE'S TESTS CARRIES STATE THE FIXTURE NEVER WROTE — `seedAgent` only `mkdir -p`s it, so a plugin an earlier happy-path test installed SURVIVES, the gate under test prints `Skipped (plugin unchanged)`, and the assertion passes over a gate that never ran. Both my tests were vacuous until each one WROTE its plugin set; `null` is a write, not an omission.
- WHEN A UNDO-PATH TEST FAILS ON THE VERDICT WHILE ITS OWN STATE ASSERTIONS PASS, THE BUG IS A NEIGHBOUR'S: mine asserted the flag (restored, correct) and `not.toMatch(/INVALID STATE/)` (red) — the second assertion is the only one that could see G16's broken undo, because a rollback's verdict is a property of the WHOLE unwind. A test that asserts only the state its own gate owns will call a half-failed rollback clean.
- SPLIT ONE `it()` PER BRANCH — putting the named assertion first saves ONE, splitting saves all, because a neuter stops at the FIRST failure. 12 assertions in one test: both neuters died on #2/#4, leaving 7 unpinned — including the branch whose honesty paragraph I had just written, deletable while green — while the commit congratulated itself for running "separate neuters". Assertion ORDER decides what a neuter can reach; separate tests remove the question.
- START THE CONTENDER OUTSIDE THE HOLDER'S CALLBACK when the lock is REENTRANT — AsyncLocalStorage propagates into anything called inside, so a contender started there inherits the held set, skips the lock, completes instantly, and the test passes no matter what the code does. It must run in a SIBLING async context to contend at all.
- "ONE LOCK" MEANS ONE PHYSICAL OBJECT CONTENDED FOR, not one function each module calls: a string key in an in-process Map and a `mkdir` lockdir on disk are both "the lock", share nothing, and produce a system where every module is individually correct and the whole is unserialised.

- "SKIPPED 0" ON A CONTRACT THAT MAKES SKIPPING CORRECT IS A CLAIM TO PROBE, NOT A PASS: verify it by FALSIFYING one of the agent's own checklist assertions against live code, never by re-reading its report. Mine claimed a trust-shortcut was gone from a shell script — the only surviving hit was a COMMENT describing the removed bug, and its three cited SHAs all resolved, which is what made 18/18 credible. A tally is not evidence; a claim you could have proven false is.
- A FIXTURE DERIVED FROM THE CONSTANT UNDER TEST CANNOT SEE IT CHANGE: mine built its input as `[...WHITELIST, ...others]`, so emptying the whitelist shrank the fixture with it and the neuter came back 8/8 GREEN. Hard-code the REQUIREMENT in the test; the constant is the implementation. The second "green" run was a neuter script matching the `]` inside `readonly string[]` — it never emptied anything, and only a `git diff` of the mutated file, not the verdict, showed that.
- A TEST SEAM NO CALLER CAN REACH IS NOT A SEAM, and its own docstring will insist that it is one: `NetworkDeps` declared `cooldownStore`/`probeLock` and explained that without them a 429 test writes the DEVELOPER'S real machine-wide state — while `netDeps` forwarded only `fetchImpl`, so no tick test could ever drive a cooldown. That is precisely why the overload above sat undetected. Follow a seam from the TEST'S entry point inward, never from the module's declaration outward.
- A TEST WHOSE INPUT IS A PARAPHRASE OF THE BUG REPORT PROVES THE PARAPHRASE: a peer's regression fixture rewrote the reported line with an em dash the real one lacks, so it passed while covering a sentence nobody had ever reported and the reported one stayed unpinned. Paste the REAL line verbatim from the source that carries it — a fixture you retyped from the report is a fixture about your reading of the report.

## Tools that gate
- A reader that returns `[]` on an I/O error turns its gate into one that passes because it read nothing — separate ENOENT (legal absence) from every other errno (a fault), or "clean" and "unread" are the same answer.
- A gate needs THREE exit codes: 0 clean · 1 findings · 2 could-not-run. With two, every failure to read reports success. The same collapse in a one-liner: `cmd 2>/dev/null | grep -c X` prints 0 for a crash (mine died at module resolution) and for a clean run alike — one such 0 reached a commit body as a census. Never read a count without its producer's exit: capture to a file, print `$?` and `wc -l` beside it.
- The non-vacuity guard belongs in the TOOL, not only in the test that happens to exercise it — ours asserted `scanned > 100` in vitest for months while the shipped CLI certified an empty read.
- A secret/PII scan keyed on ONE shape is blind to every other shape BY CONSTRUCTION: mine matched `*.ts.net` FQDNs and so could never see the bare hostname, the raw `100.x` address, or the `user@` that were sitting in the same file — enumerate the classes, print a COUNT per class, and carry a positive control proving the scanner sees a string you know is present.
- A gate whose regex match CONSUMES its argument window skips every call site inside that window: mine matched `verb\s*\(` PLUS 240 chars, so `exec` advanced past a `saveJsonSafe(USER_GLOBAL_SETTINGS…)` sitting two lines below an `mkdir(…)` and reported it clean — match the verb ONLY, extract arguments separately.
- Splitting a call's first argument with a regex mis-cuts nested calls: `/,(?![^(]*\))/` cut `mkdir(join(CLAUDE_DIR, 'plugins'), …)` in the wrong place and attributed the finding to whichever token appeared later, so the SITE was right and the REASON was wrong — count bracket depth and skip string literals.
- A source scanner must EXCLUDE ITSELF — its own docs and pattern tables necessarily contain the patterns it hunts, so it reports its own prose as findings (the `pgrep -f` self-match trap, one layer up); mine flagged 2 violations in the detector file, which writes nothing.
- PIN what a detector CANNOT see: a write through a local variable (`renameSync(tmp, file)`) is invisible to textual matching, and silence about it reads as absence — list the blind spot as data and test the list, so it cannot grow unnoticed.
- A shared "set up the connection" helper can contain a WRITE, so an OBSERVER that calls it modifies what it measures by a route nobody would call healing: `applyPragmas` sets `journal_mode = WAL`, which is persistent, so a read-only verifier would have silently converted every rollback-journal index it inspected. Read what the helper does before reusing it on a path you only mean to look at.
- An observer that OPENS a path CREATES it unless told not to — `new Database(p)` materializes an empty db, so a sweep with one bad path leaves litter shaped exactly like the thing it audits. `fileMustExist: true` is the difference between an observer and a writer, and it is one word.
- A BOUNDED audit log written by a POLLING observer destroys the signal it exists to keep: at 50 slots and a 6-hourly sweep, one unrepaired fault fills every slot with copies of itself in two weeks and evicts all real history — the log then looks full of history and contains none. Record a TRANSITION (append only when this is not already the newest entry), never a poll.
- DELETING A NOW-STALE ALLOWLIST LINE WITHOUT RECORDING WHERE THE WRITE WENT MAKES A REAL WRITE INVISIBLE TO EVERY LIST AT ONCE: my `mkdir :: USER_GLOBAL_SETTINGS` entry went stale because the explicit call moved INSIDE the lock primitive — where it happens on a PARAMETER and no textual scan can ever see it. Stale-in-the-allowlist and gone-from-the-codebase look identical; the honest move is to re-home it in the known-indirect-writers list, never to drop it.
- READ THE FLAG'S OWN HELP before believing it filtered anything: `--min-severity error` sets the **exit code** only — the run still PRINTED all 426 lines (19 ERROR / 229 WARN / 176 INFO), so the first screen of a severity-"filtered" run was pure INFO and reading it as the error set would have inflated 19 into 426. A flag named after a severity is not necessarily an output filter; grep `^ERROR` yourself.


- A LINT MUST NEVER EXECUTE THE CORPUS IT LINTS: the blocker-probe evaluator's first draft (TRDD-U1EYWIPT) had `trddgrep validate` run the `sh -c` strings stored in card frontmatter — git-tracked, agent-writable, run by CI, the heartbeat and every cloner of a PUBLIC repo: remote code execution shaped as a lint. A probe nobody runs is inert; one the linter runs is a payload. Evaluate DECLARATIVELY (resolve `blocked-by` ids to columns); shell strings stay documentation.

## Lenient readers and the writes built on them
- GUARD THE WRITE PRIMITIVE, NOT THE CALL SITES, WHEN COMPENSATIONS CALL IT DIRECTLY: a per-call-site read guard cannot see an undo that writes a SNAPSHOT (`c.prior`, `structuredClone`d from the same blind read — so on a corrupt file the ROLLBACK restores `{}` and destroys what it exists to protect). The primitive is the only choke point both the forward and undo paths traverse, and it is the only fix that covers a FUTURE call site.
- AN HONEST BRANCH THAT ALREADY EXISTS AND IS UNREACHABLE IS THE TELL: three gates in one file carried the right message ("Could not check…", "Could not read settings for verification") in a `catch` that could never fire, because the lenient reader does not throw. The right answer had been written down three times and disarmed three times by the same reader — so look for the dead `catch` before writing a new branch.
- WHEN A CHANGE REDS N TESTS, SPLIT THEM BEFORE FIXING ANY: 13 of my 15 were fixtures encoding the bug (mocks that never persist the write, asserting an install "succeeded" with the plugin absent) and **2 were the design telling me no**. Fixing the 13 first would have buried the 2 under a pile of green.
- AN INVARIANT MAY ABORT ON A POSITIVE VIOLATION AND NEVER ON AN UNKNOWN — and check whether the gate is a "mere WARN" before believing it: mine flipped `result.success`, a later gate turned that into a REGISTRY flag, and the wake route refuses to start an agent carrying it. So a corrupt settings file made a CORRECT install report failure and brick the agent. "It only warns" was three hops from a bricked agent.


## Verifying a fix
- DISCLOSING THE SAME RULE VIOLATION TWICE IS A DECISION, NOT DISCLOSURE: the second obliges a STOP or a proposal, never better paperwork — verifying harder never restores the diff the rule exists to show.
- A BLANKET "ALL VERIFIED" OPENING IS FALSIFIED BY ITS OWN BODY when items are marked inferred further down: mine opened "Every charge below was verified first-hand", then labelled 3 of 7 inferred or unfixed. Honest labelling downstream does not repair a false summary upstream — the opening is what gets quoted. Same defect one scale up as the card it was fixing: a corrected header over a stale body. Scope the claim to what it covers.
- RUN YOUR OWN GATE ON YOUR OWN ARTIFACT: flipping a card to a terminal column is TWO edits — the column AND the `git mv` — and I did the first, committed, and shipped a ZONE-MISMATCH that the very linter this card delivered then flagged. A terminal column left in the OPEN zone makes the open count a lie, and it is exactly the half a human forgets.
- A ticked acceptance box recording a decision since REVERSED is worse than an open one — the next reader takes it as current: mine said the pillar CLIs are "repo-local, and here is why" hours after the USER ordered them installed. Strike it through with the reversal's CAUSE, and name the half that SURVIVES (the Node-22 objection was real; it is now handled, not avoided).
- The positive control that proves a subprocess READ your injected input is also what finds the bug: mine proved the fake `$HOME` was live and thereby exposed that `process.cwd()` is a kernel realpath while a recorded path is a typed string — so a lexical `path.resolve` compare made an agent in its OWN workdir report "not an agent". No in-process test could reach it (the constant is fixed at module load), and no zero-writes assertion is non-vacuous without it.
- Diagnose by dumping the actual ops/trace, not by reasoning about what the code should have done — the trace named the real cause in one run, twice, after reasoning had blamed the wrong thing.
- A verified WORKING TREE is not a verified COMMIT: every gate I ran (`validate`, `pillars:lint`, the doctor) reads the tree, all three passed, and HEAD meanwhile held a `column: dev` card inside `archived/` — the exact mismatch the doctor exists to catch. When the verdict matters, run the gate against what you actually committed (`git stash -u`, a temp clone, or `git show HEAD:<path>`).
- A sha written INTO the commit that carries it is correct only until the next `--amend`: I recorded the pre-amend sha in `implementation-commits:`, amended for an unrelated reason, and the list then named a commit that does not exist — and nothing checks it. Record a commit's own sha in a FOLLOW-UP commit, never inside itself.
- An acceptance box naming ANOTHER card as its destination is voided when that card goes terminal first: mine said "state the number in CTEQX0ZA's budget table" and CTEQX0ZA had reached `complete` hours earlier, where rule 12 freezes the body — name a destination you still own.

- An acceptance box can name the wrong OWNER, not merely an unmet state: mine sent a `~/.aimaestro/` inventory row to the janitor's footprint rule, which contains ZERO mentions of that path (it documents what the JANITOR creates) — and the precedent it told me to copy, `kanban-index`, was itself undocumented in the real owner. Check the box's named document AND its cited precedent before writing to either. Three of that card's four boxes had a wrong premise.
- A cross-boundary violation has TWO ends, and the fix belongs at the end with fewer edits — COUNT them before choosing: my plan promoted a page to clear 2 findings, but resolving its 11 outbound links first showed 9 pointed the forbidden way, so the promotion would have ADDED 9 to clear 2, and stopping the cascade meant migrating all 111 pages. Two consecutive plan revisions picked the wrong end because neither counted.
- VERIFY AN ISSUE NUMBER AGAINST ITS REPO BEFORE CITING IT: my own handoff listed `#49` as open work (it is CLOSED) and `#106` as this repo's (it is the JANITOR's) — two repos' numbering conflated in a list I then read back as fact. `gh issue view N --repo <owner>/<repo>` is one call and it is the difference between a work item and a phantom.
- Ask who the AUDIENCE of a reference is before valuing it: I refused to remove a link because it was "a good link", when a shared-store page naming a machine-private page cannot resolve for any other reader BY CONSTRUCTION — it was already dangling for everyone but me, so it had nothing to protect and cost self-containedness.
- TWO SIBLING CARDS THAT DISAGREE ARE A FREE DEFECT DETECTOR, and the contradiction is cheaper to spot than either error alone: one card's acceptance box said a dependency had "landed and wired" while that dependency's own card said `column: todo` over NINE `implementation-commits`. Neither is suspicious read by itself — `todo` looks like backlog, "landed" looks like progress — and together they cannot both be true. Cross-read the cards that cite each other before believing either.
- **A DEADLINE ON EDITABILITY INVITES WRITING MORE INTO THE FINAL EDIT** — a terminal freeze makes the closing commit permanent, and a review ending *"add X before you archive"* is the usual trigger, so *"this card is its last editable moment"* is the tell. The boundary, after two breaches in one day: a closing commit may write the transition's own record — `column:`, `updated:`, an append-only `## Approval log`, a STATE block ABOUT the closure — never a revision of existing prose.
- A carve-out list naming only the fault you have MET destroys healthy state on the next one: `downgrade` was carved out of the self-heal and `busy` was not, so a second process's lock timeout took the generic "delete and rebuild" branch. And "is this healable?" was being decided in TWO places, neither of which knew about the new code — make it ONE set.
- A `catch` that re-throws as `new Error(\`…: ${err.message}\`)` ERASES `err.code`, so an outer handler switching on that code cannot see it — and two conditions with OPPOSITE repairs silently collapse into one. Translate at the throw site, and guard the CONDITION rather than the reporter.
- `unlink` SUCCEEDS against a file another process still holds open (POSIX), so "delete it and rebuild" as a repair destroys a concurrent writer's work IN SILENCE — it goes on writing into an unlinked inode and reports success — while the heal ledger fills with "damage" that was only contention.
- A deliberate decision can rest on a false premise about a setting the SAME module enables: "holding the write lock across the read would block every other reader" is true for rollback-journal and FALSE in WAL, which `applyPragmas` turns on two files away. Check the mode before accepting the rationale that cites it.
- `busy_timeout` does NOT retry a snapshot conflict — a deferred `BEGIN` that reads before it writes can fail `SQLITE_BUSY_SNAPSHOT` unretried — so such a transaction is safe only by the ACCIDENT of its statement order, and the first `SELECT` anyone adds inside it breaks that silently. `BEGIN IMMEDIATE` puts the wait where the timeout applies.
- A handle leaked on an error path is bounded by what the CALLER does next: when the caller DEGRADES and keeps running (falls back to the slow path), the leak lasts the whole process rather than until exit.

## Measuring at scale
- A DENOMINATOR COUNTING EXPOSURE WHERE THE QUESTION NEEDS DETECTION inflates the arm you meant to exonerate: half my polling trials could not FAIL on the effect (a truncated WRONG password is still refused), so a "dead heat" was nothing of the kind. Ask "would this test FAIL on the effect?", never "did it encounter it". An arm with blind trials makes the event COUNT a floor; the RATE stays unbiased. And read each test WHOLE — a 10-line window hid one detector's last assertion.
- Measure peak RSS, not just wall time: the wall here was MEMORY and it landed at ~60-70k documents — BELOW the 100k target — so the failure is a heap crash, not a slow run.
- Hoisting a parse OUT of a transaction (to avoid holding the write lock) still has to STREAM — retaining the rows makes peak memory the CORPUS SIZE, and that exact hoist-and-retain shape appeared twice: the linter (4.45 GB crash) then the index builder (2.36 GB at 10⁵).
- A structure that is written, validated and tested but never QUERIED is invisible to the whole suite — my tests proved `records_fts` was POPULATED, never that anything reads it, so it dominated the cold build for a year unnoticed; grep for a consumer (`MATCH`/`bm25`), not for coverage.
- An RSS PLATEAU is a diagnosis, not a plateau: it stops rising exactly when accumulation ends, so flat-during-the-write-phase told me the wall was the pending array and not the writes.
- A fixture built from the SAME assumption as the code validates the assumption, not the behaviour: 10 green tests fed my checker a `.git/HEAD` mtime table, and the real `.git/HEAD` had not moved in a MONTH (a commit rewrites the reflog, not the symbolic ref) — so it reported "fresh" about a 5-hour-stale build. When the question is a fact about the world, one test must read the world.
- A committed fix is not a DEPLOYED fix: `pm2 restart` replays the existing build, so my ledger fix sat in git for 20 min while the server kept writing the buggy value — the corruption I had just repaired came straight back, and I only saw it because I checked the DATA rather than the commit.
- Which files are bundled decides which fixes a restart picks up: `server.mjs` + `lib/*.mjs` are loaded at runtime (live immediately), while `lib/*.ts` goes through `.next` (stale until rebuilt) — so "I restarted it" is true and irrelevant unless you know which half you changed.
- Date the artifact against the commit before trusting a deploy: `.next` mtime 13:59 vs fix 18:47, and `grep -c nextSeq .next/server` = 0, settled it in one command.
- Read the WHY-comments before designing a repair — they name the invariant you are allowed to lean on: verify()'s comment explaining that it ANCHORS on entries[0] "so a rotated file verifies" is the entire reason a lossless split existed, and I had been about to re-sign 703 entries.
- Before accepting a menu of bad options, ask which field the check actually reads: `seq` sits FIRST in canonicalize(), so renumbering re-signs — and that one fact turned "pick your loss" into "split the file, lose nothing".
- "One discontinuity" and "702 duplicate values in one file" are different diagnoses of the same scan — I reported the gap and only found the DUPLICATES by asking separately; a contiguity check cannot see an overlap.
- A dependency's module-level cache defeats streaming outright — gray-matter keys a cache on each file's full text, so a reader retaining NOTHING still accumulated the whole corpus; grep the parser for `cache` before believing a streaming rewrite.
- Peak RSS is not the live set: RSS counts uncollected garbage, so measure RETENTION with `--expose-gc` + `heapUsed`, or a heap-cap sweep — mine dropped 57% while the retained set barely moved.
- A memory correlation has more than one plausible cause: identical frontmatter + 4.4x memory looked exactly like V8 sliced strings, and deep-flattening every string moved it −3%, refuting it — run the candidate fix as a PROBE before editing any source.
- Extrapolation can be wrong in KIND, not degree — a projected "~6.5 GB, 80-90 s" was in fact an OOM CRASH at 4.45 GB; generate the real 10^5 fixture, because "slow" and "dead" are different verdicts.
- When a refactor must preserve output ORDER, say which alternative you rejected for it: evaluating rules inside the stream would have moved every cross-card finding into a trailing block, and that is invisible on a corpus whose cross-card rules all pass.
- Super-linear wall time near the limit is a SYMPTOM of the memory wall (GC pressure), not a second problem to optimize.
- "Do we need an index?" is usually "is the index rebuilt in RAM every run, or persisted?" — grep for the Maps first; this linter already built one, and that in-memory index WAS the 6.5 GB.
- Cost the JOIN, not just the scan: validating references is O(N × refs × lookup), and a lookup that re-readdirs the corpus makes a linear-looking tool quadratic.
- A generated fixture of identical stubs measures filesystem throughput and nothing else — give it the real body size, the real field set, and real cross-references, or the number is theatre.
- Before generalizing over N consumers, verify they share the shape you assume — I checked all three pillars on disk and found three different document models, one of which (PRRD) has no zones and no id in any filename.
- When the repo lacks an instance of the thing you are encoding (no PRRD.md here), find a REAL one elsewhere rather than encoding the grammar from memory.
- `\(` means OPPOSITE things per grep mode — a group in BRE, a literal in ERE — so a paren-balance audit that ignores `-E` calls correct code broken: mine did, 2/2 false positives, until I made it mode-aware and gave it an ERE-literal negative control.
- A pattern can be VALID under one grep and an ERROR under another: my `…|64\.0\.0/10)` (stray close-paren) matched under BSD grep and exited 2 under ugrep — so the check said "found" from a script and "could not scan" from an interactive shell. Balance the group; never let the verdict depend on which grep is on PATH.
- `\|` inside `grep -E` is a LITERAL pipe, not alternation — the pattern matches nothing and reads as "absent"; I nearly reported a subagent for a silent drop on the strength of it, four instrument-bugs into the same session.
- When a subagent's self-report and your check disagree, suspect the CHECK first: today the report said MERGED and my grep said 0, and the content was on line 947 the whole time.
- A wall-time delta whose SIGN flips between corpus sizes is noise, not a regression — mine read +12% at 50k and −6% at 10^5 for the same change, so the honest claim was "unchanged; the win is memory".
- Isolate the variable before crediting your change: after a corpus-mutating session, re-run the SAME corpus with the change stashed — three "differences" I was about to attribute to a sort were a new card, an unblocked card, and a row pushed past a 25-row cutoff.
- `readdirSync` order is POSIX-UNDEFINED — APFS returns it sorted, ext4 with dir_index returns hash order — so a byte-identical acceptance built on it passes at home and flakes in CI; sort at the ONE owner before building any differential on top.
- A benchmark measures its ENVIRONMENT until you make it not: two of my own probes overlapping read 17.35 s and 111.56 s for the SAME config, and the headline run — started the instant its 1.2 GB fixture landed, so it paid the write-back — read 33.29 s against 16.45 s once settled. Serialize, let the FS settle, THEN interleave the variants.
- A KEY-SET MATCH IS NOT A VALUE MATCH, and the SECOND pillar under a corrected story is the one nobody audits: told a backup cannot identify an unsampled moment, I rebuilt the claim on a flattened path-set diff and wrote "genuinely measured twice" in the sentence that said "identical key set". Two 2-element arrays with different commands flatten to the SAME paths (`path sets identical: True`) — it establishes SHAPE, never content.
- A heap CAP answers retention where peak RSS cannot: RSS counts garbage, but COMPLETION under `--max-old-space-size=256` is a boolean that contention and GC timing cannot fake — 1.29 GB of RSS over a live set under 256 MB was pure churn, and only the cap could prove it.
- When a box asks "is X still <a number measured in another session>", do NOT compare against the recorded number — its harness is gone. Run the A/B: same fixture, same method, your change vs HEAD with it stashed. Mine read 0.58 s against a recorded 0.37 s and looked like a 60% regression; HEAD read 0.58 s too.
- Isolate the harness FLOOR before attributing a total to the work: `help`, which reads nothing, cost 0.49 s of the 0.57 s total, so the thing I was measuring was ~0.08 s and four fifths of my "measurement" was `npx tsx` starting up. One extra run of the do-nothing command makes the number mean something.
- A table of `0.00`s is a broken instrument, never a fast tool: `$(bash scripts/pin-node.sh | tail -1)` captured a "must be sourced, not executed" usage LINE as the node path, so every timed command failed instantly. POSITIVE-CONTROL the timer against a known-duration busy loop before believing any row of it.
- Optimising N verbs to the SAME number is a finding, not a coincidence: all five graph verbs landing at 0.98-1.11 s says one shared term dominates them all (the O(N) freshness probe), which collapses five budget rows into one lever. Look for the common floor before tuning any single row.
- A gap between your parts and your whole is a measurement you have NOT made — never an overhead you may name: I proposed a cause for the same ~120 ms twice and was wrong twice (`realpathSync` at 1187 ms, which the code deliberately avoids; `path.resolve` at a real but tiny 28 ms), and my stage parts summed to 787-866 ms against a ~1.05 s end-to-end. Make the parts SUM in ONE interleaved process before aiming an optimisation at the difference.
- A probe can faithfully measure a cost the code does not pay: `realpathSync` per file really is 1187 ms, and `freshness.ts` really does a one-shot PREFIX REMAP instead — so the number was true and the attribution was fiction. Read the code path before believing your own benchmark of it.
- A "missing stage" between two measurements taken in two PROCESSES is the harness, not the code: my probe's node boot read 101 ms against the real CLI's 210 ms do-nothing floor (`help`, which reads nothing), and `identifyFiles` read 432 ms in one process and 299-306 in another — so BOTH gaps (an outer 180-260 ms and an inner ~120 ms) vanished on one clock, at 0.6% residual. Measure every stage and the wall in the SAME process before naming what is missing.
- Prove the instrument before reading it: my probe's residual came out at 977 ms and the diagnostic layers I had deliberately excluded summed to exactly 977 — that millisecond agreement is what made the 0.6% figure believable, and no amount of re-running would have.
- A CUMULATIVE-layer decomposition UNDERSTATES what removing a layer buys: increments of 28+2+13 ms predicted 43, and the hoist measured 63-68, because skipping a layer also skips the garbage it allocates (200 000 dead strings the GC no longer chases). Use layers to LOCATE the cost, then A/B the removal to size it.
- Ask whether a branch can EVER be taken before optimising inside it: 43 ms of 302 was spent building a git lookup key and probing two git maps that are EMPTY on a non-git corpus — a fast path `gitRoot` returning null makes unreachable BY DESIGN, and the hoist that skipped it met a budget three sessions had attacked from the expensive side.
- A vitest run given a test path that DOES NOT EXIST silently drops it: 5 files listed → `Test Files 4 passed`, exit 0. Same trap as `-t` matching nothing, one level up — read the FILE count against the number you passed, not just the test count.
- When a hoist is performance-only, NO behavioural test can pin it, and writing one anyway ships a false comment: 3 of my 4 neuters PASSED (`root !== null` for `shas.size > 0` — identical behaviour; dropping the `sha &&` check — the hoist itself shields it; only `canBeGit = false` reddened anything). I deleted the test rather than dress it as a guard, and the ONE neuter that failed named 4 real tests including the file's own positive control.

## Mocked modules
- Destructuring an export a module-mock does not define THROWS, even if the function is never called — import lazily, on the branch that needs it.
- A `vi.mock` FACTORY CLOSES OVER THE OBJECT IT WAS HANDED AT FIRST IMPORT, and that capture SURVIVES `vi.resetModules()` — so REASSIGNING a shared fixture per test leaves every mock writing to the PREVIOUS one: my pipeline really did call `removeManager()` and the assertion read a world nothing had touched, which is indistinguishable from a gate that never ran. Create the fixture ONCE and reset it IN PLACE (`Object.assign`), the way the sibling harness already mutates its `state`.
- A STUB WHOSE RETURN *SHAPE* IS INVERTED FAILS SILENTLY AND LOOKS LIKE THE FEATURE: `checkIbctScope` returns `string | null` (an ERROR, or null when authorized) and my stub returned `{allowed: true}`, so `if (scopeErr) { result.error = scopeErr; return }` made a SUCCESS verdict the failure reason and every call died at gate 0b. Only an assertion on the ERROR VALUE caught it — `expect(success).toBe(false)` would have called it a pass forever. Read the real signature, not the name.


## All-in-one functions (R50/R51)
- A gate whose `run` is a LOOP is not atomic: register its compensation BEFORE running it, or its own partial work is the one thing nothing reverts.
- An `undo` must tolerate `run` having done none, some, or all of its work — reverse only what `run` recorded in ctx.
- Check every precondition (adapters, permissions, reachability) BEFORE the first mutation; ordering prevents states that rollback can only repair.
- The last write in a pipeline still needs a compensation — a registry write after the filesystem work leaves the two disagreeing forever.
- Swallowing a per-item failure into `console.warn` and continuing converts one bad item into an invalid system.
- Order a compensation by the CONSTRAINT graph, not by blind reversal: if the do-path removed X first to satisfy a gate, the undo must restore X first to satisfy that gate's mirror.
- A snapshot nothing reads is not a safeguard — if a gate announces an archive, point at the artifact or stop announcing it.
- "Nothing was deleted" is false the moment ANY earlier sub-step landed; a preserved parent row with its children stripped is a husk, not consistency.

## Reading a running system
- `restart_time` IS NOT A CRASH COUNTER — pm2's crash counter is `unstable_restarts` (a restart before `min_uptime`): a peer read `restart_time = 9` and reported a CRASH-LOOP nobody had diagnosed, while `unstable_restarts = 0`, `exit_code = 130` (SIGINT — a deliberate stop), and the app's own boot banner appeared EXACTLY ONCE since `pm_uptime`, i.e. it ran 17.5 h straight. `restart_time` counts every deliberate `pm2 restart` too. Count the app's OWN boot lines before naming a loop.
- "No log line" is a claim about YOUR FILTER until proven otherwise — I concluded "the watchdog stopped beating" twice from my own instrument: first an `awk '$2 >= "09:09"'` whose `$2` was the literal `|` (pm2 prefixes each line), then a grep of `pm2-out.log` when the logger is `console.warn` → **stderr** → `pm2-error.log`. The beats were there the whole time.
- Before concluding a periodic task is dead, find the ONE branch that decides whether it logs at all: this watchdog logs only `if (stalled.length || tokenBlocked.length || dead.length)`, so silence and health are the same output.
- `pm2 restart <name>` replays the env pm2 CACHED at first start — it never re-reads `ecosystem.config.js`, so a var ADDED later never reaches the process no matter how often you restart. Use `pm2 restart ecosystem.config.js --update-env`, then verify against the PROCESS (`ps eww -p <pid>`), never against the file you just edited.
- `pm2 save` is a THIRD copy: the live process, the config file, and `~/.pm2/dump.pm2` (what `resurrect` replays after a reboot) drift independently. Ours held a var the config no longer defined and lacked the one it did.
- A gated feature that logs its own gate state (`[detect-only: FLAG not set]`) had been saying so on every beat for six days — detection nobody reads is not detection. Grep the log for the gate string before believing a flag is live.
- A live end-to-end probe of a route-level gate proves NOTHING when an earlier layer refuses first: my curl from the real Tailscale IP got the middleware's 401, never reaching the console check. Isolate the ONE link you actually doubt — a throwaway server printing `req.socket.remoteAddress` settled it in seconds.
- On a dual-stack (`::`) bind, loopback presents ONLY `::ffff:127.0.0.1` — so the "IPv4-compat" branch of a loopback check is the SOLE path the owner takes, not an edge case, and dropping it locks them out at their own keyboard.
- ASK the supervisor where it logs — never assume the default: pm2 was configured to `<project>/logs/pm2-*.log` while I read `~/.pm2/logs/ai-maestro-*.log` (18 days stale), so a healthy boot read as "produced no output at all". `pm2 jlist` → `pm_out_log_path`/`pm_err_log_path` settles it in one call.
- Do NOT append a marker into a log to bracket a restart: the supervisor REOPENS the file so the marker is orphaned, and the write freshens that file's mtime — which is exactly how I certified a dead log as live and read its silence as evidence.
- A restart is not a redeploy of the half you changed: under `tsx server.mjs` in FULL mode, `server.mjs` is transpiled at runtime but API routes still come from the prebuilt `.next`, so a process started AFTER the fix commit was still executing pre-fix route code — check `MAESTRO_MODE`/`NODE_ENV` on the PROCESS before reasoning about which half moved.
- Prove a deploy from the ARTIFACT THAT EXECUTES, not the commit: `grep`ping the compiled chunk for the new expression (`nextSeq(){…e.seq+1…}`) and for ZERO instances of the old shape is the check; `git log` showing the fix is what made this bug survive 20 minutes of believing it fixed.
- A NUMERIC CONSTANT IS THE WRONG NEEDLE FOR "IS MY FIX IN THE BUNDLE?" — a bundler keeps `3 * 60 * 60 * 1000` as the EXPRESSION, so the new `10800000` AND the old `3600000` both matched **0** files and that zero was uninformative in both directions (it reads as "the old value is gone", which is what you want to hear). Grep a distinctive STRING LITERAL the change introduces (an ops label, a field name), and carry a positive control proving the grep reaches the tree at all.
- **AN ARTIFACT DIRECTORY SHARED BY EVERY CALLER ATTRIBUTES NOTHING** — presence there is not authorship. `~/.dev-browser/tmp/` held `am2svg_*`, `p25-tables-integ-dark.png`, `scen14-S011f-after-click.png` and `amw-parity-*` side by side, from four unrelated projects. Before treating a file's location as evidence of who made it, `ls` the directory and see whose else is in there.
- `find <cache> -name X | head -1` RETURNS THE ALPHABETICALLY-FIRST VERSION, NOT THE INSTALLED ONE: eight `ai-maestro-plugin` versions were cached, mine picked `3.1.31` (21 columns) and I nearly called a peer's verified `3.2.0` (27) wrong. The cache is a SET; which member an agent loads is in `installed_plugins.json` per workdir — and there the answer was SPLIT (live agents 3.2.0, scenario litter 3.1.31). Enumerate the set, then ask which one each consumer resolves.
- **A GREP FOR AN EXACT STRING YOU PRINTED EARLIER THIS SESSION MATCHES YOUR OWN TRANSCRIPT.** My "unbounded" search for the two artifact filenames across all 172 sessions returned exactly one hit: the session I was typing in, because I had `ls`-ed those names an hour before. Same family as `ps | grep` finding its own shell, one layer up — the corpus you are searching now contains your own output. Exclude your own session id, or pick a needle you have never printed.

## Second-hand reports (sub-agents, prior sessions, TRDD verdicts, audit findings)
- A report from a sub-agent, a prior session, or a recorded TRDD verdict is a HYPOTHESIS — demand the exact file:line, grep it YOURSELF, and only then call it a fact.
- Never propagate a citation you did not run: I copied SF4's "wakeAgent enforces the roleMissing 409 (~:1958-1973)" into a new TRDD under the word "verified" — the gate was in the ROUTE and that range holds zero `roleMissing`.
- The reporter's confidence is not evidence; a verdict labelled REFUTED / CONFIRMED / VERIFIED still needs the grep, and this one was wrong in the REFUTED direction for five weeks.
- A quoted line RANGE rots even when the claim was once true — re-resolve it against the current file before citing it forward.
- A cache-miss write that RECURS every turn (~450-480k on two consecutive fires here) is a FAT SESSION, not a runaway — and the process table's AGE SPREAD is what tells them apart: oldest 1d2h / newest 7h58m means nothing was spawned recently, so there is no fan-out to `TaskStop`. The alert's own remedy ("stop background subagents") is then the wrong lever; the right one is to compact, because the cost is the standing prefix being re-billed, not anything still running.
- An automated alert fuses a trustworthy MAGNITUDE to a GUESSED cause — two sessions got different confident labels (`FORK_STORM` / `PREMIUM_MODEL_FANOUT`) for the same main-loop burn; act on the number, verify the attribution.
- Disprove a "storm" by the AGE spread, not the count: 29 `claude` processes all 1h+ old is standing infrastructure, and `turns × context × 0.1` already accounted for the whole spike.
- An audit naming ids you cannot find may be auditing a DIFFERENT repo — positive-control your `find` before reporting the absence as a defect (this stopped a false filing against janitor #120).
- Before exporting YOUR finding to another project, read THEIR architecture: my column-granular fix applies to an incremental-shape ladder, and memgrep runs full-current DDL on every open, so the "bug" does not exist there — checking is what stopped the second wrong filing.
- An advisor's VERDICT and its AMENDMENT need separate checking: mine was right that FTS5 cannot serve a regex search, and wrong that indexing replaces "the doctor's O(N x refs) join" — the doctor resolves via an O(1) Set over a Map it builds anyway, so the amendment would have added a native dep to buy nothing.
- "IT PASSED 6 TIMES, SO I FIXED IT" — a clean batch of 6-8 is not evidence of absence at any rate a flake plausibly has, and each statistic you reach for to dress it up needs an assumption you already denied. I quoted three p-values, then a Wilson CI as the *cautious* option: a permutation test needs RANDOMISATION, a binomial CI needs INDEPENDENCE AND HOMOGENEITY, and time-ordered batches over differing file versions supply neither. Report raw counts; interleave the arms.
- A complexity claim in a comment may be hypothetical and still correct: store.ts's "O(N^2 x refs)" names a lint written on `findRecord` that NOBODY WROTE, and says so one line later — the summariser dropped the qualifier, not the comment.
- A note you wrote in your OWN task description is a second-hand report by the time you read it back: mine said "ORDER BY path — the walk now agrees", and TRDD_ZONES is `proposals,tasks,archived,refused`, not alphabetical, so path order silently reshuffles every tie-break.
- A task title can outlive what shipped: #78 said "point trdd-doctor at the pillar index" and the commit made the LINTER streaming instead — read the commit, not the card, before believing a subsystem has a consumer.
- A sub-agent's self-reported INPUT COUNT is not coverage: a batch report headed `units: 67` had cited 21 and JUNK-listed 5, silently dropping 46 — and a truncated report is indistinguishable from a thorough one, so the skipped inputs are lost invisibly rather than re-queued. Check every input is either CITED or explicitly DISCARDED, and make the agent emit that accounting itself.
- A low yield is a question, not a result: 46 atoms from 67 units next to 91 from 21 is the signal that made me check — compare per-unit yield ACROSS sibling batches before accepting any of them.
- The TODO LIST and the CARD disagree, and the card wins: two cards this session read `column: todo` / `dev` with open boxes while my task list called them completed — because the CODE had landed with a parent and nobody advanced the card. Believing either one alone loses work twice over (re-building what shipped, or shipping what was never finished). Read the tree, then fix BOTH.
- ATTRIBUTE A DELTA PER-FILE BEFORE DESCRIBING IT — the extra file is usually not the finding: my backup mirror's 12-ERROR excess was 4 from the one page canonical lacks and **8 from a page present in BOTH stores that lints CLEAN in canonical**, because the stale page duplicated 4 atom ids corpus-wide. "One stale page" and "one stale page that breaks recall for a live page" are different bugs, and only the per-file breakdown tells them apart.
- READ THE CODE'S OWN DOCSTRING BEFORE CALLING A BEHAVIOUR A BUG: `sync_user_memory_mirror` says "it NEVER deletes a note … erring toward keeping memory" — the additive copy was DELIBERATE and correct (a mirror that replays deletions cannot protect against an accidental one). The real defect was its INTERACTION with consolidation, which moves atoms and deletes the source. Reporting "the sync is broken" would have asked them to remove the safety property.

## Claims about the codebase
- A CLAIM TAKES THE CHEAPEST EVIDENCE, NOT WHAT IT REQUIRES: a PROXY (a comment for the code), a QUANTIFIER over a SAMPLED population (`all 6`, `no exec`), an ACTOR swap (a watchdog's clause read as YOURS). Ask: what population, enumerated or sampled? whose action? THE DIMENSION YOU DID NOT VARY HOLDS THE ANSWER.
- BEFORE `git commit`, NAME THE COMMAND BEHIND EVERY FACTUAL CLAIM IN THE MESSAGE; soften what has none to "inferred", or cut it. Twelve review rounds on one card: every claim asserted from adjacency, or accepted from review UNCHECKED, failed — one refutation found by grep AFTER committing. But naming is not running: a claim I DID source failed too, off a 10-line window that truncated its own evidence. The defect is PLACEMENT — verifying downstream of the commit is the expensive way.
- A CORPUS-WIDE ALL-CLEAR CANNOT SEE A CONDITIONAL LIE, and a tool's own report is not the population it reports on: `trddgrep fix` printed "nothing to repair" while `lintCorpus` declared 3 findings autofixable — the flag was wrong only on the FROZEN subset, so the aggregate read clean while the promise stayed live. An earlier flag on the same file was wrong unconditionally and was therefore countable. Measure the PREDICATE, never the consumer's summary of it.
- WHEN YOUR OBJECTION IS "THESE ARE NOT THE SAME PROPOSITION", THE SETTLING COMMAND MUST READ THE OTHER ONE: a review that correctly challenged a fixer's output as a proxy then proposed measuring that same output. Run as given it would have CONFIRMED the finding for the wrong reason and closed the case over a live bug — a false confirmation is worse than a miss, because it ends the search.
- WHEN TWO THINGS DISAGREE, THE AUTHORITY FOR WHICH TO CHANGE IS THE RULE, NEVER A COMMENT WRITTEN BY ONE OF THEM: I made a linter flag agree with a fixer on the strength of the fixer's own comment saying it was correct. It WAS (the rule permits removing only a body line FALSELY contradicting a terminal column; the agreeing case stays frozen) — but had it not been, I would have deleted the disagreement that was the only signal.
- A comment citing a rule is NOT a guard enforcing it; the enforcement map is right more often than the comments.
- A citation pointing at a CONST TABLE is worth LESS than no citation: R19.10 cited one line of `TITLE_PLUGIN_MAP`, and a test written against a table stays green after every guard that READS the table is deleted — so the row advertises a pin it never had. Cite the site that ACTS on the data, never the data.
- A rot-proof gate qualifier does NOT make its line range trustworthy: the check verifies the LABEL exists in that pipeline and never that the range still contains it, so R20.5's ranges sat ~74 lines adrift under a passing check. Re-measure the range whenever you touch a qualified row.
- A CONTRADICTED row with no guard is not automatically a stale citation — read the RULE TEXT before "fixing" it: R9.13 says REJECT while the code QUARANTINES, so the row was correct and the citation was the lie waiting to be written.
- A guard reachable only when a flag is UNSET stays untested when every existing test sets that flag — grep the fixture for the skip flag before believing a gate is covered.
- `awk '/^func/,/^}/'` stops at the FIRST `}` at column 0 and can report a 425-line function as 11 — brace-count the span before concluding a symbol lacks a guard.
- A gate enforced in the ROUTE is absent from every non-route caller: headless routers call services directly, so a quarantine flag set by a pipeline is bypassable until the refusal lives in the SERVICE.
- Prove a guard dead by EXPERIMENT (break it, watch a named test fail), never by reading — a static read produced a confident false positive the tests already refuted.
- Verify a cited line range before writing against it: this repo's citations have been wrong roughly a third of the time.
- `grep -l '^field:'` matches the BODY too — a field inside a fenced example is not frontmatter; check where the `---` block ENDS before calling two values a conflict.
- When a green instrument contradicts your confident reading, re-check the READING: the linter ignored a body-only field and was right, twice in one session (cf. the TITLE_PLUGIN_MAP inversion).
- Scope a new lint to the SCAN SET of the consumer it mirrors — flagging cards no consumer evaluates produced 218 findings that named no broken reader, and a wall of warnings is how a linter gets routed around.
- Two `catch` arms in one function are two bugs with two fixes — I reported "the parser returns null on corrupt frontmatter" when that arm deliberately keeps the file and a DIFFERENT arm drops read errors; name the arm before writing the fix.
- Before flagging a documented invariant as violated, check what the rule's own examples mechanically ARE: the reference DAG's legal edges are all frontmatter fields, so 18 prose mentions of a TRDD id in specs were never edges and a body-scanning lint would have flagged the arbiter itself.
- NEVER WRITE AN INSTRUMENT THAT PRE-SUPPOSES ITS ANSWER — mine was `find … ; echo "(none listed = absent)"`, and the "absent" label printed directly beneath a line that had just LISTED the file, which is how I came to believe it was missing. Compute the label from the RESULT (count the output and branch on it), never assert it alongside. Same root as the caveat above: when you anticipate an outcome, you build the output around it instead of testing for it.
- Checking does not merely correct a detail, it can CHANGE THE FINDING: the verified version was "the sidecar was written and NOT READ, so the chore is stamped as run without running and skips a full cadence" — a different, worse bug than the missing write I nearly filed, and the janitor's own code comment had predicted it verbatim. The unchecked issue would have sent them looking at code that was already correct.
- A CENSUS inside a normative doc can be falsified by the very commit that writes it — my clause said "the specs carry 18 provenance mentions" while adding more of them. State the boundary test qualitatively and cite the card that holds the DATED count; a spec asserts a contract, not a headcount.
- Never use REAL ids as format examples in a document others parse for references: four real TRDD ids illustrating "prefix optional, case-insensitive" would have minted phantom provenance edges inside the arbiter file itself. Generic forms (`[ABCD1234]`, `[TRDD-abcd1234]`, `[25]`) state the identical contract and cannot be mistaken for citations.

- A SPEC can be WEAKER than the comment implementing it, and the gap is where a wrong "safe to change" comes from: `governance-spec` pinned only "`verify` exits non-zero", while the script's own header pinned `2 = INVALID, 1 = ERROR` — so reading the spec alone said renumbering was permitted and the unauditable external consumers said it was not. Read the spec AND the code's own documented contract AND who consumes it before calling a contract changeable.
- When two conventions collide on one surface, MEASURE which is canonical instead of picking: `grep` itself exits 0/1/2 (match / no-match / error), so the grep-shaped CLIs were already right and the wrapper was the inverted one — and the file stating the exception must name the canon BESIDE it, or a reader of that file alone learns the inverted rule in isolation and copies its `||` idiom onto the tool where `||` silently means the opposite.
- WHEN YOU CATCH YOURSELF WRITING "PLAUSIBLY MEANS" ABOUT CODE YOU HAVE NOT OPENED, that is the whole finding — twice in one card I theorised about a call site (*"success is only ever assigned true"*, *"a mismatch means try the next shape"*) and both died to a single read. A hypothesis recorded in an acceptance box reads as analysis and is deferred like analysis; the read that settles it costs less than the sentence hedging it.

- RE-READ YOUR OWN EDIT AFTER A COMPACTION BEFORE REPEATING "VERIFIED" ABOUT IT — the claim is inherited from a measurement you can no longer see, and mine survived four turns of me asserting it: re-reading the two route files I had not opened since the compaction found the design **wired at FOUR sites and pinned at ONE**, so reversing the check order at three of them reds nothing. The edit was correct; the COVERAGE claim was not, and only opening the files could tell those apart.
- THE ORDER OF TWO GUARDS IS INVISIBLE TO THE TYPE CHECKER, so a "tsc 0 lines" verification says nothing about it: my `!success → 400` had to precede `verified === 'mismatch' → 409` at four sites, and reversed it would blame the read-back for a gate denial while compiling perfectly. When a fix adds a second early-return beside an existing one, the PRECEDENCE is the new claim — grep both line numbers at every site.

- A TEST THAT FAILS MAY BE ASSERTING A REQUIREMENT YOU INVENTED — read the code's own claim before believing your test: mine asserted a cleanup sweep removes a DIFFERENTLY-SPELLED key, and the source says it *"only removes a key the CLI was already asked to remove — a second writer that can only ever converge on the CLI's own outcome"*. The red was correct and my expectation was the bug.
- PAIRING AN ERROR WITH "THE LAST FAIL LINE SEEN" IS UNSOUND UNDER PARALLEL OUTPUT — vitest interleaves files, so an `awk` that carries the most recent `FAIL` forward attributes errors to the wrong one: mine invented a "14th fixture" in a file that turned out to contain no reference to the function under test at all. Confirm an attribution by running the suspect file ALONE before recording it as a finding.
- **A COMMIT MESSAGE IS THE ONE CLAIM NOTHING CHECKS**, so a mechanism you traced an hour earlier can still ship wrong there: mine said committing a digest *"stops the loop — `index_is_stale` compares the committed digest"*, and that function is handed the WORKING-TREE text and never reads git. Tests, types and the pre-commit hook all pass straight over a false because-clause. State the mechanism you MEASURED, or state the effect and omit the why.
- **A CONSTANT'S NAME AND ITS OWN DOCSTRING ARE NOT ITS USE SITES** — read who calls it before deriving anything from it. `TICK_ALERT_PREFIXES` reads as a producer's declared namespace and its docstring asserts the correspondence, but its ONE use site is `ownsTickAlert`, passed as the `owns:` REAP FILTER: it constrains what the beat DELETES, never what it EMITS. The real emission was one three-branch ternary 200 lines away, which is both the correct source and a stronger one.
- **LABELLING AN UNVERIFIED CLAIM IS DISCLOSURE ONLY WHEN THE CONCLUSION STILL NEEDS IT** — the mechanical test is to DELETE the claim and see whether the conclusion weakens. If it does, the label discloses a dependency; if it does not, the label is retention dressed as honesty, and the claim rides forward as though checked. Apply it before writing "inferred" or "unverified" beside anything.
- **A PARENTHETICAL ENUMERATION NAMES ITS OWN COUNTEREXAMPLE AS AN EXAMPLE**: "every pane is `absolute inset-0` (empty state, terminal, work, hosts)" — the empty state is `h-full`; the loose sentence survived, the PARENTHETICAL was flatly false, in a pushed memory atom. And the claim was the wrong KIND: `absolute inset-0` pins a pane's BOX to its parent's, not its CONTENT — it moved the question into two components I never opened. One grep settled it.

## Shell
- `${var/pat/rep}` with `\'` or `\/` typed inside DOUBLE quotes keeps the backslashes under /bin/bash 3.2.57 and zsh 5.9 — MEASURED; bash 5.3.15 strips them, so the same line is clean or corrupt by which shell ran it: my card line gained `\'s` and `0\/1\/2` (this harness's Bash tool runs zsh), and `trddgrep edit` printed "edited" for it. Close the quote to escape (`'"'"'`) or replace a whole line from a file; then verify the WRITTEN line (`grep -c '\\'` = 0).
- `cmd | tee FILE | head` truncates FILE via SIGPIPE — capture to the file first, then inspect it.
- MISDIAGNOSING A TRUNCATION IS WORSE THAN THE TRUNCATION — the wrong fix can work by accident and CONFIRM the wrong cause: `… | sort -u | head -6` emitted exactly 6 lines, cutting the alphabetically-last name; I blamed "ANSI noise" and "fixed" it by stripping escapes, which worked only because that rewrite also dropped the `head`. Count output lines against your cap FIRST — a result exactly equal to `head -N` is the tell.
- A SCRIPTED SECTION-REPLACE SILENTLY DELETES EVERY SECTION INSIDE ITS RANGE — and the follow-up edits aimed at the deleted text then no-op WITHOUT ERROR: slicing a card from `## Problem` to `## Approval log` ate its whole `## Acceptance` block, and three later `.replace()` calls on its checkboxes reported nothing wrong. Counting the boxes returned **0**, which is the only reason I caught it. After any range replacement, COUNT what should still be there.
- `$?` AFTER A PIPELINE IS THE *LAST* COMMAND'S STATUS, so `grep X file | head` reports `head`'s success and reads as "matched": mine printed `exit-of-grep=0 (1 = no findings)` under NO output at all — the label and the number contradicted each other and I nearly believed the label. Use `grep -c` and read the COUNT, never a pipeline's exit code.
- A NODE INSIDE A `catch` BLOCK IS NOT PROTECTED BY ITS OWN `try` — an instrument that walks the parent chain for enclosing `TryStatement`s OVER-REPORTS: mine called 4 writes "swallowed" and the true answer was 3, because one sat in the fallback `catch` where a throw propagates. Compare `node === tryStatement.tryBlock`, not mere ancestry.
- `cp -R` over an EXISTING file keeps the DESTINATION's old mode, so withdrawing an exec bit silently never lands on any machine that installed the previous version; `-p` forces it down (and is also the only form that survives a restrictive umask — plain `-R` under `umask 077` yields 700/600). Measure the overwrite case, not just the fresh one.
- `sed -i ''` is BSD-only: under GNU sed the `''` is an extra EMPTY FILENAME, so every call printed `can't read :` AND STILL applied the mutation — the stderr equally supported "my neuter never landed" and "it landed fine". Count the changed lines (`diff | grep -c '^<'`) and read the red test NAMES; an error message is no more proof the work failed than silence is proof it succeeded.
- A variable holding a COMMAND does not word-split in zsh either: `$mode src dst` with `mode="cp -R"` looks for a binary named `cp -R`, copies nothing, and every downstream check reads as a clean negative — the same non-splitting trap as `for x in $VAR`, and again only the positive control caught it.
- `git mv` stages the rename from the blob already in the INDEX, so content edits made BEFORE the move stay UNSTAGED at the new path — and `git status --short` renders that as `RM`, one letter from a plain `R` and reading as "renamed" at a glance. Stage the moved file BY NAME after every `git mv`.
- `git log --not --remotes` WITH NO POSITIVE REF LISTS NOTHING, and that empty reads as "everything is pushed" — git does NOT substitute HEAD when only NEGATIVE refs are given. MEASURED after a review called it an untested guess: bare form **0**, `git log HEAD --not --remotes` **458**, same repo same second, no remote ref containing HEAD. A false all-clear on a question whose wrong answer is unrecoverable. Ask `git rev-list --left-right --count <remote>...<branch>`.
- Never `pgrep`/`ps | grep` for a cmdline: the scanning shell matches itself. Snapshot `ps` to a file, then search the file.
- `grep -r --include=<glob>` SILENTLY DOES NOT FILTER on some toolchains — a positive control with `--include=*.cjs` returned `LICENSE` and `.cspell.json`, so a whole-ecosystem audit produced **38 false violations** across 4 repos that I was one step from filing upstream. The tell was that the "code" hits were `.md` files. Enumerate with `find`, grep each file, and positive-control the filter before believing ANY count built on it.
- A NEEDLE KEYED ON THE WRONG EXTENSION REPORTS A CONFIDENT FALSE ABSENCE: `find … -name '*.flag'` missed the gate file `oauth-rotator-tick.enabled`, so I concluded a live subsystem was inert and nearly reported the rotator as switched off. Test for the THING (`test -f <exact path>`), not for a naming convention you assumed.
- `$?` AFTER A PIPELINE IS THE LAST COMMAND'S STATUS — `yarn … | tail` then `echo $?` printed `0` for a run that exited `1`, and the `(1 = findings)` label I printed beside it made the wrong number look authoritative. Capture to a file, then read the file.
- `ls dir/*.md | wc -l` on an unmatched glob is not 0, it is MEANINGLESS — count with `find`; mine reported 65 files in two empty dirs and the sample listing beside it was already blank.
- When two outputs of the same command block disagree, recount before building on either — the contradiction IS the finding.
- A scripted bulk edit over PROSE destroys what its regex cannot parse: my "strip 1350 citations" pass ate the `[]` inside `s.get('DNSNames', [])` as an empty citation bracket and left ~600 broken sentences (`Sources:,,,,,.`) across 8 files. A removal that requires RE-GRAMMARING the surrounding sentence is a language task — Edit tool or one agent per file, never `sed`.
- Back up before a bulk edit, because the repair is a RESTORE, not a patch: the deleted citations were the only thing that made those sentences parse, so nothing in the damaged file could reconstruct them.
- A corruption scan for `` `` `` matches every ``` fence — mine returned ~600 hits that were 90% fences, hiding the real damage. Filter the fence out (`grep '``' | grep -v '```'`) before believing either the count or the clean.
- An EXACT-STRING coverage test under-reports against a document that normalizes as it merges: mine scored 81% and every one of the 10 command-shaped "losses" was present as a variant (`--exit-node=<hostname-or-ip>` vs `<node-or-ip>`, a persistent `sysctl.d` line vs the ephemeral `sysctl` one) — grep the CONCEPT before reporting content lost.
- A byte-count floor is the cheapest guard against an agent that summarizes when told to union — it caught a re-merge that returned 18,823 bytes from 23,850 bytes of input while reporting `22 merged, 0 dup, 0 junk`, three claims that cannot all be true.
- An unanchored alternation matches INSIDE ordinary words: `roo` in my harness-detector matched **"root"**, reporting 80 units where the true answer was 0. Word-boundary every term AND count each term separately, so one bad alternative cannot hide inside the total.
- `for x in $VAR` over a multi-line variable runs ZERO iterations in zsh (it does not word-split), so every count returned 0 and read as a clean refutation — the same trap as `set -- $spec`. Use `while IFS= read -r`, and put a POSITIVE CONTROL in the same block: mine (145/158 files mention `tailscale`) is the only reason I caught it.
- A CONTENT scan cannot find an artifact defined by its LOCATION — a file inside `.cursor/plans/` is a Cursor artifact whether or not its text ever says ".cursor/". My content scan found 7 files and missed the only unit that mattered; the path scan found 469 and reached it.
- Scope the sweep to the ARTIFACT, not to the subdirectory you happen to be editing: I measured `references/*.md` for four passes and the skill's PRIMARY file, `SKILL.md`, was never once in scope — it held 8 sites, one of them a bullet still DESCRIBING the citation system I had already deleted, which is a false claim rather than mere leftover narration.
- A near-miss synonym re-reads as clean: `the corpus` does not match `this corpus` or `corpus-derived`, so one file measured 0 twice and was not — widen to the bare stem and re-measure everything already called DONE.
- `grep -c FAIL` on a test log counts the word FAILED inside expected negative-path OUTPUT: mine reported "FAIL lines: 31" on a suite that was exit 0 / 274 files green. Count the runner's own failure MARKERS (`Failed Tests`, `×`) or read the summary line — never a substring that the tests under test are supposed to print.
- "0 errors" means "no rule looked" — never "clean": `greptrdd validate` passed my corpus while 10 of its own cards carried a duplicate body state field. Read a clean verdict as *clean of the classes it tests*.
- A linter and its `--fix` must share ONE predicate: mine had drifted (the lint checked only the v2 vocabulary, the fixer also accepted the v1 map), so it REPAIRED `status: not-started` — all 10 real cases — without ever REPORTING it. The report is the only thing a human reviews before running `--fix`, so that asymmetry is the worst one a fix pipeline can have.
- A glob whose depth does not match the layout returns 0 and reads as ABSENT: `~/Code/*/design` missed every fleet plugin repo (they nest two deep), so "0 occurrences on this machine" was about files I never scanned. DISCOVER the corpora (`find -type d -name tasks -path "*/design/*"` → 37, not the ~12 the glob saw) instead of assuming their shape.
- A repair tool's fallback must be the COMPLEMENT of its migrate branch, or a card falls through both: gating "add the missing `column: todo`" on `status === undefined` while the migrate branch required a pipeline VALUE left a card carrying a legitimate `status:` and no column column-less forever.
- Never TYPE a timestamp — I wrote a future `updated:` three times in one session, each within minutes of running `date`. Read the clock into a variable and paste that.
- A bash script SOURCED FROM ZSH does not error, it answers DIFFERENTLY: same tree, same minute, `source scripts/pin-node.sh` gave bash `v22.23.1` and zsh `v26.5.0` — past the `engines: <26` cap the native deps need — because its `BASH_SOURCE`/`local -a` version gate degrades silently under zsh. I nearly filed the repo's Node pin as broken when the broken thing was my shell. Run a bash-ism under `bash -c` before believing what it told you, and A/B the two shells when the answer is surprising.
- A negative control with its output SUPPRESSED proves nothing: my first hazard A/B piped the naive arm to `/dev/null`, so "nothing was created" was indistinguishable from "the process never ran" — and the other arm had in fact died on a broken `--eval`. Two of three attempts measured my own instrument. Show stderr, and make the arm PRINT something only a real run can print.
- A shared helper can be correct only for its current caller's ambient state: `lib/workdir-path-policy.ts` fixes `INSTALL_ROOT = resolve(process.cwd())` at module load — true in the server, whose cwd IS the install tree, and inverted in a globally-installed CLI, where it would refuse every caller's own directory as "inside the ai-maestro installation". Reuse is right until the new caller breaks the ambient assumption the helper never stated.
- IDENTIFICATION is not AUTHORIZATION, and the authorizing function is the wrong instrument for the identifying question: `checkAuthorizedAgentWorkdir` says ok to ANYTHING under `~/agents/` without reading the registry — correct for "may an agent use this dir?", and it would have called the plugin-SOURCE containers `~/agents/{role,custom,core}-plugins/` agent workdirs. Ask which question you are asking before reaching for the one authority.
- A tool whose name cannot be GUESSED from the corpus it reads is not installed, whatever the filesystem says: ours was `greptrdd` (the words backwards) while `memgrep` shipped and set the `<doctype>grep` convention, so an agent reasoning by that convention searched `trddgrep` and found nothing. Distribution and discoverability are two independent failures and fixing one leaves the other.
- A violation count LARGER than the population it draws from is a broken parse, not a finding — "46 across 21 rules" from 31 gate-qualified citations was a strip-then-split that cross-produced every qualifier against every citation in a row. Sanity-check the count against the corpus SIZE before believing, reporting, or acting on it.
- When a label appears in BOTH code and its own doc comment, a text needle counts the documentation: mine matched a JSDoc gate manifest (`* G10: Idempotency check`) and reported 764 "gates" where 492 real `ops.push` emissions exist, then blamed citations that were pointing at the right place. Match the EMISSION, never the name.
- A per-scope identifier searched file-wide answers about the wrong scope — gate numbers are per-pipeline local and reused (`G10` is one gate in `InstallElement`, another in `DeleteAgent`), so a whole-file grep for `G10:` "finds" it in a pipeline the citation never named. Confine the search to the scope the citation names, or the hit is meaningless.
- One construct can have TWO syntactic forms and a needle that knows one reports the other as ABSENT: a gate is `ops.push(\`G07: …\`)` in a hand-rolled pipeline and `{ id: 'G07', … }` under the transaction runner, so my scanner declared four live gates missing. Before filing "X does not exist", enumerate the forms X can take.
- Skipping the resolution step when the optional half is absent makes the failure counters read 0 because NOTHING WAS CHECKED — indistinguishable from "all resolve". My `continue` on a range-less citation made "pipeline not found: 0, gate not found: 0" vacuous at exactly the moment those became the only checks left. When you delete one half of a redundant pair, the survivor's check must become UNCONDITIONAL.
- Deleting one half of a two-part citation obliges a COMPLEMENTARY neuter pair, and each must redden a DIFFERENT test: re-adding a range failed `carries NO line range`, breaking the qualifier failed `names a real gate inside that pipeline`. One neuter alone would have proven the new rule fires while leaving "is the surviving half load-bearing?" unasked — which is the whole risk of removing a coordinate.
- A permanent check finds what your ad-hoc measurement's regex missed, on its FIRST run: mine matched only `G\d+` while the real qualifier grammar also admits `PG\d+` and `EXE`, so 3 rows survived a sweep I had just called complete. Prefer landing the check to perfecting the script — the check runs against the real grammar forever, the script ran once against your idea of it.
- A citation half that NOTHING checks decays continuously and silently: 22 of 31 gate-qualified ranges (71%) were wrong, every drift POSITIVE (+63 to +623) — pure displacement from code inserted above. A coordinate no test validates is not documentation, it is a lie with a timestamp; delete it or check it.
- `--help` omitting an option is a HYPOTHESIS, not a verdict (a CLI may hide or `allowUnknownOption`) — but "help lists it nowhere, on four levels of the command tree" is enough to justify the probe, and the probe is one command. Do not skip from "undocumented" straight to "broken", and do not stop at "undocumented" either.
- A GUARD WRITTEN AS `[ "$mode" = check ] ||` SILENTLY MEANS "EVERY OTHER MODE EXECUTES", so adding a THIRD mode makes it run the operation it was added to pre-screen: `dispatch validate list` would have actually listed. Write the guard against the mode that ACTS (`[ "$mode" != run ] ||`) so an unwired mode is inert by construction — the safe default for a new enum value is do-nothing, and only one of these two spellings has it.
- `cond && return 0` UNDER `set -euo pipefail` KILLS THE SHELL WHEN `cond` IS FALSE — the statement's own status becomes 1, `errexit` fires, and every later dispatch in that run dies. The equivalent-looking `cond || cmd "$@"` is safe. Same trap as `$?`-after-a-pipeline: the status you get belongs to the construct, not to your intent.
- A PURE HELPER IS A DESCRIPTION OF WHAT WOULD OFFEND; THE CALL SITE IS THE POLICY. I cited `gates.filter(g => !g.readOnly && !g.undo).map(id)` as proof a sequence REFUSES to start — it returns a list, and only the caller testing it for non-emptiness enforces anything. Such a helper is routinely computed and merely logged, or written before the wiring and never called. Cite the branch that acts on the predicate, never the predicate.
- A COMMENT IN THE CALLER HAS NO STANDING ON THE CALLEE'S BEHAVIOUR — ask whether the source you took a reason from is entitled to state it. A gate's own note said its `readOnly` is "what makes its failure roll G08 back"; opening the runner, the unwind is GENERIC over every executed gate, so I had written a designed pairing where the sequence has a uniform property. The same note's other half WAS true and load-bearing — cite the runner, not the annotation.
- AN EXPLANATION THAT DISSOLVES AN ANOMALY IS THE LOAD-BEARING CLAIM, because it licenses INACTION and stops the next reader looking: I measured that one gate of eleven declares no `undo`, then explained it away as "read-only, correct by construction" from log strings recalled a round earlier. One read settled it — an explicit `readOnly: true` field, and a contract stronger than I claimed. Measure the excuse at least as hard as the anomaly.
- WHEN A CORRECTION LANDS, AUDIT THE SENTENCE IT PRODUCED, NOT ONLY THE FACT IT REPLACED — four rounds on one passage moved the error OBJECT to SET to INSTRUMENT to PREDICATE, each fix leaving its own new claim unexamined, and each time the fix's credibility carried the unverified half along. A measured count with an unmeasured adjective ("11 gates WITH COMPENSATION") is read on the count's evidence; the adjective is what argues for acting.
- `\b` DOES NOT WORK IN `git grep -E` (POSIX ERE) — it matches NOTHING, silently, exit 0. Measured: `\b(opus|sonnet)\b` over `.claude/agents/` = **0 files**, the same pattern without `\b` = **5**. A word-boundary sweep proving a NEGATIVE thus "confirms" an absence with a command that could never find anything. Same family: `git log -S` counts OCCURRENCE CHANGES and misses a value SWAP — use `-G` for "what values did this hold".
- A GREP PATTERN YOU WROTE TO FIND X IS A HYPOTHESIS ABOUT HOW X IS SPELLED, so its output is evidence about the PATTERN until you check it against a known case — and line numbers make it read as measurement: mine matched comments by design and counted a gate whose own comment said it is NOT in the sequence, turning 11 structural entries into a confident 15. Bound the range (print the span, compare the next declaration) and count STRUCTURE, never log strings.
- CORRECTING A PROXY READ WITH ANOTHER PROXY READ IS THE COMMON REPAIR, and the second is likelier to be believed because it reads as a dry enumeration: I struck an invented severity sentence and replaced it with a five-gate list I had RECALLED, never opening the pipeline — which owns fifteen, so my subset understated the bypass. A list is not less of an inference than a sentence; when a claim names a STRUCTURE, open the structure.
- A VARIABLE NAME PLUS A `sed` WINDOW IS NOT A FUNCTION'S CONTRACT, and the inference it licenses is the sentence that persuades: a `catch (deleteError)` around a registry delete read as a rollback "firing when the system is already broken" — the enclosing function was `transferAgent` and the site its `mode === 'move'` branch, the SUCCESS path of a user action. The bypass was real; the severity story was fabricated, and already committed. Read the enclosing declaration, not the window.
- **"NOT VERIFIED" AND "VERIFIED ABSENT" MUST BE DIFFERENT TOKENS, or they collapse into the same failure.** A subagent reporting *"0 present / not fully verified"* is evidence that the SUBAGENT STOPPED — never evidence the thing is missing. Both agents that returned that phrasing in one audit were wrong, and a session trusting the line would have manufactured two phantom findings out of an agent's fatigue. Put the distinction in the worker CONTRACT, not in the reader's judgement.
- **`"$rev:path"` IN ZSH SILENTLY EATS THE PATH VIA THE `:t` MODIFIER** — `git show "$r:tests/..."` expanded to `8450bbf6ests/...`, so all 7 revisions errored and the `grep -c` beside them printed `0`, reading as "the check is absent from every revision". Build the spec with `printf '%s:%s'`. Any path whose first char is a modifier letter (`t h r e a`) is the class, and the false answer is ABSENCE.
- `grep -v '^\+\+\+'` PRINTED 0 LINES ON THREE GREPS FOR TWO REASONS, AND THE PIPE HID BOTH: GNU 3.12 warns "stray \" yet matches every line that starts with `+`, so -v prints nothing (rc 1); ugrep 7.8 and BSD 2.6 reject the pattern (rc 2). Which grep a script gets follows the SHELL that runs it (PATH order and aliases differ by shell) — so "0 added lines" over a 2-line diff read as measured. Bracket a literal plus, `grep -E '^[+][^+]'` (2/2 on all three), and read that stage's own rc.
- **A PIPELINE WHOSE PRODUCER FAILS SILENTLY MAKES "NO DIFFERENCE" AND "NO DATA" INDISTINGUISHABLE, and the wrong answer is the CONFIDENT one.** `diff <(json.tool A 2>/dev/null) <(json.tool B 2>/dev/null)` printed `IDENTICAL` — which would have REFUTED the hypothesis and ended the search. Both files had been pruned, the parser's error went to `/dev/null`, and `diff` compared two empty streams; only a positive control caught it. Never suppress a producer's stderr inside a comparison.

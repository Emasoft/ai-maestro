# The dependency graph and board render must stay usable at 100000 documents

## The hole this handles

`lib/trdd-graph.ts` (`loadTrddGraph`, `checkTrddInvariants`) and the `board` / `next` / `why` /
`unblocks` / `roots` subcommands all reconstruct the full edge set from a full corpus read on every
invocation. The graph is the part of the system agents actually steer by — `next` answers "what is
workable RIGHT NOW", `why` answers "what is the root cause of this being stuck".

At 10⁵ nodes: the read is the cost, cycle detection must stay near-linear, and `board` printing
every card is unusable output regardless of how fast it is produced.

## Why it is an EHT

Same reason as its sibling BQC8NQSW: the parent claims the pillar system works at 10⁵. A fast
index-backed *search* beside a graph walk that re-reads 1 GB to answer `why <id>` is not a system
that works — it is one fast question surrounded by slow ones.

## Shape of the fix

- Edges are frontmatter-only (`blocked-by`, `npt`, `eht`, `parent-trdd`, `supersedes`) — they belong
  in the index as rows, so a graph query is a join rather than a corpus read.
- `why` / `unblocks` are **local traversals** from one node; they must not materialise the whole
  graph to answer about one card.
- `board` gains paging / column filters; the default output stays scannable at any corpus size.
- Cycle detection stays near-linear and runs over index rows.

### Box 2 and box 4 cannot both be read literally — the reading is stated, not assumed

Box 2 asks for output *identical to today's*; box 4 asks for output *bounded*. Today's board is
unbounded, so a literal reading of both is unsatisfiable. The reading taken: **box 2 governs the
ANSWER — which cards, in which order — and box 4 governs how many are PRINTED.** A truncated list
is the same cards in the same order, stopping early and saying so.

That reading is then verified in its strongest available form rather than argued: HEAD's output for
all five verbs was captured **before** any edit, and `--limit 0` reproduces each **byte-for-byte**.
So the bound is a DEFAULT, not a capability removed, and "we did not change the answer" is a diff
rather than a claim.

### Box 2 at 10⁵, not just on the live corpus

`next` at HEAD (walk-fed, via `loadCorpus`) vs `next --limit 0` (index-fed): **byte-identical over
31 115 lines / 31 111 ranked rows.** A differential on 3 fixture cards proves the shape; one over

### A REAL BUG the differential found, and it was in the WRITE GATE

Neutering `next` back to `readyQueue(designDir)` was supposed to prove the new differential
non-vacuous. It did — and the two feeders disagreed on the ANSWER: the walk called a card READY
that the index correctly called blocked.

Cause: **`lib/trdd-doctor.ts`'s `asList` was `Array.isArray(v) ? … : []`**, so a legal bare scalar
(`npt: TRDD-X`) was invisible to it — in **all seven** of its call sites: the depth-1 derivation
rules, `GRAPH-BLOCKED-NOT-BLOCKED`, `ORDER-NPT-VIOLATED`, the supersede check, the ready queue, and
the fixer. This is *precisely* the divergence `refList` was exported to end one layer down
(greptrdd carried the identical array-only reader and reported a scalar-blocked card as READY), and
the linter — the WRITE GATE — kept it longer, silently, because a rule that cannot see an edge
reports no finding about it.

Fixed by delegating to the one owner: `const asList = (v) => refList(v)`. `normalizeTrddRef` is
idempotent, so the sites that re-normalize are unaffected.

**Why it survived: no live run could expose it.** Measured — **0 of 196** live cards carrying a ref
field use the scalar form, and `validate` output is byte-identical before and after (303 rows, 0
errors). So the fix is inert on today's corpus and correct for the form the spec's `3P-DAG` id-forms
clause admits. Two new tests pin it from both ends (the lint and the ranking), each with its own
positive control, both reddened by NEUTER-2.

### Two instrument failures, recorded because each read as a result

- `scripts/pin-node.sh` **must be sourced**; executed, it prints a usage line. `$(… | tail -1)` took
  that line as the node path, so `env … "" --import tsx …` failed instantly and **every timing read
  `0.00`** — a table of zeros that looks like an impossibly fast tool. Fixed by timing through
  `scripts/with-node.sh` (the documented entry point) and positive-controlling the timer against a
  500 ms busy loop first.
- `AIM_NODE` holds a VERSION (`v26.5.0`), not a path.
